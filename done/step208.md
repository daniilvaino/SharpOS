# step 208 — команды окружения в оболочке, `$ИМЯ`, интерактивный KQL, дополнение запроса

## Контекст

Окружение процесса появилось в step207. Объём оболочки задал ведущий агент: только команды (`export`, `unset`, `env`, `which`, `cd`, `pwd`), `$ИМЯ` и `${ИМЯ}` из окружения, сценарий старта в переменной. Переменных оболочки, `$(…)`, `x=1`, `X=1 prog`, циклов, `if`, функций нет; на неподдержанное — ошибка с местом.

KQL — по предложению пользователя: `… | KQL` без запроса ждёт тип входа и спрашивает запрос уже с ним. В строке оболочки дополнение тоже нужно, упрощённое.

## 1. Разбор: один раз, только синтаксис

Bash разбирает строку один раз, а подстановки делает перед запуском каждой простой команды, и результат заново не разбирается. Так же сделано здесь.

- **Режим.** ShellSyntaxTree — анализатор безопасности (Netclaw). В режиме по умолчанию он отвергает `$NAME`. `IsolatedNonInteractive` пропускает `$NAME`, но моделирует `for … in`: плоский `Clauses` тогда содержит только тело цикла, а `echo $(ls)` даёт два клаузы. Поэтому:
  - отказ ищется по дереву `parsed.Syntax`: `ForEachSyntax`, `GroupSyntax`, `CommandSubstitutionSyntax`, `ExecutionRegionSyntax`, подстановки внутри `SimpleCommandSyntax`;
  - значения слов берутся из `ClauseElement.Raw`, не из `Value` и не из `Redirect.Target`: там догадки анализатора о содержимом переменных.
- **`export` и `unset`** анализатор отвергает всегда (`IsPotentialBindingMutation`). До разбора они переименовываются в `__export`/`__unset` — только голое слово на месте команды, найденное его же лексером (`BashLexer.Tokenize`, внутренний тип, компилируется в ту же сборку). `'export'` в кавычках и `echo export` не трогаются. Столбец ошибки пересчитывается обратно к введённой строке.
- **Отказ — до запуска** чего-либо в строке: `export A=1; echo $(pwd)` не выставляет `A`. Каждое слово один раз раскрывается без подстановки значений — так находятся `$1`, `$?`, `${A:-x}`, `$'…'`. Код 2, `sh: not supported: … (column N)`. То, что отвергает сам разборщик (`X=1 prog`, `` `…` ``, `if`, `{ …; }`), идёт с его текстом и без столбца.

Проверено на хосте пробником (функции из `Executor.cs` + исходники ShellSyntaxTree): 28 строк, столбцы сходятся с введённой строкой.

## 2. Подстановка

`Executor.Expand`:
- кавычки снимаются;
- `\` экранирует; внутри `"…"` только `$ " \` и перевод строки;
- `$ИМЯ` и `${ИМЯ}` — из окружения процесса в момент запуска команды; нет переменной — пусто;
- в `'…'` ничего не раскрывается;
- `~` в начале слова — `HOME`;
- деления на слова нет: `export A='a b'` даёт программе один аргумент.

Цель `> $HOME/x.txt` раскрывается так же, из текста перенаправления, и считается от рабочей папки.

## 3. Команды

- `export ИМЯ=значение…`; без аргументов — список. `export ИМЯ` ничего не делает: переменных оболочки нет. Пустое значение удаляет переменную — окружение устроено как в Windows.
- `unset ИМЯ…`.
- `env` — список; `env ИМЯ=значение…` — список с добавкой; `env ИМЯ=значение программа аргументы` — запуск через `Process.Start(…, environment:)`, в том числе стадией конвейера. Встроенную команду `env` не запускает: отказ.
- `which ИМЯ…` — путь по `PATH` или `shell builtin`; не нашлось — 1.
- `ENV` — сценарий, который приглашение выполняет при старте (как в POSIX sh). Не для `sh -c` и не для сценария аргументом.
- Tab: `$ИМ`, `${ИМ` и слова после `unset`/`export` — имена из окружения.

## 4. Интерактивный KQL

`PIPEGEN 100 | KQL`:
1. KQL ждёт объявленный тип (`PipeTransport.WaitSchema`);
2. приглашение `kql (LogEntry)> ` — редактор строки оболочки (`LineReader`, своя история `\kql_history`);
3. Tab — `KustoCodeService.GetCompletionItems` по таблице `Input` с этими столбцами; над Expando таблица открытая;
4. запрос, который не связывается, — сообщение и новый вопрос: данных ещё не читали;
5. Enter запускает запрос на потоке тем же путём, что `KQL 'запрос'` (`OverInput` разделён на чтение типа и выполнение);
6. пустая строка, Ctrl+C, Ctrl+D — выход без чтения, писатель получает обрыв (141).

Клавиатура в ядре общая, стадия конвейера читает её, пока оболочка ждёт стадии.

Кандидаты — `BeforeText` элемента (`abs(`, `where `, `Level `). Знаки, которые Kusto предлагает тоже (`(`, `[`, `@`), отброшены. Проверено на хосте: после `where ` — столбцы первыми, затем функции; `cou` → `count()`, `countif(`…; `su` после `|` → `summarize `.

## 5. Дополнение в строке оболочки (упрощённое)

Tab внутри открытых кавычек аргумента `KQL` (`PIPEGEN | KQL 'where Le`) — `KQL --complete ТЕКСТ`:
- KQL отдаёт строками начало слова и кандидатов;
- `Input` — открытая таблица без столбцов: операторы, функции, ключевые слова, без имён столбцов, потому что строка не запущена и типа нет;
- `|` внутри кавычек — часть запроса, не труба.

Цена — запуск KQL.EXE на каждый Tab; не замерялась.

`KQL --complete` со входом (`PIPEGEN 0 | KQL --complete 'where Le'`) дополняет по объявленному типу — те же кандидаты, что приглашение. `SHELL.EXE --complete СТРОКА` печатает то, что Tab предложил бы в конце строки. Через них батарея проверяет дополнение без клавиатуры (тест 20); непроверенным остаётся только сам редактор строки.

## 5a. Тождественный `project` сохраняет тип

Любой `project` отключал пересылку блоков (`Plan.Of`): даже `project Level, Text` над LogEntry давал Expando. Теперь `project`, перечисляющий все столбцы того, что к нему приходит, по имени и в том же порядке, вырезается из выполняемого запроса (`WithoutIdentityProjects`). Что приходит, берётся из связанного дерева — тип результата выражения слева от черты, — поэтому `summarize … | project Level, n` судится по столбцам `summarize`. Перестановка, подмножество, переименование, выражение — по-прежнему новые сообщения. Запрос с ошибкой не трогается: она сообщается по тексту как написан. ## 5b. Каталоги и удаление файлов

До сих пор FAT-писатель только создавал и дописывал. Теперь (`Hal/Fat32Remove.cs`):

- **Удаление файла:** записи помечаются `0xE5` — 8.3 и все записи длинного имени перед ней (`FindIn` теперь запоминает, где они лежат, в фиксированных буферах без выделения: путь загрузки), потом освобождается цепочка. Порядок такой, что сбой посередине оставляет ничейные кластеры, а не запись на свободные. Открытый файл (читатель — по кластерам, писатель — по записи) и файл, который пишется секторами (журнал загрузки), не удаляются.
- **Создание каталога:** кластер с `.` и `..` (`..` корня — 0, как в FAT32) и запись с атрибутом `0x10` в родителе — 8.3 или длинное имя, тем же путём, что файл (`TryWriteDirectoryEntry` и `TryCreateLongEntry` получили атрибут и первый кластер).
- **Удаление каталога:** только пустого — ничего, кроме `.` и `..`.
- Курсор перечисления каталога сбрасывается при любой правке каталога — продолжение обхода иначе сдвигалось бы.

Программам — служба `FileManage` в хвосте таблицы (`int (op, path, ulong* result)`: удалить, создать каталог, удалить каталог, что за путь); версия ABI та же. SDK: `File.Delete`, `Directory.CreateDirectory` (с родителями, возвращает `DirectoryInfo` — урезанный: имя, путь, `Exists`), `Directory.Delete(path[, recursive])`, `Directory.Exists`; `File.Exists` на каталог теперь «нет», как в BCL. Исключения — как в BCL; в std добавлены `DirectoryNotFoundException`, `UnauthorizedAccessException`. Оболочка: `mkdir [-p]`, `rm [-r] [-f]`, `rmdir`.

DATATEST, тест 21 — 19 проверок, в QEMU все прошли (вложенные каталоги; длинное имя удалено, сосед на месте, имя создаётся снова; отказы BCL; открытый файл; рекурсивное удаление; `mkdir`/`rm`/`rmdir`). Ожидания батареи: DATATEST 125, `--quick` под стрессом 122.

Найдено попутно (в `donext`): имя, которое влезает в 8.3, хранится заглавными — `ls` показывает `A.TXT` для `a.txt`; PowerShell через PAL каталоги не создаёт и файлы не удаляет.

## 7. ФС до хорошего состояния

Порядок пользователя: проверка и мясорубка → сброс кэша устройства → рост
каталога и переименование → API и команды → регистр и не-ASCII → `Seek`/
`SetLength` → кэши и FSInfo. PowerShell (PAL) — вне его.

**Проверка снаружи.** `tools/Test-FatImage.ps1`: после выхода QEMU
`run_build.ps1` гоняет `fsck.fat -n` по образу (свой dosfstools или WSL),
отчёт — `last_fsck.log`; порча — провал прогона. Проверено на копии образа с
одной испорченной записью FAT: 94 потерянных кластера найдены. DATATEST 22 —
мясорубка: 600 операций по зерну (создать, дописать кусками неровной длины,
удалить, переименовать, каталог создать и удалить), модель содержимого, сверка
листингов, файлы вне дерева не тронуты.

**Сброс кэша устройства.** `Disk.Flush`: AHCI `FLUSH CACHE EXT` (0xEA), USB
`SYNCHRONIZE CACHE (10)` (SCSI 0x35). После закрытия записанного файла, правки
каталога и в `Platform.Shutdown` (без ожидания тома — паника посреди записи его
держит). Отказ устройства — не ошибка записи: больше не спрашиваем.

**Рост каталога; переименование.** Полный каталог получает кластер. Первая
версия оставляла записи `0x00` («конец каталога») в хвосте прежнего кластера:
длинное имя, не влезшее в два последних слота, уходило в новый кластер за ними —
листинг, поиск и проверка «пуст ли» останавливались раньше. Рекурсивное
удаление сочло каталог с 269 файлами пустым и удалило его; `fsck` нашёл 269
потерянных кластеров — это и поймала проверка снаружи. Теперь при росте `0x00`
прежнего кластера становятся `0xE5`. Переименование: новая запись раньше
удаления старой, атрибуты, время и размер переносятся, у каталога — `..`,
каталог в самого себя — отказ, открытый на запись — отказ.

**API и команды.** `FileManage` оп 4 отдаёт время записи, оп 6 — объём тома;
время записи обновляется при закрытии (раньше оставалось временем создания).
SDK: `GetFiles`/`GetDirectories`/`GetFileSystemEntries`/`Enumerate*` (шаблоны
`*` `?`, `AllDirectories`), `FileInfo`, `DirectoryInfo`, `DriveInfo`,
`File.Copy`, `ReadAllText`, `GetLastWriteTime`, `SearchOption`, `DriveType`.
Оболочка: `cp [-r]`, `ls -l`, `df`. Попутно: `DateTime.Now` у приложений был
«год один плюс время с загрузки» (служба даты не существовала); служба процессов
оп 19 отдаёт часы ядра, приложение берёт смещение один раз.

**Регистр и не-ASCII.** Регистр 8.3 — флаги байта 12 (0x08 имя, 0x10
расширение), смешанный — длинным именем. Пути от программ и имена обратно —
UTF-8 (ядро: `TryReadUtf8Path`, `TryWriteUtf8Name`, рабочая папка и путь образа;
SDK: `AppHost.TryEncodePath`, `AppFile`, `Process.Start`, `EnvironmentStore`).
До шага всё не-ASCII в пути отказывало, а в листинге было `?`. Сравнение имён —
`char.ToUpperInvariant`, расширенный в std на Latin-1, греческий и кириллицу.

**`Seek`, `SetLength`, запись на месте.** У пишущего файла позиция: внутри —
перезапись кластеров (чтение, правка, запись), буфер дописывания
перечитывается; за концом — нули в промежутке; `SetLength` вниз освобождает
хвост цепочки и обнуляет остаток последнего кластера, вверх — нули. Режим
открытия 3 — на обновление. Служба `FileControl`. `FileStream` на запись и
чтение-запись — через неё; только на чтение — как был (файл целиком).
`File.OpenWrite` не обрезает, как в BCL.

**Кэши и FSInfo.** FSInfo ведётся: число свободных кластеров двигают две
функции, меняющие записи FAT; на диске — «неизвестно» с первой правки до точки
сброса, там — точное число и подсказка. `fsck` сверяет его: сходится. Кэш
одиночных секторов (`CachedDisk`, 1024 сектора, сквозная запись). Замер выявил

## 10. USB-диск: восстановление, сброс кэша; кэш программ; запуск по фазам

С экрана пользователя (`-UsbOnly`, WHPX, окно QEMU увеличено): в `\home` `ls` —
«cannot list», `mkdir` — «no room», `cd` и `mkdir` по нескольку секунд. Образ
снаружи цел; на AHCI не повторялось.

**Корень.** `SYNCHRONIZE CACHE` (сброс, step208 §7 — после каждого закрытого файла)
под QEMU отвечает, когда хост сбросил файл образа. Первый сброс после загрузки
выталкивал весь свежий `esp.img`: статус пришёл через 2,8 с, драйвер ждал 5 с, но
ожидание обрывалось раньше — потолком в 50 млн оборотов. Отказ любой фазы BOT
драйвер возвращал как `false` и только: конечная точка оставалась Halted или с
брошенным TRB, следующая команда получала чужой ответ или таймаут — и так до
перезагрузки. Поймано строкой `[usbmsd] scsi 0x35 failed reading status, xhci
code 0x00 (no event, timeout)` в замере ниже.

**Сделано.**
- `UsbMassStorage`: восстановление по BOT 5.3/6.6 — STALL в данных: снять HALT,
  дочитать статус; STALL статуса: снять HALT, прочитать ещё раз; иначе Reset
  Recovery (класс-запрос 0xFF, CLEAR_FEATURE ENDPOINT_HALT на обе трубы) и один
  повтор команды. Каждый сбой — строка `[usbmsd]` в COM1 (фаза, опкод, код xHCI).
- `XhciRecovery.TryResetBulkEndpoint`: Halted — Reset Endpoint + Set TR Dequeue;
  иначе Stop Endpoint и пересоздание конечной точки (`Configure Endpoint`
  drop+add, чистое кольцо): только так сбрасывается toggle хоста, а CLEAR_FEATURE
  сбрасывает его у устройства. QEMU toggle не моделирует — проверит железо.

## 11. `ArrayPool` пулит, `MemoryStream` со span-перегрузками

Причина медленного `BinaryWriter` — три выреза сразу:
- `MemoryStream` не переопределял `Read(Span<byte>)`/`Write(ReadOnlySpan<byte>)`:
  каждый `Write(int)` и `ReadInt32` шёл через базовый `Stream` — аренда у
  `ArrayPool`, копия, `try`/`finally`, возврат;
- `ArrayPool` не пулил: `Rent` выделял, `Shared` создавал новый пул на каждое
  обращение — три выделения на четыре байта. Обоснование в комментарии (статик
  ломает cctor) устарело давно;
- в `BinaryReader` вырезан короткий путь по `MemoryStream`.

Сделано портом из dotnet/runtime: в `MemoryStream` — `Read(Span)`,
`Write(ReadOnlySpan)`, `ReadByte`, `WriteByte`, `InternalReadSpan` (и обнуление
промежутка при записи за концом, как в оригинале, — раньше его не было и в
`Write(byte[])`); в `BinaryReader` — короткий путь (`is MemoryStream`, `Type`
нет); `ArrayPool<T>` — абстрактный, как в BCL, `Shared` — `ConfigurableArrayPool`
(корзины под `lock` вместо `SpinLock`; потоковый пул BCL требует `[ThreadStatic]`),
`Utilities`. Статик обобщённого типа работает и для ссылочного `T` (общий код):
AOTTESTS проверяет `ArrayPool<string>`.

PIPEPERF под WHPX, `BinaryWriter` + `BinaryReader`, на сообщение:

| граф | было | стало | хост |
|---|---|---|---|
| объект, 2 числа и строка | 0,9–2,0 мкс | 0,37–0,76 | 0,06–0,12 |
| объект с массивом из 100 | 44–99 мкс | 5,9–13,4 | 2,4–6,6 |
| `Expando` из 8 (хост — `Dictionary`) | 8,5–18 мкс | 5,0–12,8 | 0,7–1,5 |

Полный путь трубы не изменился (4,8–4,9 мкс на массиве из 100): она не ходит
через `Stream`. Остаток разрыва с хостом — в donext. AOTTESTS +4 (пул байтов,
пул строк, `MemoryStream`, `ReadInt32` за концом): ожидания 307. Батарея 28/28.

Батареи: AHCI 28/28; `-UsbOnly` 28/28 (дважды); fsck чистый. DATATEST 212 / 209.

## 14. Теневая карта раскладки; трубы между процессами

**Теневая карта.** «Режим для деревьев» по каталогу невозможен: общая ссылка —

сообщениями, до 128 (4 МиБ), сверх — прежняя хеш-таблица. Смысл прежний: общие
ссылки и циклы сохраняются. Раскладка большого графа 2642 → 3099 раундов за 3 с
(+17 %); `Find` 38 % → 1,5 %, первым теперь `Add` — первое касание объекта.

## 16. Остаток переключения — опрашивающий поток CoreCLR

После §15 маленькое сообщение при ёмкости 16 стоило ~6,8 мкс на переключение.
Двумя потоками одного процесса (`PIPEPERF --ipc-threads ROOM COUNT`) — ~4,2, и
стоимость гуляла между прогонами: при одном переключении на ожидание дёшево, при
~1,7 — дорого, ждущий стоял 28–32 мкс вместо 9. Профиль сэмплера: первым —
`Hpet.ReadCounter`, вызывающий — `ThreadStubs.WaitForSingleObject` (ветка `Event` с
конечным таймаутом). Ожидание с таймаутом было циклом «проверить, прочитать HPET,
`Scheduler.Idle`»; `Idle` спит, только когда работы ни у кого нет, — рядом с
писателем и читателем фоновый поток CoreCLR не засыпал никогда, вклинивался
между каждым их переключением и читал HPET (7,7 мкс под WHPX).

Сделано: `Event.Wait(timeoutMs)` — поток в списке ожидания и в очереди таймеров
сразу (разные связи), будит первое; по сроку снимает себя со списка.
`WaitForSingleObject`: `Event` и завершение потока (через `JoinEvent`) с конечным
таймаутом — им. Семафор, мьютекс и `WaitForMultipleObjects` — прежним опросом
(donext); сон до тика вместо `Idle` в них пробовался и откачен — без нужды.

Маленькое сообщение при ёмкости 16: между потоками 1,56 → 0,26–0,27 мкс, между
процессами 2,06 → 0,25–0,30 (как при 4096); переключений столько же, сколько
ожиданий. `Bench.dll` (CoreCLR) — без изменений; первый запуск в сеансе всегда
вдвое медленнее второго (массив из 100: 10,4 и 3,4 мкс), сравнивать вторые.

## 6. `string.Concat(IEnumerable<string>)` в std

В QEMU Tab в KQL не дополнял ничего, хотя `KQL --complete` отдавал верное начало слова. Кандидатов Kusto давал, а `CompletionItem.BeforeText` был пуст: он строится через `string.Concat(ApplyTexts.Select(…))`. Такой перегрузки в std не было, и вызов молча связывался с `Concat(object)`, то есть с `ToString()` перечислителя. KQLTEST этого не видел: он сверяет `DisplayText`.

Добавлены `Concat(IEnumerable<string>)` и `Concat<T>(IEnumerable<T>)` — порт из BCL (`String.Manipulation.cs`), `StringBuilder` вместо `ValueStringBuilder`.
