# step 185 — подготовка к трубам: сбой приложения не роняет машину, точная сборка ядра, вытеснение под лаунчером

Шаг начался со сверки спецификации «Трубы SharpOS: архитектура» (Р1–Р45,
С1–С16) с кодом. Сверка дала план (`pipe_plan.md`, разделы «Починить»,
«Подготовить под трубы», «Проверить опытом»). Здесь — раздел «Починить», пункты
1–5 и 9: то, без чего первая труба между ядром и приложением легла бы на
неверные допущения.

Прототип межобразных объектов (`std-no-runtime/Diagnostics/*`,
`KernelPipeHandoff.cs`, `ForeignApp`) из дерева убран раньше и лежит в
`work/foreign/tree-snapshot/`. На ESP остался старый `FOREIGN.EXE` — он читает
хвост таблицы служб с другими полями и падает (только чтение); с образа его
надо удалить руками.

## Что было не так

| | Как было | Чем грозило |
|---|---|---|
| `RhpStelemRef` | Ни null, ни границ, ни типа элемента. ILC перед вызовом границу не проверяет | Запись за конец массива ссылок молча портила память за ним |
| Сбой в приложении | `HwFaultBridge` создавал исключение типа **ядра**; catch приложения сравнивает таблицы по указателю — не совпадал ни `catch (Exception)`, ни `catch { }` (в IL это `catch (System.Object)` приложения) | Любой сбой приложения → `FailFast` → `Panic` → машина стоит |
| Необработанное исключение | `FailFast` → `Panic` всегда | Приложение роняло машину |
| IF после пойманного сбоя | Обработчик и всё после него — с выключенными прерываниями до следующего `IRETQ` | Первый `Sleep` после catch не просыпается |
| Сборка ядра | Хук `GC.Collect`/сборки при нехватке — `CollectConservative` (step131). Он сканирует только свой стек и только ниже вершины загрузочного потока | На другом потоке и внутри службы приложения — ни одного стекового корня; стеки остальных потоков не обходились вовсе |
| Вытеснение | Только вокруг проб и в сеансе CoreCLR | Приложение, не уступающее процессор, держит всех |

## Что сделано

**1. `stelem.ref`** (`GcRuntimeExports.RhpStelemRef`) — порт `TypeCast.StelemRef`:
`NullReferenceException`, `IndexOutOfRangeException` (и отрицательный индекс),
`ArrayTypeMismatchException`. Тип сначала только считался: прогон всех приложений
дал ноль записей чужого типа в массивы ядра, после этого — строго. Без проверки:
массив как элемент или значение (нет приведения массивов, п. 6), вариантность.
`RhpLdelemaRef` — по-прежнему без проверок.

**3. Прогон сбоя в приложении** (`AotTests`, `HwFaultProbe`). #GP на нечётном
неканоническом адресе (ключ типа из прототипа), обход дошёл до кадра с `try`,
ни один catch не совпал, `Panic`. Это и решило, что ловушка нужна в ядре.

**4б. Ловушка в ядре.** `JumpStub` теперь сохраняет все неизменяемые регистры
ядра (rbx, rbp, rsi, rdi, r12–r15, xmm6–15), RFLAGS, CR3 и RSP в `JumpContext` на
стеке ядра — раньше только r12/r13, остальное ядро ждало от приложения, и
свернуть его на полпути было нельзя. Вторая точка входа («свернуть», смещение
0x800) и обычный выход — один хвост восстановления. `FailFast` зовёт
`JumpStub.TryAbortCurrentApp()`: восстанавливает `ExInfoHead.s_head` и глубину
`Preemption`, печатает `[app] unhandled exception: app ended, exit code 134` и
возвращается в `JumpStub.Run`, дальше обычная уборка. Не срабатывает из
обработчика прерывания и на рабочем потоке приложения (там по-прежнему `Panic`).

**4а. Исключение типа приложения.** Служба `SetHwExceptionFactoryAddress`;
`AppRuntime.CreateHardwareException` создаёт NRE/AVE/DivideByZero из std
приложения (сборщик придержан на время выделения — на стеке кадр прерывания).
`HwFaultBridge.ResolveException` берёт фабрику, если RIP в образе текущего
приложения; сбой в коде ядра, в том числе в службе, остаётся типа ядра.

**5. IF** восстанавливается из RFLAGS прерванного кода перед `DispatchEx`.

**2. Точная сборка ядра.** Хук → `KernelGC.Collect`. Обход кучи ядра
останавливается на переходнике службы или первом кадре чужого образа и
продолжается с каждого `JumpContext` потока (`ContinueBelowApps`) — кадры ядра под
приложением. Кадры приложений не обходятся: в них объекты приложения, а образ
вложенного родителя снят с отображения. `Thread.InterruptDepth` (счётчик на
потоке, ведёт `Idt.Dispatch` для таймера): сборка из обработчика отказывает.
Вытесненный поток сканируется консервативно от точки остановки до верха стека
(своего или стека приложения из `JumpContext`). Маркировщик приложений
отбрасывает кандидатов с таблицей типа вне своего образа. Проба
`Probes.KernelGcAcrossApp`: строка, живущая только в кадре `RunExternalApp`,
переживает сборку из службы дочернего приложения.

**9. Вытеснение под лаунчером** (`Probes.PreemptLauncher`; запасной
`PreemptAppCodeOnly`). Модель `preempt_disable` на одном процессоре; секции
`Preemption.Suppress()` уже были в 23 файлах ядра. Добавлено:
- планировщик: очереди, реестр, счётчик id, `WakeFromWait`, `MakeRunnable`;
- `NativeArena.Allocate`;
- `Fat32` — повторно входимая блокировка (`Fat32.Lock.cs`), не `Suppress`:
  операции ждут диск;
- `ExInfoHead.s_head` переключается вместе с потоком (`SwapExceptionChain`);
- приложения: аллокатор и сборщик — секции на счётчике ядра
  (`AppServiceTable.PreemptionDepthAddress`, `AppPreemption`);
- статические конструкторы потокобезопасны: один поток запускает, остальные
  ждут, владелец проходит сквозь свой; внутри прерывания — прежнее
  однопоточное правило (`ClassConstructorRunner.s_canWait`).

## Корни, найденные прогонами вытеснения

**Утечка подавления в `DispatchEx`.** Первая версия держала `Suppress` на всю
диспетчеризацию и снимала его перед переходом в catch-funclet. Если `finally`
бросал во втором проходе (проба `eh L15 collided unwind`), внешняя
диспетчеризация бросалась на полпути, её `Allow` не исполнялся, глубина
оставалась > 0, и таймер больше не переключал никого. `PreemptionProbe` повис на
рабочем потоке без единого `Yield`. Подавление из диспетчера убрано совсем: его
состояние на стеке потока, цепочка `ExInfo` своя у каждого потока, изменяемых
глобальных статик в коде EH нет.

**Заголовок объекта писался после критической секции аллокатора.** `RhpNewFast`,
`RhpNewArray`, `RhBox`, `Array.CreateInstance`, делегаты — все писали таблицу
типа после `AllocateRaw`. Поток, вытесненный между выделением и этой записью,
оставлял блок со старой отметкой «свободно»; сборка в другом потоке возвращала
его в список свободных, и один блок получали два объекта. `AotTests` падал на
`keep[i] is int[]` — у объекта мусор вместо таблицы типа. Теперь
`GcHeap.AllocateObject/AllocateArray` пишут заголовок внутри секции.

**Чтение снятого стека в `ThreadDump`.** Печать «idle window» читала
сохранённый RSP текущего потока, оставшийся на стеке уже завершённого
приложения, — #PF из тика сэмплера, и ловушка 4б свернула **лаунчер** (до
запрета на сворачивание из прерывания). Проверка `Pager.TryQuery` перед
чтением.

## Прогоны

QEMU, `SHARPOS_GUI=1`, `-UsbOnly -SkipCoreClr -Autorun`
(`apps_native/Shell/autorun.sh`: AotTests дважды, BenchAot):

- `write barrier (ref field + GC.Collect): ok`, `collect was precise: ok val=11`;
- `[preempt] switches=145 … PASS`;
- AotTests 95/95 дважды: шесть проверок `stelem`, три проверки вытеснения
  (занятый поток не морит другой; два потока выделяют и собирают; два потока
  бросают и ловят);
- `[kgc-probe] … ok` на каждом вложенном запуске;
- `[appwalk] … conservative=1` и `=2` во время проверок вытеснения — п. 2б
  исполнялся. Рядом `unresolved=1/2` со `skipped=0x7E13F04E<-Idt.Dispatch+0xa0`:
  точный обход припаркованного потока останавливается на заглушке входа в
  прерывание (у неё нет unwind-данных), дальше его покрывает скан;
- `[sh] done ran=3 failed=0`; красные строки ядра — прежний набор
  (`enum.toString`, `[ModuleInitializer]`, `rethrow preserves stack trace`,
  `string.Format`, `[term]`, `[ahci]`).

Ручные прогоны до этого: режимы `HwFaultProbe` 1 (пойман, `Sleep` после catch
вернулся), 2 (сбой без обработчика → `app ended, exit code 134`), 3
(необработанный `throw`, три запуска подряд из лаунчера); все приложения
пакета, в том числе DOOM, оболочка, эмуляторы.

На железе ничего из этого не гонялось.

## Уроки

- **README и limits расходились с кодом месяцами, и это стоило ложной
  уверенности.** Строка «Аппаратный сбой → managed-исключение» стояла ✅ для
  приложений с 2026-05-21 (`f0fee05`, «gate L13» — проба **ядра**), пережила
  переименование столбца ELF-app → PE-app в step141 (`7fe865d`), хотя limits со
  step140 писал «отложено: `RhpThrowHwEx` в аппе». Раздел limits «`KernelGC.Collect()`
  по умолчанию точный» написан в step110 и стал неправдой в step131, когда хук
  переставили на консервативный путь. Прогон показал обратное за один запуск.
- **Зелёная проба, которая не может покраснеть, хуже отсутствующей.**
  `PreemptedAllocProbe` (step155) выделяет в одном потоке и не держит ни одного
  блока дольше итерации — блок, отданный дважды, ей не виден; она была зелёной и
  до, и после найденной гонки. `array covariance (stelem.ref)` проверял только
  правильную запись. Новые проверки строились так, чтобы без исправления
  падать (две нити держат объекты и сверяют содержимое; занятый поток без
  `Yield` с ограничением по часам).
- **Счётчик пути, которого не видно.** Консервативный скан вытесненного потока
  (п. 2б) прошёл бы любой прогон, даже не исполнившись; в `[appwalk]` добавлено
  `conservative=`.
- **Подавление на пути, который может быть брошен на полпути, течёт.** Где
  управление уходит нелокально (catch-funclet, `finally`, бросающий во втором
  проходе), парный `Allow` не гарантирован.

## Отложено

- Необработанное исключение в **рабочем** потоке приложения — `Panic`.
  Свернуть приложение из чужого потока значит прервать главный, спящий в
  планировщике.
- Блокировки служб в момент гибели приложения не снимаются.
- `RhpLdelemaRef` без проверок; приведение массивов (п. 6).
- Вытеснение на железе; SMP — настоящие блокировки (п. 10).
- `FileStream` приложения молча выбрасывает запись (п. 7), версии ABI SDK/ядра (п. 8).
