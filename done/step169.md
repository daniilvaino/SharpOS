# step 169 — бенчи по всем фронтам, gen0, вывод, NativeAOT-бенч, корни GC приложений

Продолжение step168: инструмент замеров расширен на всё, что подозревалось в
`work/perf-suspects.md`, и по нему — правки в порядке 1 → 3 → 2 плана
(вывод, бюджет gen0 и аллокаторы, исключения). Исключения не тронуты: вывод
и gen0 закрыты, по дороге нашлись две ошибки корректности (повторный вход в
терминал, корни GC приложений), они и заняли конец шага.

## Инструмент

**Счётчики** (`PerfCounters`) — теперь перечисление на фиксированном буфере
(массив потребовал бы cctor, limits §1). Отчёт снимает все разницы до первой
строки, чтобы не считать сам себя:

| строки | что |
|---|---|
| `clock.*` | часы hosted-яруса (step168) |
| `disklog.*`, `com1/3/4.chars`, `screen.*` | секторы дискового лога, символы по портам, перерисовки |
| `write.*` | запись программ, как её обслуживает ядро: службы AOT и консоль hosted |
| `sink.*`, `terminal.lock/feed_ms` | посимвольно по стокам, по TSC; за `PerfCounters.TimeSinks` (выключено — сам стоит 25–35 % вывода) |
| `terminal.drops` | символы, выброшенные терминалом за занятостью замка |
| `seh.*` | `RaiseException`, поиски в таблицах функций (какая ответила), размотки |
| `kgc.*` | сборки кучи ядра |

Интервалы: `init`, `census`, `run.<имя>` — теперь и для PE-приложений из
лаунчера, не только управляемых.

**Bench** (`apps_managed/Bench`) — восемь замеров: `alloc.short`,
`alloc.retained`, `strings`, `collections`, `exceptions`, `jit`
(`DynamicMethod` ×100), `tasks`, `output`; у каждого `ns_per_op` и сборки по
поколениям.

**BenchAot** (`apps_native/BenchAot`, `BENCHAOT.EXE`) — та же работа на
NativeAOT-ярусе приложений, время по HPET из таблицы служб. Отличия
вынужденные: нет `jit`; задачи пачками по 16 — ядро держит не больше 32 ещё не
стартовавших потоков приложения (`PendingAppEntries`), 50 сразу обрушили
`Wait`; `alloc.short` пишет в кольцо из 64 ссылок — присваивание в одну
локальную ILC выкинул как мёртвую запись и намерил 3 нс. `output.first` —
тот же вывод до задач (детектор, см. ниже).

**Эталоны.** `tools/bench-host-reference.log` — `dotnet Bench.dll` на ПК.
`run_linux_ref.ps1` — Debian 13 в том же QEMU (TCG, тот же `-cpu`, 1 CPU,
2 ГиБ) с рантаймом .NET 10: образы BENCH и cloud-init через mtools, `-snapshot`,
результат в `tools/bench-qemu-linux-reference.log`. Вывод бенча идёт в ttyS1:
getty на ttyS0 делал vhangup и убивал shell посреди прогона. Эмуляция есть в
обоих — `x linux` и есть цена самого SharpOS.

**`perf_report.ps1`** — конфигурация прогона из лога (форк, `-cpu`,
ускоритель, диск) с предупреждением, если прошлый прогон был в другой;
столбцы `x host`/`x linux`; `-Label` пишет прогон в `docs/perf-history.csv` и
перестраивает таблицу в `docs/perf-progress.md`. Тёплая медиана — по прогонам
после первого.

**`run_build.ps1`** — `-ForkConfig Release` по умолчанию (Debug-форк был
подозреваемым 15–16: закрыт), `-Cpu` (по умолчанию `qemu64,+nx`), сборка и
выкладка Bench, BENCHAOT в списке приложений. Баннер печатает конфигурацию
форка (`[info] fork: Release`).

## Правки

### Перерисовки терминала — не чаще 60 раз в секунду

Каждый перевод строки рисовал экран, а рисование после новых строк внизу —
это сдвиг всего экрана, ~0.5 мс под QEMU. 200 строк Bench стоили 132 мс только
перерисовок. Теперь перевод строки рисует, лишь если прошлый кадр старше
1/60 с; остальное дорисовывает `InputPump` (опрос раз в 10 мс,
`TerminalConsole.CoalescePaints`). Явный `Flush` — конец строки ядра, ожидание
ввода — рисует сразу. Экран 132 → 10 мс на прогон, вывод 1.00 → 0.40 мс на
строку.

### Кеши процессора → бюджет gen0

`GetLogicalProcessorInformation` в форке ничего не отдавал, GC брал gen0
по умолчанию — 78–87 сборок на `alloc.short`. Теперь ядро читает CPUID
(`Hal/CpuCaches.cs`: лист 4, иначе `0x8000001D`, иначе старые AMD
`0x80000005/6`), `SharpOSHost_GetCacheDescriptors` отдаёт записи
CACHE_DESCRIPTOR, а форк только раскладывает их в
`SYSTEM_LOGICAL_PROCESSOR_INFORMATION` (ядро + по записи на кеш; 122 и нужный
размер на коротком буфере). Сборок 2, как у Linux; `strings` 4.1 → 0.6 мкс.

Для CPUID понадобился стаб в exec-буфере, и при раскладке нашлось: стабы
MSR/MXCSR/TSC на 0x200 **перекрывали код восстановления SehDispatch**. Стабы
переехали на 0x400–0x480, CPUID — 0x4A0, буфер 1024 → 2048.

### Быстрые аллокаторы CoreCLR

`JIT_NewS`/`FastAllocateString` были выключены под `TARGET_SHARPOS` из-за
коллизии имён: ядерные `[RuntimeExport] RhpNewFast`/`RhNewString` против
`AllocFast.asm` CoreCLR. В форке его символы переименованы
(`SharpOS_ClrRhpNewFast`, `SharpOS_ClrRhNewString` — `TEXTEQU` в asm и
`#define` в `jitinterface.h`), защиты в `jitinterfacegen.cpp` сняты.

### Падение загрузки после расширения exec-буфера

Сборка во время пробы write barrier падала в
`GcObject.EnumerateObjectReferences`: консервативный обход принял слово стека,
указывавшее внутрь полезной нагрузки объекта, чьё первое слово
`0x0000020000020100` — каноничный, но не отображённый адрес. Раньше сходило с
рук случайно. `GcMark` теперь пропускает кандидата, чей MethodTable не лежит
в образе ядра (`MethodTableLow/High`, границы из `SizeOfImage` в
`BootSequence.BoundMethodTablesToImage`). Вторая находка на том же прогоне:
`TryActivateFrameChain` спрашивал цепочку кадров CoreCLR до того, как фасад TEB
поднят — теперь за `SehDispatch.FrameChainAvailable`.

### Исключения в приложениях: 25 мс → 5 мкс

`DispatchEx` печатал трассу на каждом шаге каждого броска, в тихом режиме тоже
форматируя строки. Трасса за `const bool Trace = false`.

Hosted-исключения (~120 мкс, ×3 к Linux) не тронуты. `seh.raises=0` в Bench:
.NET 10 бросает управляемые исключения мимо `RaiseException`; поиски в
таблицах функций и размотки в ядре — около 15 % цены броска, остальное внутри
CoreCLR. Опыт с `-cpu max` не изменил ни `strings`, ни `exceptions` —
подозреваемый 20 (набор инструкций) отпал.

### Вывод NativeAOT-приложений

Служба `WriteString` рисовала экран в конце каждой записи, мимо пакетирования:
283 перерисовки на прогон BenchAot против 21 у Bench, 1.42 мс на строку.

Первая правка — «в конце записи рисовать, только если пора» — сломала
лаунчер: Terminal.Gui шлёт кадр несколькими записями по 4 КиБ и перерисовывает
неизменный кадр целиком; рисование в конце каждой записи делало одинаковые
кадры невидимыми, а отложенное показывало первый кусок нового кадра одного.
Лаунчер мерцал и поднимался недорисованным до нажатия клавиши: после загрузки
он работает без вытеснения и опрашивает клавиатуру, не засыпая, так что
помпа хвост кадра не рисовала. Итоговое правило: откладывается только запись,
кончающаяся переводом строки; остальные рисуются сразу, как раньше.
`TryReadKey` сначала дорисовывает отложенное.

Перерисовки 283 → ~50, но строка всё ещё стоила 0.64 мс против 0.41 у hosted.
Разбор по счётчикам, по одной гипотезе за прогон:
- `output.first` (до задач) = `output` (после) — остатки 48 потоков ни при чём;
- `write.*`: ядро на символ AOT тратит 9.2 мкс против 5.9 — дело в ядре, не в
  приложении;
- `sink.*`: порты и диск одинаковы, терминал — 11.8 против 1.9 мкс;
- `terminal.drops=108` в каждом прогоне, у hosted 0, `kgc=0`.

108 = 4 × 27: четыре строки `[info] heap grow pages: 65`. `Feed` при прокрутке
выделяет строку буфера, куча растёт, рост пишет в лог — и строка возвращается
в `Putc` того же потока, который держит замок движка. Вложенный `Putc`
крутил все 4096 попыток и выбрасывал символ: ~1.2 мс на символ, ~0.3 мс на
строку — весь разрыв. `s_feeding` (как `s_rendering` у `Paint`) — вложенный
`Putc` выходит сразу. Глобального флага достаточно: `Putc` вызывается только
из `Platform.WriteChar` под запретом вытеснения. AOT 431 мкс на строку против
391 у hosted.

Остаток к Linux (×1.7–1.9) — COM3 и экран: в эталоне вывод идёт в ttyS1, без
фреймбуфера.

### Корни GC приложений: другие потоки и переходники служб

Лаунчер упал внутри собственного аллокатора
(`GcHeap.TryAllocateFromFreelist`, чтение по `0x2`, из перерисовки
Terminal.Gui): список свободных блоков испорчен. Свободные блоки появляются
только после сборки `AppGC`, а лаунчер собирает лишь при нехватке — перед
падением его куча выросла ~300 раз.

`AppGcService.WalkRoots` обходил только стек собиравшего потока, хотя сборщик
ядра давно обходит припаркованные потоки. Первая правка
(`KernelGC.MarkOtherThreadStacks(markRoot)` с колбэком приложения) проверку не
прошла: спящий поток приложения стоит внутри службы `Sleep`, службы вызываются
через переходники без `.pdata`/GcInfo, и `WalkFrames` останавливался на
первом нераспознанном кадре — до кадров приложения не доходил. Свой стек
обходился, потому что `GcWalkRoots` зовётся напрямую, без переходника.
`AppServiceBuilder.TryUnwindServiceThunk` переступает переходник по форме
(`sub rsp,28h / call rax / add rsp,28h / ret`, у SysV — с `mov rcx,rdi`
впереди): переходник корней не держит.

Проверка в AotTests «other thread's stack roots survive collect»: поток держит
массив с узором только в локальной и спит, главный собирает и занимает
освободившееся массивами того же размера с другим узором. FAIL с одним
обходом потоков, `ok` с переступанием переходников; 57/57 дважды за
загрузку. Что падение лаунчера было именно этим — сильная версия, но не
доказанная: оно воспроизводится только долгой работой лаунчера.

## Уроки

- Счётчик по стокам нашёл за один прогон то, что гипотезы не нашли за три:
  выброс символа не был виден ни в одном времени, пока его не посчитали.
- Правка ради бенча проверяется и на интерактивном приложении: «рисовать,
  когда пора» было верно для строк и неверно для кадров.
- Любой обход стека, пересекающий границу «приложение → ядро», должен
  переступать переходники служб (память `reference_service_thunks_no_unwind`).

## Дальше

- Исключения hosted-яруса (×3 к Linux) — многоуровневая компиляция
  (подозреваемый 18) одним прогоном через свойство `coreclr_initialize`.
- Задачи в AOT — поток на задачу, ×4.4 к Linux; пул потоков приложения.
- Куча ядра растёт, но не собирается (`kgc=0` во всех прогонах; лаунчер
  набирает ~70 ростов по 65 страниц).
- `[seh] throw` форматирует строки на каждом `RaiseException` (подозреваемый
  41; управляемых бросков не касается).
- Разбор переписи в `probe_report` (имена с `[`), файлы дискового лога по
  каналам.
