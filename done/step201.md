## 1. Expando: таблица записей и корзины

`Expando` (std) — как `Dictionary` BCL, но без упаковки скаляров:
`ExpandoEntry[] _entries` в порядке вставки (хеш, следующая в цепочке, род
значения, «мертва», скаляр 8 байт, имя, ссылка), `int[] _buckets`, `_count`,
`_live`. Скаляр и ссылка — раздельные поля: точный сборщик видит ссылку
обычным полем структуры. Хеш — часть формата: FNV-1a по UTF-16 без зерна и
перемешивание для корзины (`ExpandoHash`), одинаков во всех образах. Род
значения меняется свободно; удаление вынимает запись из цепочки и помечает
мёртвой, таблица перестраивается из живых.

В регионе `View` находит запись по корзине и цепочке, шагов не больше числа
записей, индексы проверяются: битый блок — исключение, не цикл. Раскладка
полей Expando — один раз на описание типа (`TypeShape.Cache`).

## 2. Правки принятого сообщения на месте

`ExpandoEdits.Set/Set<T>/Remove(this RawRegion, View, ExpandoName, …)` →
`EditCost`: `InPlace` (число, bool, char, null — в саму запись), `Tail`
(строка, новое имя, новая таблица — в хвост блока, до конца его блока
обменной кучи), `Grown` (живых больше половины — копия байтами в блок вдвое
больше: ссылки непереведённого блока — смещения), `Compacted` (достижимые
записи от корня — в новый блок по размеру). Сначала заявка на место всей
правки, потом запись: правка целиком или никак. `Set<T>` для скаляров без
упаковки (`value is int` для значимого T сворачивается; `typeof(T) ==
typeof(int)` нельзя — наш `GetTypeFromHandle` создаёт `RuntimeType` на
вызов). Стадия `RawPipeReader.Edit(Func<RawRegion, bool>)` владеет
сообщением и отдаёт дальше его текущий блок.

Проверки: AotTests pipe 20 — ядро пишет, приложение правит (смена рода,
строка, удаление, 30 добавлений с ростом, 60 строк со сжатием), ядро читает
типизированно; PIPEPERF 7 (QEMU, три прогона): поиск ≈120–140 нс в куче и
≈750–870 нс видом на 4–256 записях, от числа записей не зависит; правка
существующей записи и удаление — ноль выделений;
100 стадий по полю — блок 696 → 15 448 байт (хвост 96, рост 4); 1 000
добавлений и удалений вперемешку — блок не больше 4 040 байт (хвост 918,
рост 39, сжатие 43).

## 3. Потоковый `KQL.EXE`

Вход — свой `ITableSource`: кусок из того, что уже пришло (одно сообщение с
ожиданием, остальное без ожидания, до 256). `where` отвечает по мере
прихода, `sort`/`summarize` ждут конца, `take` прекращает чтение — писатель
получает разрыв и тихий 141. Столбцы — из типа первого сообщения, при пустом
входе — из типа, объявленного писателем. Сообщение не из полей (Expando,
массив, строка, число) — один столбец `Value`.

Пересылка исходных блоков решается по синтаксису до схемы: запрос только из
`where`/`take`/`sort` без `*` — в схеме скрытый `__row`, регионы держатся по
номеру строки, результат уходит блоками входа под его же типом (без копии и
перевода). Иначе `__row` нет вовсе: с ним `distinct *` и `where * has …`
дали бы другой ответ.

`extend` над Expando — на месте: столбцы-числа, bool и строки пишутся в
Expando принятого сообщения (`ExpandoEdits`), блок идёт дальше со всем, что
в нём было. Проверка — запись `DateTime`: через новое сообщение она стала бы
текстом JSON, здесь доходит `DateTime` (`where Value.N >= 6 | extend Twice
= Value.N * 2, Note = 'seen'`). Прочие результаты над Expando — новые
плоские Expando: записи `Value` и столбцы рядом (`extend Copy = Value.Kind`
— `dynamic`, не на месте; `When` уже строка).

Анализатор SOSR002 не пустил виды в массив и в возвращаемое значение:
ячейка читается там, где сделан вид.

## 4. BabyKusto: `take`, `summarize` над пустым, `dynamic` в операторах

- `take` при остатке, равном куску, просил ещё кусок — на трубе это ожидание
  ещё одного сообщения. Вырез: остановка и при точном совпадении.
- `summarize` без `by` над пустым входом не давал строки (`count` — ноль
  строк вместо одной с 0). В KQL такой `summarize` всегда даёт одну строку.
  Вырез: пустая корзина.
- Kusto.Language связывает `dynamic` с числом, строкой, bool и `dynamic` в
  сравнениях и арифметике, у BabyKusto реализаций не было.
  `DynamicComparison.cs`, `DynamicArithmetic.cs`, `DynamicValues.cs` (файлы
  SharpOS): значение вынимается из узла; сравнение — по роду (числа как
  числа, строки ординально, bool и объекты — только ==/!=); арифметика —
  тип по Kusto.Language (с числом — его тип, два `dynamic` — `dynamic`).
  Перегрузки стоят впереди типизированных — у тех параметр `string`
  принимает любой аргумент и забрал бы `dynamic` текстом. KQLBABY +3:
  таблица с `dynamic` из `JsonNode.Parse`, сравнения, `tolong(Bag.n)`,
  `Bag.n * 2`, `Bag.r / 2.0`, `Bag.n + Bag.r`.

## 5. Отказ процессора: «nested fault» от соседнего процесса

В батарее была строка `[nested fault] while reporting …`: PROCTEST 1
запускает два AOTTESTS разом, оба делают намеренный `#PF`, отчёт первого
уступил процессор, второй увидел глобальный `s_reporting`. Отказ, о котором
идёт отчёт, теперь хранится в потоке (`Thread.ReportingFault`). Записано в
donext, не исправлено: `s_hwRec`/`s_hwCtx` пути PAL SEH — тоже общие
статики после `Sti()`.
