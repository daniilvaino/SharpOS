# step 190 — надёжность после трубы: стресс сборщика, запись в регион, анализатор

Задание «надёжность после трубы»: режим стресса сборщика для ядра и
приложений, прогон в нём AotTests, PipeProbe и `--pipe-stress`, починка
найденного; тесты сортировки в регионе и пути `RhpByRefAssignRef`; правило
анализатора против чужих ссылок в регионе и протягивание ссылки региона через
`?.`, приведения, `as`, `?:`, `??`, свойства и индексаторы. Прогоны QEMU
`-UsbOnly -SkipCoreClr -Autorun` (`SHARPOS_GUI=1`) из сессии.

## Режим стресса

`SharpOS.Std.NoRuntime.GcStress` (std, общий для ядра и приложений):

- `Every = N` — сборка перед каждым N-м выделением (`GcHeap.Allocate`). Перед,
  не после: выделяемый блок держат только локальные аллокатора, их не видит
  никакой обход. Не из обработчика прерывания (`s_allocationAllowed`), не
  рекурсивно.
- `VerifyHeap` — обход кучи от начала до конца в `GcMark.Begin` (фаза 1:
  сломала программа) и в конце `GcSweep.Run` (фаза 2: сломал сборщик). Первая
  поломка — в `HeapBroken`: ядро паникует, приложение выходит с 134, оба
  называют адрес и фазу.
- `GcSweep.PoisonFreed` — умершие в этой сборке объекты заливаются `0xCC`.
- Проба op 13 — N ядра только для чтения: приложение растягивает ожидания
  работы ядра, когда ядро под стрессом с загрузки, а не по его просьбе.

Включение:

- ядро — `KernelGC.Stress(N)`; с загрузки — `Probes.GcStressEvery` (с фазы 4);
- приложение — `AOTTESTS.EXE --gc-stress N K [режим…]`: остаток строки идёт со
  стрессом N в приложении и K в ядре (проба op 11 включает ядро на время
  прогона и возвращает прежнее значение). Отчёты обхода (`[appgc]`,
  `[appwalk]`) на время стресса молчат.

## Что нашёл стресс и что исправлено

1. **`Region.Lay`/`Write` держали граф только адресами.** План хранил объекты
   как `ulong`, корень после первой строки `Lay` был мёртв для точного обхода.
   `writer.Copy(Build())` — сообщение держит только временный аргумент; сборка
   внутри `Lay` (растут `List`, `Dictionary`, `Stack`) освобождала граф, `Write`
   копировал залитую память → `NullReferenceException` в `Lay`. Не артефакт
   стресса: любая сборка в этот момент. Исправлено: `Plan.Root` держит корень,
   пока жив план.
2. **Сборка в пути аппаратного сбоя не видела кадров под сбоем.** Обход от
   обработчика останавливается на заглушке прерывания. Фабрика исключения
   приложения держала сборщик (`AppGC.Held`), а ядро, создавая своё
   исключение, могло собрать вслепую; `finally` и `catch` после сбоя — тоже.
   Исправлено: `ExInfo.FaultFrame` (0x258, свободный хвост структуры), запись
   связывается в цепочку **до** создания объекта исключения;
   `KernelGcPreciseWalk.MarkExceptionChain` для текущего и каждого
   припаркованного потока метит объект каждого исключения в диспетчеризации
   (`ExInfo.Exception` — сырой адрес между throw и catch, как в стоке) и
   сканирует кадр сбоя консервативно, как вытесненный поток. `AppGC.Held` снят.
3. **Цепочка `ExInfo` теряла записи при исключении внутри catch.** Шеллкод
   catch снимает ровно одну запись; при `throw;`/повторном броске из
   фанклета старая оставалась и указывала в мёртвый стек. Нашлось, как только
   сборщик пошёл по цепочке (#GP по неканоническому адресу в
   `MarkExceptionChain` после теста «rethrow appends frames»). Исправлено в
   `DispatchEx`: перед catch из цепочки выпадают записи между диспетчером и
   кадром catch (сток снимает все ниже возобновляемого SP). Обход цепочки на
   неправдоподобной записи говорит и останавливается.
4. **Декодер `GcInfo` вис на больших кадрах.** Буфер слотов — 32, диапазонов —
   16; больше — `Halt()` (бесконечный цикл), счётчик переполнения в обходе до
   этого не доходил. Первый метод AotTests с >32 GC-слотами, попавший в сборку,
   остановил машину. Исправлено: размер — из `GcInfo` (до 4096, сверх — строка
   в лог и счётчик).
5. **Отказ барьера byref нельзя было поймать.** Шеллкод `RegionBarrier` без
   unwind-данных; управляемый диспетчер на нём останавливался, исключение
   уходило необработанным мимо всех catch. В step189 путь отказа не исполнялся
   ни разу (тест 7 бил по полям и элементам-ссылкам). Исправлено в
   `HwFaultBridge`: при отказе из шеллкода диспетчеризация начинается с адреса
   возврата — как будто упал сам вызов.
6. **Заливка `0xCC` перезаливала всю свободную память на каждой сборке,
   побайтно.** Ядерная сборка под стрессом стоила мегабайт записей. Теперь
   только умершее в этой сборке, `Memset`.

Тесты, неверные под стрессом по построению (не ошибки): «collect reclaimed
something», «many small blocks» — засчитаны с пометкой в логе; ожидания по
времени (region from kernel, вердикты труб, нагрузка) под стрессом длиннее;
замеры труб пропускаются.

## Запись в регион

- **Тест 6** уже сортировал массив объектов в принятом регионе и отдавал его
  `Move`, ядро сверяло порядок (`PipeTests.PipeEcho`, `PipeProbe.EchoBack`) —
  в отчёте step189 это строка 6. Было 5 элементов: `Array.Sort` до 16 —
  вставками. Теперь 100 ключей вперемешку: разбиения и перестановки.
- **Тест byref** (`ByRefProbe`, std — один код для ядра и приложения):
  структура `Tagged` (три ссылки, два числа) копируется из элемента в элемент.
  Двухпольную структуру ILC копирует через регистры и `RhpCheckedAssignRef`;
  с тремя ссылками — память-в-память, по `RhpByRefAssignRef` на ссылку
  (проверено дизассемблером `CopyElement`). Внутри блока — проходит; со
  ссылками в кучу — `RegionReferenceException`, ссылка элемента прежняя.
  Приложение и ядро (op 12) — ok.

## Анализатор

- **SOSR006** (ошибка): в поле, элемент или свойство ссылки региона пишется
  значение, которое не ссылка этого же региона и не null — объект кучи,
  литерал, объект другого региона, структура, несущая такую ссылку
  (`new Slot { Name = "x" }`, элемент массива кучи), `??=`. Закрывает литерал
  при сборке там, где цель известна как ссылка региона.
- Ссылка региона протягивается через `?.`, приведения, `as`, `?:` и `??`
  (любая сторона — для утечек; все стороны — для SOSR006), через свойства и
  индексаторы на ссылке региона, через структуры, несущие ссылки.
- Хостовые тесты: 45/45 (было 26) — правило на пример и корректный код без
  срабатываний. Сборка ядра и приложений с SOSR006 — без нарушений; тест 7
  нарушает намеренно (`#pragma`).

**Известные ограничения:** ветки не коррелируются (`if (b) Dispose … if (!b)
use` — срабатывает); локальная, получившая ссылку региона на одном пути,
считается ссылкой региона везде; результаты методов (не свойств) не
протягиваются; цель — параметр типа сообщения — неизвестна, литерал в неё
ловит только `Move`.

## Ограничение строки «GC.Collect при нескольких потоках»

Строка стояла ✅, но держится на одном процессоре: «остановка мира» — это
подавление вытеснения на время сборки, остальные потоки просто не исполняются.
На втором ядре они бегут, нужны точки безопасности или IPI. Вытесненный поток
стоит на произвольной инструкции, его стек сканируется консервативно (лишнее
удерживается; от мусора защищает проверка таблицы типа); поток, остановленный
не на своём стеке и не на стеке приложения, — точно, без прерванного кадра.
Сборка держит вытеснение на всё время — пауза для всех потоков. Обходятся
потоки всех программ: приложение платит за стеки ядра и чужих потоков. До
этого шага не обходились исключения в диспетчеризации на других потоках —
закрыто (п. 2). Строка — 🟡.
