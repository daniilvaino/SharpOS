# step 149 — bring-up на реальном железе: FS-запись, boot-log, USB-разведка, MMIO/HPET

Шаг целиком про **разрыв между QEMU и физической машиной**. Всё, что здесь чинится,
в эмуляторе работало и потому было невидимо. Толчок — попытка запустить SharpOS с
флешки на трёх машинах (десктоп, второй десктоп, ноутбук) и получить оттуда лог.

---

## 1. Запись в FAT32 (первая в проекте)

До сих пор наша FS была read-only. Выбрано направление «запись в предварительно
подготовленный файл фиксированного размера», без аллокации кластеров — это снимает
самую опасную часть (правку FAT-цепочек) и при этом достаточно для логов.

**`Fat32.WriteFileInPlace(path, src, len)`** — перезапись содержимого от начала файла.
Частичный сектор пишется read-modify-write, размер файла не меняется.

**`Fat32.TryOpenLinear(path, out startLba, out sectors)`** — резолв файла в плоский
диапазон LBA. Непрерывность **проверяется**, а не предполагается: фрагментированный
файл заставил бы плоскую арифметику писать в чужие кластеры, поэтому такой файл
отвергается — лучше потерять логирование, чем чужие данные.

Проверено внешне: `mtype` из образа читает то, что записало ядро (`FatWriteProbe`).

## 2. Boot-log на диск (`OS/src/Hal/BootLog.cs`)

`Platform.WriteChar` зеркалит каждый символ в `sharpos/bootlog.txt` (16 МиБ, стейджится
`run_build.ps1`). Сброс — построчно, сектор переписывается по мере заполнения.
Привязка происходит **после** монтирования пост-EBS: до этого момента диск ещё не наш.

Мотив прямой: на тестовых машинах нет COM-порта, экран не скроллится, а паника
уносит причину вместе с собой.

**Что выяснилось:** на железе лог не появился вообще. Причина не в записи —
`ahci init=N`. На этих машинах контроллера в режиме AHCI нет (NVMe либо SATA в RAID),
и весь дисковый стек не поднимается. Значит носитель для лога — та же USB-флешка,
с которой мы грузимся, а не SATA. Это и стало обоснованием USB как следующего фронта.

## 3. USB-разведка (`OS/src/Hal/Usb/UsbHost.cs`, `UsbProbe`)

Перечисление контроллеров по PCI (класс 0x0C/0x03, ProgIF 0x00/0x10/0x20/0x30),
декодирование MMIO BAR с учётом 64-битных. Драйвера ещё нет — сначала надо знать,
что писать.

Ответ по трём машинам одинаковый: **xHCI и только он**. QEMU `1B36:000D`,
VirtualBox `8086:1E31`, ноутбук — три AMD `1022:1503/1504/1505` на шинах 3 и 4.
UHCI/OHCI/EHCI не нужны.

Побочно: `Pci.MaxBus` 2→8, `MaxDevs` 32→96. Старые лимиты **молча** обрезали скан —
устройства с шин 3–4 просто не существовало, и «контроллеров нет» было ложью.
Добавлен флаг `Truncated`, и `UsbProbe` печатает его: «не найдено» ничего не значит,
пока скан обрезан.

## 4. Отображение MMIO (`VirtualMemory.MemoryKind`)

`MapFixed` пропускал уже отображённые страницы целиком (`if (TryQueryKernel) continue`).
На железе HPET/ECAM/framebuffer/ABAR отображены унаследованными от прошивки таблицами,
поэтому наши атрибуты не применялись **ни к одной из них** — включая бит записи.

Теперь тип памяти задаётся явно: `Normal` / `Device` (PCD|PWT) / `Framebuffer` (PWT —
полный запрет кеша сделал бы каждый глиф отдельной транзакцией на шине).
Для не-`Normal` флаги переустанавливаются принудительно. Унаследованная 2-МиБ страница
расщепляется на 4 КиБ через существующий `Unmap` — `TrySetKernelFlagsEx` кеш-биты на
большой странице трогать не может, там сиблинги с кодом ядра.

**`wbinvd`** — новый стаб в `Cr3Accessor` (третий рядом с CR3 read/write, той же схемой
Iced + байты + сверка). Без него смена атрибутов бесполезна: пометить страницу
некешируемой не значит выбросить уже закешированное. Заодно это готовый
serializing-инструмент для §9 (self-modifying code).

## 5. HPET: прошивка отдаёт остановленный счётчик

Главная находка шага. На железе `hpet=STUCK`.

Диагностика по шагам (каждый шаг — прогон на железе, три моих гипотезы подряд были
опровергнуты приборами, а не рассуждениями):

| Замер | Значение | Что исключает |
|---|---|---|
| `caps` прошёл sanity | период 1.1176 мкс | чтения доходят до чипа |
| `pte=0x…7B` | биты 3,4 стоят | страница реально uncached, кеш ни при чём |
| `spins=0x4C4B40` | все 5M оборотов | компилятор цикл не свернул |
| `t0=t1=ctr` | одно значение | счётчик стоит физически |
| `cfg0=0x1` | до нашей записи | `config \| 1` — no-op |
| restart → `r0=0 r1=0xE` | пошёл | корень подтверждён |

**Корень:** UEFI при teardown останавливает счётчик, **не** сбрасывая `ENABLE_CNF`.
Поэтому по регистру конфигурации HPET выглядит включённым, а установка бита ничего
не делает. Оживляет только halt → counter=0 → enable (счётчик по спеке пишется
только остановленным).

**`Hpet.EnsureRunning()`** — проверяет движение, один раз перезапускает (перезапуск
обнуляет счётчик, поэтому строго один). Зовётся из `Init` и **сразу после
`ExitBootServices`**, до всех потребителей: `Init` отрабатывает в Phase 3 при живой
прошивке, когда счётчик ещё идёт, и там чинить нечего.

Видимый эффект: исчезли 2–3 секунды на заставке — AHCI больше не крутил таймауты
с застывшим счётчиком.

## 6. Паника вместо тихого выключения

Два пути молча заканчивались ничем, и на железе это неотличимо от нормального
завершения — машина гасится, не выполнив ничего:

- ФС не поднялась → был `Warn` + `Shutdown`, стал `Panic.Fail`.
- Батарея не запустила ни одного приложения (`passed: 0 / failed: 0` читается как
  зелёный прогон, а означает обратное) → `Panic.Fail`.

Там же: провал установки interface-dispatch моста теперь паникует сразу, а не
двумя фазами позже первым же диспатчем, когда причина уже уехала с экрана.

**Следствие:** конфигурация без `HELLO.EXE` на ESP теперь ошибка, а не допустимый вариант.

## 7. Мелочи

- `[ebsx]` — вердикт больше не липнет к последнему полю (`hpet=adv FAIL` читалось как
  провал HPET, хотя падали `uart` и `fb`). Теперь `=> FAIL(uart fb )`.
- `run_build.ps1` — `[Array]::Fill` заменён на чанковую запись: метода нет в
  .NET Framework, и скрипт падал под Windows PowerShell 5.1, работая под pwsh 7.

## Что откладываем

- `fb=FAIL` на железе — расхождение эталонной CRC кадра. Экран очевидно живой,
  значит расходится эталон, а не вывод. Не трогалось, чтобы не мешать с HPET.
- `uart=N` входит в общий вердикт наравне с остальным, поэтому машина без COM-порта
  обречена показывать `FAIL`. Надо развести «нет оборудования» и «сломано».
- AHCI на тестовых машинах не поднимается вообще (NVMe/RAID) — чинить не AHCI.
