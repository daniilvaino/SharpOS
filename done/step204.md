# step 204: KQL `extend` правит поле типизированного сообщения на месте

## Контекст

С step201 KQL писал результат `extend` в само сообщение только над Expando.
Над сообщением типа с полями — у PIPEGEN это `LogEntry`, у SYNTH «призрачный»
тип — `extend` всегда выпускал новые Expando-сообщения. Так было даже для
`extend Weight = Weight * 2`, где значение помещается в то же поле.

Нижний слой это уже умел: `View` пишет число, bool или null прямо в поле
принятого блока и проверяет род и диапазон. Не хватало только KQL.

## Что сделано

**`apps_native/KqlApp/Program.cs`:**
- **Сбор имён.** `Plan` собирает имена, которые присваивает `extend`
  (`Plan.Extended`).
- **Тип с полями.** `Columns.Typed` — каждый столбец есть поле сообщения.
  Для такого входа при `extend` включается скрытый номер строки, как над
  Expando.
- **`Edits`.** Пересылка блоков выбирается, если результат имеет ровно
  столбцы входа (`extend` только переприсвоил) и каждое присвоенное имя —
  поле-значение: целое любого размера, float/double или bool. Строка, char
  (в KQL это строка), структура или ссылка — новые сообщения, как раньше.
- **`Forward` → `Write`.** Ячейка результата пишется через `root[name] = …`.
  `View` сам проверяет род и диапазон: `long` 10 000 000 000 в поле `int` —
  `OverflowException`, KQL выходит с кодом 1 и сообщением
  `'Level' holds a System.Int32: 10000000000 does not fit`. Null в поле-значение —
  тоже ошибка.
- **Сообщение об ошибке.** Имя типа исключения печатается, только если
  приложение его знает. Иначе вместо имени стоял бы сырой `EETypeRva:0x…`.

`extend` с именем существующего столбца BabyKusto выполняет как замену
столбца (`IRTranslator.HandleExtendOperatorInternal`): набор столбцов
результата совпадает со входом.

**PROCTEST 18 — три проверки** (66 → 69, под стрессом 61 → 64):
- `where Level == 4 | take 3 | extend Level = Level * 10` над PIPEGEN —
  `40 text 4;40 text 9;40 text 14;`, тип по-прежнему `PipeApps.LogEntry`;
- `take 2 | extend Text = strcat(Text, '!')` — строковое поле: новые
  сообщения, `text 0!;text 1!;`;
- `take 1 | extend Level = Level + 10000000000` — не помещается в `int`:
  KQL — код 1, на выход ничего.

## Ошибка по ходу

Первая версия собирала имена `extend` веткой `else if`, стоявшей перед общей
веткой операторов. `extend` перестал снимать признак «только where/take/sort»,
и KQL пересылал блоки без изменений: все три новые проверки показали
исходные значения. Сбор имён теперь отдельно, правила операторов прежние.

## Как проверить из оболочки

```
SYNTH 3 | PIPESPY a | KQL 'extend Weight = Weight * 2' | PIPESPY b
```

У `a` и `b` один адрес блока, у `b` `Weight` вдвое больше, тип тот же.

## Проверка

Полная батарея QEMU 2 ГиБ, сборка `bf38ec2+dirty.1012-2220`:
`[sh] done ran=28 failed=0` — PROCTEST 69 и 64 под стрессом, паник нет.
