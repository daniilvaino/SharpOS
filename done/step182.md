# step 182 — шина USB попала в приложение, а часы приложений оказались стоячими

Шаг начинался как «сделать приложение для работы с USB» и закончился тем, что в
приложениях SharpOS впервые пошли часы. По дороге закрылись три прибора, которые
врали или молчали, и одна правка внутри шага сломала загрузку — разбор ниже, потому
что форма поломки полезнее самой поломки.

## Что теперь работает

**Ключ регистрируется.** Полная операция U2F с подтверждением присутствия, из
приложения на SharpOS:

```
[usbtest] Register
[usbtest] Touch the key. Register again gives up.
[usbtest]   answer 0x9000 (done), 31 keepalives
[usbtest] registered: 694 bytes of key handle and attestation
[usbtest] 0000  05 04 e5 0a 32 07 f9 41 b9 0a 86 cf 07 81 5d 3c  ....2..A......]<
```

`05` — обязательный первый байт ответа U2F, `04` — несжатая точка, дальше X
открытого ключа; 694 байта это дескриптор ключа, сертификат аттестации и подпись.
31 keepalive — ключ держал запрос открытым, пока ждал палец. То есть работает вся
цепочка: кадрирование CTAPHID, `CTAPHID_MSG` с APDU, keepalive-кадры, кнопка
присутствия, генерация пары P-256 и аттестация на ключе.

## 1. Две службы и приложение

`AppServiceUsb.cs` — две службы в хвост таблицы, версия ABI не поднята (наличие
службы = адрес не ноль):

- `UsbEnumerate` — вся шина одним вызовом: плоский массив узлов с индексами
  родителей. Плоский, потому что дерево через границу службы означало бы указатели
  в чужое адресное пространство; индексы говорят то же самое без них.
- `UsbCtap` — один обмен CTAPHID. Канал 0 значит INIT, дальше любая команда с любой
  нагрузкой. Не заточена под `getInfo`: из приложения достижим весь CTAP2.

`apps_native/UsbTest` — вкладки, а не меню из клавиш. Вкладка шины (дерево
`TreeView` плюс подробности выбранного узла) и вкладка ключа (кнопки INIT /
getInfo / PING / WINK / Register и журнал разговора). Вкладки не знают друг о
друге: вкладка шины сообщает найденные FIDO-интерфейсы через оболочку. Вкладка,
которая лезет в другую, — это вкладка, которую нельзя убрать, а смысл затеи в том,
что их станет больше.

## 2. Три дефекта вида «прибор соврал уверенным тоном»

Все три нашлись **глазами по выводу дерева**, а не тестом.

1. **`0000:0000 speed 0 per-interface` у каждого устройства.** Служба не заполняла
   ни vid:pid, ни класс, ни скорость, хотя описание структуры их перечисляет. Не
   пустота, а неправильный ответ: класс 0 значит «смотри интерфейсы», то есть вывод
   выглядел осмысленным. Теперь дочитывается дескриптор устройства, а если он не
   пришёл — ставится бит, и приложение печатает `????:????  [descriptor unread]`.
2. **`interface 2 mass-storage [free]` на машине, загруженной с этого диска.**
   Признак «захвачен» ставился только внутри ветки поиска HID-функции. Завёл
   `IsInterfaceClaimed` — одно место, которое смотрит во все драйверы.
3. **Двенадцать точек под одним интерфейсом у Bluetooth**, адрес `0x03` шесть раз.
   Записи интерфейса с ненулевым `bAlternateSetting` пропускались, но родитель не
   сбрасывался, и точки альтернативных настроек приписывались предыдущему
   интерфейсу.

Плюс имена: три поля по 32 байта в узле, ASCII с нулём, складываются в ядре — провод
несёт UTF-16, а консоль выбрасывает то, чему в шрифте нет глифа.

## 3. Часы приложений стояли, и это глушило все таймауты Terminal.Gui

Симптом: нажатие Register не делало **ничего**. Ни строки в журнале, ни реакции
ключа, диод в Idle.

Нашлось это только потому, что журнал разговора начал дублироваться в лог
(`AppHost.WriteDiagnostic`, канал измерений — COM1 и диск, экрана не касается).
До этого панель жила только на фреймбуфере, и «реакции в логе нет» принималось за
улику, хотя улики там быть не могло. В логе стало видно отсутствие строк там, где
они обязаны были быть: между «Touch the key» и «gave up» — пусто, то есть тик
таймаута не выполнился ни разу.

Причина в `MainLoop`:

```csharp
var k = (DateTime.UtcNow + time).Ticks;   // срок
if (k < DateTime.UtcNow.Ticks)            // пора?
```

`System.DateTime.Clock.Install` не вызывался **нигде в дереве**, поэтому `UtcNow`
всегда отдавал `MinValue`, срок всегда оставался в будущем, и **ни один таймаут
Terminal.Gui никогда не срабатывал** — ни в этом приложении, ни в лаунчере. Молча:
ни исключения, ни сообщения, обработчик просто не вызывается.

`AppRuntime.Initialize` теперь ставит источник тиков поверх того же HPET, который
уже питает `Stopwatch`. Часы **монотонные, не верные**: эпоха — `MinValue` плюс
аптайм, потому что настоящей даты приложению никто не отдаёт. Это выбрано осознанно
— «первый год плюс двадцать минут» очевидно не дата, а правдоподобно неверной
поверили бы.

Комментарий в `DateTime.cs` при этом уверенно описывал, как «ядро ставит читалку
CMOS, а приложение спрашивает ядро через таблицу служб». Намерение, которое никто
не подключил, и оно пережило в дереве несколько шагов.

## 4. Опрос CDC отменял свою же передачу

`[idlewait]` в каждом окне простоя: `usb` ≈ 1.07e9 тиков, `screen` и `progwrite`
ровно ноль. То есть машина не доходила до рисования, а полноэкранная программа
выглядела перерисовывающейся по частям, потому что получала процессор только между
отменами.

`TryCdcRead` на каждом пустом опросе делал Stop Endpoint + Set TR Dequeue — два
круга по командному кольцу со своими ожиданиями, 25 раз в секунду при молчащем
порте. Клавиатура так никогда не делала: ставит запрос один раз, собирает
неблокирующе, перезаряжает только завершившееся.

Переписано по её образцу: `ReadOutstanding`/`ReadPending` у конечной точки, своя
страница DMA (обязательное следствие — буфер пульта был `stackalloc`, а передача,
живущая дольше вызова, это контроллер с указателем на исчезнувший кадр), стаж
завершения несёт длину. Опрос стал 5 мс вместо 40, таймаут чтения 0 вместо 2 мс:
интервал теперь выбор задержки, а не бюджет.

Результат: `[idlewait] usb` 1.07e9 → 7.6e6 за окно (в 140 раз), `usb.abort.calls=0`.

## 5. Экран: прибор врал вчетверо, а потолок оказался чужим

- **Фаза строк мерила настенное время внутри вытесняемого потока.** 16.6 мс на
  кадр — это перепись с четырёхпоточными стресс-тестами и 650 тысячами переключений
  контекста, записанными на счёт экрана. Добавлен `screen.rows.clean` — только
  кадры без единого переключения: init 463 → **97 мкс**, census 12.3 → **3.44 мс**.
  Оговорка в счётчике: фильтр смещён в короткие кадры, так что это нижняя граница.
- **Форма записи ни при чём.** Новое измерение `cell8x16` (те же байты формой
  глифа) даёт 519 против 527 у подряд идущих — пол-кэш-линии в шестнадцати строках
  развёртки стоят столько же. Гипотеза про чтение-под-запись мертва.
- **Потолок поставлен прошивкой.** `[fbperf] range: mtrr=WT` — апертура помечена
  write-through, действующий тип строже PTE. 520 MiB/s это цена нашего шаблона, а
  не панели; 16 байт за раз дают вдвое. PAT это не ослабляет (WC на WT-диапазоне
  даёт UC — пробовали, перерисовка уезжала к трём секундам).
- **Кэш палитры.** `Color` — класс, палитра за конструктором класса, две проверки
  на ячейку. Массивы выделяются в методе, а не инициализатором поля: инициализатор
  дал бы классу конструктор, и проверка появилась бы перед каждым чтением статика в
  том же цикле.
- **Оракул кадра стал переносимым**: узоры фиксированной ширины, строка с
  разрешением вынесена из проверяемой области, сравнение с самим собой до
  ExitBootServices. Был красным на ноутбуке всегда.

## 6. Тема и вывод поверх приложения

Дефолты Terminal.Gui: `Base.Normal` — белое на **синем**, `TopLevel.Focus` — белое
на **голубом**. `Toplevel.ColorScheme = Colors.TopLevel`, и всё под ним наследует
эту схему; лаунчер перекрывал `Base`, `Menu`, `Dialog` и **не** `TopLevel`, поэтому
панель в фокусе выходила синей. Палитра переехала в
`vendor/Terminal.Gui/SharpOS/SharpOSTheme.cs` — одно место на все полноэкранные
программы и **все пять** схем, потому что пропуск одной это и есть та поломка.

Отдельно: сообщения ядра печатались поверх полноэкранной программы и исчезали с
её следующей перерисовкой (`[heapcensus]`, `heap grow pages`). Признак взят тот,
который уже означает ровно нужное — **альтернативный буфер**: программа,
переключившаяся в него, владеет экраном. Пока это так, из `KernelLog` снимается
сток `Screen`. `Panic` выведен в отдельную ветку и остаётся на экране всегда —
раньше он попадал в `default` вместе с обычным логом.

## 7. Прошивка ключа под плату

Ключ — самодельный, на Raspberry Pi Pico 2. Прошивка RS-Key по умолчанию собрана
под Waveshare RP2350-One: адресуемый WS2812 на GPIO16. У Pico 2 светодиод обычный,
на GPIO25, и на GPIO16 не висит ничего — прошивка честно гоняла протокол WS2812 в
пустоту. При этом `CAPABILITY_WINK` она выставляет, потому что `can_wink` спрашивает,
*настроен* ли индикатор, а не *подключён* ли.

Добавлен профиль платы `firmware/boards/pico2.toml` (в дереве RS-Key, не в нашем):
`kind = "gpio"`, `pin = 25`, остальное дефолтное — флеш 4 МБ как у эталона,
присутствие на BOOTSEL, кварц 12 МГц. Собрано и залито, диод ожил.

Мелочь, которая стоила попытки: перетаскивание `.uf2` на диск BOOTSEL **не
сработало** — у платы уже есть таблица разделов, и образ надо класть в раздел
(`picotool load -v -x`). Файл при этом просто остаётся лежать на томе, без единого
сообщения.

## Ошибка внутри шага: чтение GC-статики из пути вывода

Правка про альтернативный буфер остановила загрузку. Последнее на экране — строки
`[uefi]`, дальше ничего:

```csharp
var terminal = s_terminal;                       // читается ВСЕГДА
if (!s_ready || terminal == null) return false;
```

`s_terminal` — ссылочный статик, то есть GC-статика, а они материализуются поздно.
`OutputRouting.SinksFor` зовётся на **каждый** записанный символ, включая самый
ранний вывод ядра. Строки `[uefi]` идут в ConOut напрямую, мимо маршрутизации, —
поэтому они и оказались последним, что видно: обрыв пришёлся ровно на границу двух
путей вывода.

Порядок проверок исправлен (`s_ready` — обычный `bool`, лежит в образе). Правило
записано в limits §17: условие в пути вывода исполняется с первой строки ядра, и всё,
до чего оно дотягивается, обязано быть примитивным статиком.

Снятая по дороге версия, выглядевшая правдоподобнее: массив счётчиков объявлен как
`fixed long V[Slots]`, где `Slots = (int)PerfCounter.Count` — он растёт вместе с
перечислением, четыре новых счётчика его не переполнили.

## Что откладываем

- **Горячее подключение** — шина перечисляется один раз, любое переподключение
  требует перезагрузки. Наблюдателя за состоянием портов нет.
- **Настоящая дата приложениям** — службы времени в таблице нет; в ядре
  `DateTime.UtcNow` тоже константа.
- **CBOR** — 548 байт `getInfo` печатаются сырыми, декодера нет. Теперь есть на чём
  его проверять.
- **CCID** — интерфейс 2 виден, точки известны, класс не захвачен.
- **Запись шире 8 байт** в блиттер (×1.9 по измерению) и **MTRR на WC** — обе цены
  известны, ни одна не взята: кадр 97 мкс на выводе не узкое место.
- **Часы как узкое место**: `Hpet.ReadCounter` первый в профиле (18 % переписи,
  52 % init), миллион обращений за 12 секунд по 1.2 мкс. TSC-часы — отдельный фронт,
  записан в `docs/fronts-2026-09.md`.
