# step 194 — два приложения одновременно, трубы между ними, концы при старте

Задание 3 мастер-агента. Прогоны — QEMU без графики; итог — ещё и ноутбук HP
(стенд с телефоном), разделы в конце.

## Исходное состояние (карта «одного приложения»)

- Образ: `/BASE 0x100000000 /FIXED`, `PeLoader` кладёт его ровно по базе
  одним непрерывным куском физических страниц; пул кучи приложения (64 МиБ)
  — в `.bss` образа. Релокации (`PeRelocations.TryApply`) есть, но на пути
  запуска не применяются.
- Главный поток приложения — сам запускающий поток ядра: `JumpStub.Run`
  переключает RSP на стек приложения. Вложенный запуск идёт на потоке
  родителя, родительский образ на время снимается с отображения
  (`ProcessManager.TrySuspendCurrentForNested`) и возвращается по снимку.
- «Текущее приложение» — глобальное: `ProcessManager.s_currentContext`,
  `JumpStub.s_active` (цепочка `JumpContext` по вложенности),
  `AppServiceBuilder.s_exitRequested/s_exitCode/s_publishedAbiVersion`,
  `s_runExternalDepth`, `StartupData.s_pending`, `s_alternateScreenOwner`;
  `IsAppCode` смотрит только самый внутренний образ; фабрика аппаратных
  исключений — в самом внутреннем `JumpContext`.
- Владение — по `Thread.AppGeneration` (трубы, обменная куча, потоки
  приложения). Потоки приложения снимаются в `Scheduler.LeaveApp`, их стеки
  не освобождаются.
- Необработанное исключение в рабочем потоке приложения — `Panic`.
- CR3 один на всех.

## Ход работы

### 0. Хвосты шага 193

- `dynamic` над `Expando` — только записи: имени нет — `RuntimeBinderException`
  (в том числе `Count`, `ContainsKey`); свои члены — через приведение к
  `Expando`. Вызов члена-записи — «Cannot invoke a non-delegate type»
  (делегат в `Expando` не положить: он не ходит по трубе).
- Предел обходчика снят: таблица слотов кадра больше 512 записей — в
  растущем буфере из `KernelHeap` (обход один, мир остановлен), диапазоны
  прерываемости — потоково, без буфера. Нет памяти под буфер — `Panic` с
  причиной. Проверка батареи: кадр с 700 живыми ссылками через сборку.
- `--dynamic` 22/22, под `--gc-stress 16 4` — 22/22.

### 1–3. Процессы: перемещаемые образы, таблица, завершение

- Образы перемещаемые: `/FIXED` снят, `/BASE 0x100000000` остался
  предпочтительной базой. `PeLoader.TryLoad(image, loadBase)` кладёт образ в
  диапазон слота `0x2000_0000_0000 + slot * 0x4000_0000` (до прогона на ноутбуке — `0x1_0000_0000`, см. ниже) (16 слотов по 1 ГиБ) и
  применяет DIR64-релокации на месте; нет таблицы — отказ с текстом
  `[pe] image cannot be relocated to 0x…: no base relocations (linked /FIXED?)`
  (так и вышло со старым BENCHAOT.EXE до пересборки). Стек главного потока —
  по слоту. Снятия родителя с отображения больше нет (`ProcessManager`,
  `ProcessContext`, `MappingContext` удалены).
- `AppProcess` + `AppProcesses`: таблица на 16 запущенных, запись живёт, пока
  её держит запустивший. Всё «текущее» — в записи процесса: фабрика
  исключений, код выхода, версия ABI, владелец альтернативного экрана.
  `IsAppCode` / фабрика — по адресу (`FindByAddress`) или по процессу потока.
- Главный поток — отдельный поток ядра (`ProcessMainEntry`: `JumpStub.Run`,
  затем `EndProcess`). `JumpContext` — цепочка на потоке (`Thread.Jump`), не
  глобальная. Загрузочный запуск (`LauncherBoot`) и служба `RunApp` — оба
  `StartProcess` + `WaitForExit` (ожидание по адресу, без опроса).
- Завершение: `RequestEnd` помечает все потоки процесса. Поток в коде
  приложения разворачивается на тике (`Preemption.TurnToLeave`); поток в
  службе дорабатывает её и уходит в переходнике (флаг `s_currentKilled`
  проверяется после `call`); ожидание по адресу/сон обрываются и больше не
  засыпают (`AddressWait`, `Scheduler.Sleep`), циклы ожидания труб в ядре
  выходят с `Broken`. Блокировки ядра не обрываются — их отпускает
  владелец. Стеки ушедших потоков приложения освобождаются (`ReapDead`).
- Необработанное исключение в любом потоке приложения: строка
  `[app] ИМЯ: unhandled exception[ on a worker thread]: process ended, exit
  code 134`, процесс завершается, машина живёт.
- Сборка приложения обходит только потоки своего процесса; сборка ядра
  проходит под цепочкой запусков каждого потока.

Ошибка по пути: первый прогон завис после `--pipe-stress 2` — главный поток
ждал ухода рабочего, а тот в `KernelPipes.Receive` после оборванного
ожидания снова засыпал в цикле. Отсюда правило: ожидание у убиваемого потока
не засыпает, циклы ядра вокруг ожиданий проверяют `KillRequested`.

Прогон батареи (вложенные запуски из оболочки — теперь процессы в слотах
1+): 13/14, все запуски AOTTESTS с ожидаемыми кодами, в том числе
`--gc-stress 16 4`, `--gc-stress 1 1 --pipe-stress 1`, `--dynamic`; после
конца процесса снимается 1–3 оставшихся потока. BENCHAOT — старый образ с
`/FIXED`, отказ перемещения (см. выше); после пересборки всех приложений —
перепрогон.

### 4–6. Трубы между приложениями, концы при старте, оболочка

- Ядро: `KernelPipes.Transfer` (конец меняет держателя, номер тот же),
  `DeclareEnd` (тип на конце пары: первый с типом объявляет, второй
  сверяется), `IsEnd`. Служба `PipeOpenEnd`. `StartupData` — записи
  дописываются; вид 2: `uint Role, int Handle` (0 вход, 1 выход).
  `StartFromPath` проверяет концы вызывающего до загрузки и передаёт их
  новому процессу перед созданием главного потока; неудача — концы остаются.
- Служба процессов (`ProcessService`): старт с концами, ожидание (по адресу),
  завершён ли, `Kill` (137), отпустить запись, свой id. Ждать, убивать и
  отпускать может только запустивший.
- `Exit` теперь завершает процесс сразу (как `exit()`): раньше только
  запоминал код, и `Fatal` в приложении после него крутился вечно.
- Ненулевой код выхода — концы процесса закрываются «обрывом» (§3); признак
  отказа передаётся в `ProcessResources.OnAppEnded` явно — кольцо записей на
  16 мест может уже не помнить долгоживущий процесс.
- std: `Pipe.Create()` → `PipePair { WriteEnd, ReadEnd }`; конец открывается
  один раз (`Read()`, `Read<T>()`, `Write<T>()`) или уходит процессу.
  Без имени `Pipe.Read()/Read<T>()` — стандартный вход (нет — пустой поток:
  пара с уже закрытым писателем), `Pipe.Write<T>()`/`WriteTo()` — стандартный
  выход (нет — печать на экран одной строкой на сообщение, как печатается вид
  корня). Писатели удобного слоя бросают `PipeException` (обрыв — на
  следующей записи); низкий слой (`Connect` + статус) прежний.
- SDK: `SharpOS.AppSdk.Process` (`Start`, `WaitForExit`, `HasExited`,
  `ExitCode`, `Id`, `Kill`, `Dispose`). Не `System.Diagnostics`: там
  заглушка для DOOM, и форма не та.
- Оболочка: `a | b | c` (стадии — соседние предложения с `|`), голое имя без
  расширения ищется ещё и с `.EXE`.
- Имя типа необработанного исключения: `SharpOS.Std.Runtime.ExceptionNames`
  (проверки `is` от производных к базовым, точный тип — по таблице методов;
  только литералы — отчёт идёт во время раскрутки). Приложение регистрирует
  у ядра своего «назывателя» (`SetExceptionNamer`); отчёт печатает
  `[app] ИМЯ: unhandled ТИП: текст`.

Ошибка по пути: дети, запущенные новой службой, получили таблицу ABI V1 —
служба передавала «0» вместо «авто» в выбор ABI.

Первый прогон: `PIPEGEN 5` — пять строк `PipeApps.LogEntry { Level = …,
Text = "запись …" }`; `PIPEGEN 1000 | PIPEFILT 3 | PIPECNT` — `400`; то же
через `Process.Start` из PROCTEST — `400`, коды 0.

### Доводка до зелёного

Корни, найденные прогонами PROCTEST:

- **Реестр образов с разметкой размотки был на 4 места**
  (`CoffRuntimeFunctionTable.MaxExtraImages`). Пятый одновременно живущий
  образ молча не регистрировался: его кадры не разматывались, сборщик не
  находил корней под ними. Видно было только под `--gc-stress`: PIPECNT упал
  с «Invalid UTF-8» на строке из подметённой памяти, а кадры печатались как
  `(no image)`. Теперь 32, отказ регистрации — отказ загрузки с причиной.
- **Там же: снятие регистрации не сдвигало `ManagedStart/ManagedEnd`** —
  после выхода одного образа следующие отвечали на «управляемый ли код»
  диапазоном соседа. Ошибка старше шага; правка и защита от вытеснения.
- **Куча ядра росла мусором каждого запуска** (≈1 МиБ сегмента на старт):
  политика `GcHeap` — новый сегмент, сборка только когда расти некуда, а
  путь старта процесса сборки не просил. Теперь у ядра «собрать перед
  ростом», когда куча выросла на половину с последней сборки
  (`GcHeap.CollectBeforeGrowing`, у приложений выключено).
- **Список свободных страниц на 1 ГиБ** терял страницы при переполнении;
  дюжина процессов по 64 МиБ, завершившись вместе, отдаёт больше. Теперь 4 ГиБ.
- **Конец пары, не открывшийся из-за типа, оставался открытым** до выхода
  процесса (труба и блоки висели). Закрывается при отказе.
- **Убиваемый поток печатал «необработанное исключение»**: прерванное
  ожидание в трубе отвечает «обрыв», приложение бросает. Такой поток теперь
  уходит молча с кодом процесса.
- **Без пула задач `Thread.Sleep` в приложении возвращается сразу**
  (`TaskBackendInstaller.Install` в тестовом приложении); старая особенность,
  не шага.
- **AotTests «region from kernel»** ждал задачу-сборщик ровно секунду; со
  сборками ядра перед ростом не успевал. Читает, пока все не отработали (до
  10 с).

## Отчёт

### Как сделано перемещение

Приложения собираются без `/FIXED` с `/BASE:0x100000000` — линкер оставляет
`.reloc` (у AotTests 18 244 записи, у оболочки 16 892). `PeLoader.TryLoad(image,
loadBase)` кладёт образ в диапазон слота процесса (`0x2000_0000_0000 + слот ×
1 ГиБ`, 16 слотов), применяет DIR64-релокации на месте, переписывает
`ImageBase` в заголовке, точку входа сдвигает. Типов, кроме DIR64 и ABSOLUTE,
в образах нет; встреться — отказ с текстом. Таблицы нет — `[pe] image cannot
be relocated to 0x…: no base relocations (linked /FIXED?)` (так и случилось со
старым BENCHAOT.EXE до пересборки). Приложение узнаёт свою базу из блока
запуска (`GcStaticsInit.ImageBase` был константой). CR3 один, ничего не
переотображается; диапазон с пулом кучи (он в `.bss`) и стек возвращаются при
выходе.

### Как снимаются потоки и какие окна остались

Завершение (`RequestEnd`: выход, 134, 137) помечает все потоки процесса,
первый код выигрывает. Главный поток, выйдя из `JumpStub.Run`, ждёт ухода
остальных (`EndProcessThreads`: не стартовавшие снимаются сразу), затем
закрывает концы труб, отдаёт блоки, отображения, слот, будит ждущих.
Поток уходит только вне кода ядра:

- в коде приложения — на ближайшем тике (`Preemption.TurnToLeave` переписывает
  кадр прерывания на выход);
- в службе через переходник — дорабатывает службу; переходник после `call`
  читает флаг убиваемого текущего потока и уходит вместо возврата;
- ожидание по адресу и сон обрываются (`Scheduler.RequestKill`) и больше не
  засыпают у убиваемого; циклы ожидания труб в ядре выходят с «обрыв».

Окна: службы без переходника (трубы, `WaitOnAddress`, обменная куча) после
возврата отдают управление коду приложения, поток снимается тиком — до кванта
работы приложения после `Kill`. Ожидание на блокировке ядра не обрывается
(дождётся владельца). Поток, собирающий без перерыва (под стрессом), держит
вытеснение подавленным почти весь квант, отложенного переключения на `Allow`
нет — соседние потоки голодают (тесты 7, 8 под стрессом не гоняются).

### Что нашлось в службах

Глобальное «текущее приложение»: `s_exitRequested/s_exitCode`,
`s_runExternalDepth`, `ProcessManager.s_currentContext`, `JumpStub.s_active`,
фабрика исключений в `JumpContext`, `s_alternateScreenOwner` по глубине — всё в
запись процесса или в поток. `StartupData` и `s_publishedAbiVersion` — одни на
машину: старты сериализованы мьютексом. `Exit` только запоминал код (`Fatal` в
приложении после него крутился вечно) — теперь завершает. Служба запуска
передавала «0» вместо «авто» в выбор ABI. Реестр образов размотки на 4 места и
сдвиг без `ManagedStart` (выше). Файловая система уже под своей блокировкой
(step174); `Kill` посреди чтения файла её освобождает (тест 8). Остались
общими: пробы ядра для тестов (`PipeProbe`, регионы) — у AotTests режим
`--concurrent` их не трогает; ввод с клавиатуры и экран — вне шага.

### Сколько процессов помещается

Образ любого приложения в памяти — 64–65 МиБ (пул кучи 64 МиБ в `.bss`),
плюс стек 64 КиБ и стек ядра главного потока 64 КиБ. QEMU 2 ГиБ: ядро вне
кучи ≈55 МиБ; упираемся в таблицу (16, считая оболочку и запустившего —
тест 12 запустил 14 детей), по памяти влезло бы ≈26–28.

### Отступления

- `Process` — `SharpOS.AppSdk.Process`, не `System.Diagnostics` (там заглушка
  для DOOM; форма другая: концы вместо перенаправленных потоков).
- Без выхода сообщение печатается одной строкой вида корня
  (`PipeApps.LogEntry { Level = 0, Text = "запись 0" }`), а не построчно по
  объектам, как `RawRegion.Print`.
- Ненулевой код выхода закрывает концы обрывом (так в задании), в том числе
  обычный ненулевой код.
- Оболочка: кроме `|` добавлен поиск голого имени с `.EXE` — без него целевая
  строка `PIPEGEN 1000 | …` не находит программу.
- Писатели удобного слоя (`Pipe.Write`, концы) бросают `PipeException`;
  `PipeWriter<T>.Connect` + статус — прежние.
- Имя типа исключения — по типам std (для своих типов приложения — «a type
  derived from …»): рефлексии нет.

### Что осталось

- Отложенное переключение при `Allow` (голодание при сборках подряд).
- Старт: пул кучи обнуляется целиком при загрузке (225 мс) — лениво или
  меньшим пулом; копирование низких отображений ядра на каждый старт (≈30 мс)
  можно делать один раз.
- Кому идёт клавиатура, Ctrl+C, SMP, изоляция — вне шага.

### Прогон на ноутбуке (HP, 7 ГиБ): зависание на первом запуске

Лог по последовательному порту телефона (`/data/local/tmp/rig/serial.log`):
оболочка стартовала, первый ребёнок (`AOTTESTS --pipe-writer-dies normal`)
встал внутри загрузки образа — после `heap grow pages: 513` нет
`[abi] from image manifest`. Причина: `usable pages: 1872588` (7,1 ГиБ), и
прошивка положила **само ядро** по 0x1_4000_0000 (`ib=0x140000000`, стек
ядра 0x14052DA28) — в отображённую один к одному память выше 4 ГиБ. Слоты
процессов начинались с 0x1_0000_0000, слот 1 = 0x1_4000_0000: ребёнок грузился
поверх ядра. Под QEMU (2 ГиБ) выше 4 ГиБ ничего нет. Слоты перенесены на
32 ТиБ (`0x2000_0000_0000`), туда же предпочтительная база при линковке.
(Слот 0 при старом адресе тоже перекрывал память 4 ГиБ + 64 МиБ — до шага 194
так жил любой запуск приложения на машине больше чем с 4 ГиБ.)

Раскладку ноутбука повторяет QEMU с 8 ГиБ (`run_build.ps1 -MemoryMb 8192`,
новый параметр): OVMF кладёт ядро туда же, на 0x1_4000_0000. На новом адресе
слотов там всё запускается, и вскрылась вторая ошибка, которую 2 ГиБ прятали:

**Страницы процессов терялись при большом объёме памяти.** Образ брал
непрерывный кусок через `AllocPages` — только из нетронутой памяти, мимо
списка свободных. Отданные процессами страницы копились в списке и не
использовались, пока список (1 млн страниц) не заполнялся; дальше
освобождаемые страницы терялись (PROCTEST: +3,4 ГБ в обороте). При 2 ГиБ
нетронутая память кончалась раньше, и страницы шли по кругу. Образ теперь
берёт страницы по одной (`AllocPage`, сначала из списка свободных):
отображению непрерывность не нужна. С 8 ГиБ PROCTEST 49/49, страницы до и
после — 46242 и 46242. Остаётся: стеки потоков по-прежнему непрерывные
(`AllocPages`) — их страницы копятся в списке так же, но по ≈20 на процесс.
