# step 206 — `> файл` хранит объекты, CBOR, jsonl

Задача от пользователя: `synth > file`, потом `read file | …` давал строки, а не объекты. `>` писал объекты строками с экрана, и тип терялся.

Решения, принятые в разговоре:

- **Формат по умолчанию самодостаточный, явные конвертации — через `CONVERT`.**
- **Смешивать трубы нельзя.**
- **JSON — потоковый массив, JSON Lines — отдельный формат `jsonl`.**
- **Склейка байтов — не наша забота.** `CONVERT` конвертирует, `WRITE --append` дописывает; проверок формата у байтовых файлов нет.

## 1. externalpipe

Блок в трубе уже не зависит от адреса и от писателя: ссылки — смещения от начала блока (`RegionWriter`), типы — ключи, описание типов — `RegionSchema`. Файл — это описание и блоки как есть:

```
"SharpOS externalpipe 1\n"
u64 ключ корня, u32 n, n байт описания
на сообщение: u64 длина, байты блока
```

- `std-no-runtime/Pipes/ExternalPipe.cs`:
  - `Header`;
  - `Copy` — вход в байты, без обхода и сериализации;
  - `ExternalPipeReader` — заголовок, затем блоки в арену обмена;
  - `Replay` — на выход под описанием файла или на экран;
  - `SameTypes`, `RootName`.
- **`WRITE`.** Поток `string` и `byte[]` пишется байтами, как раньше. Любой другой поток (класс, Expando, object) — externalpipe.
  - `--append` в externalpipe — только тех же типов: совпадает корень и набор ключей всех типов описания. Иначе отказ с обоими именами, код 1.
  - Пустой файл или его отсутствие — как новый.
- **`READ`** узнаёт сигнатуру: объявляет выход описанием файла и отправляет блоки. Класс не нужен.
  - KQL после `READ` связывает запрос до данных, как после живого писателя.
  - Обрезанный или битый файл: целые сообщения, сообщение о месте, обрыв выхода, код 1.
  - `--bytes` — всегда байты.
- **`CONVERT --to externalpipe` / `--from externalpipe`** — то же отдельной стадией (байты как `byte[]`-сообщения).

Тип блока проверяет читатель, как у любого писателя: вид проверяет запись при обращении (step205).

## 2. CONVERT

| | to | from |
|---|---|---|
| `json` | массив, объект на строку | массив или последовательность — по первому токену |
| `jsonl` | JSON Lines | только последовательность |
| `cbor` | тег 55799, массив неопределённой длины, словарь на сообщение, `FF` | массив (любой длины) или последовательность, тег 55799 пропускается |
| `cborseq` | CBOR Sequence (RFC 8742) | только последовательность |
| `lines` | строка как на экране (раньше это делал `WRITE`) | строка на строку файла |
| `externalpipe` | байты файла | сообщения файла |

- `--to json --lines` убран: два способа записать одно и то же.
- Классы `ToJsonl`, `FromJsonl`, `ToCborseq`, `FromCborseq` — наследники с другим именем формата: реестр создаёт по классу на файл.
- **CBOR сохраняет то, что JSON превращает в строки:**
  - `byte[]` — байтовая строка;
  - `DateTime` — тег 0 (строка «O»);
  - `Guid` — тег 37 (порядок RFC 4122);
  - `float` и `double` — своей ширины;
  - NaN и бесконечности — как есть.
- **При чтении:**
  - теги 0 и 1 → `DateTime`, тег 37 → `Guid`, неизвестный тег → его значение;
  - `TimeSpan` остаётся строкой;
  - число-ключ словаря → текст.
- **Потоковость CBOR.** Элемент разбирается из того, что пришло. Если он обрезан концом прочитанного (`UnexpectedEndOfBuffer`), буфер дочитывается до полного, растёт вдвое, и элемент разбирается заново.
