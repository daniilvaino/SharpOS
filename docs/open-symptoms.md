## SYM-003 — `GC.WaitForPendingFinalizers()` hangs

**Date:** 2026-05-28 (step113-followup)
**Tier:** CoreCLR-hosted
**Status:** open, not yet investigated

**Observation:** A probe doing
```csharp
GC.Collect();
GC.WaitForPendingFinalizers();   // <-- hangs here
GC.Collect();
```
at the bottom of a deep managed recursion hung the kernel (QEMU stayed
open, not a triple fault). Sampling RIP via QMP `info registers` showed
it MOVING through CoreCLR GC/sync code (`GCHolderBase::EnterInternalCoop`
threads.h:4649 and neighbours) -- a busy/blocking wait, not a hard
deadlock at one instruction. CR2=0 (no fault).

Removing just the `WaitForPendingFinalizers()` line made the same probe
pass cleanly (now `GC FRAMEREG_REL refs across Collect [OK]`, census
OK=50). So the hang is specifically in the finalizer-drain wait, NOT in
GC.Collect / FRAMEREG root reporting (which work fine).

**Hypothesis:** our CoreCLR-hosted finalizer thread either (a) never
starts, (b) starts but never drains the finalizer queue, or (c) drains
but never signals the completion event that `WaitForPendingFinalizers`
blocks on. `EnterInternalCoop` in the RIP sample suggests the calling
thread is parked in a coop-mode GC-safe wait expecting the finalizer
thread to make progress that never comes.

**Important context (confounding cleared):** this was initially
mis-attributed to the step72 RBP override during a "is the override
redundant?" experiment. The first probe was confounded -- it tested
FRAMEREG slot reporting AND WaitForPendingFinalizers at once. The hang is
the finalizer wait. A later clean single-variable probe removed the
step72 RBP override successfully (see `done/step113.md`); this symptom is
only about finalizer completion.

**To investigate (when picked up):**
- Does the finalizer thread get created at CoreCLR startup? Grep for
  `FinalizerThread` / `GCHeap::CreateFinalizerThread` activity in a
  verbose boot log.
- Is the finalizer-done event (`hEventFinalizerDone` /
  `FinalizerThread::FinalizerThreadWait`) signaled? Check the
  fork's finalizer thread wait/wake wiring against our PAL
  Event/WaitForSingleObject.
- Does a plain `new object()` with a finalizer ever get its finalizer
  run at all (separate from the Wait)? If finalizers never run, the
  whole subsystem is the gap; if they run but Wait doesn't return, it's
  the completion-event signaling.

**Why parked:** finalizers are not on the current critical path; most
managed code doesn't call WaitForPendingFinalizers. Logged so the next
finalizer-dependent workload (using/Dispose patterns relying on GC
finalization, IDisposable-heavy code) has a known starting point.

## SYM-004 — нарушение доступа в `ModuleHandle.GetDynamicMethod` под четырьмя потоками

**Дата:** 2026-09-16 (step175-followup, стенд)
**Ярус:** CoreCLR-hosted
**Статус:** открыт, не воспроизведён намеренно

**Наблюдение.** Проба переписи «JIT stress: 4 threads emit+run, 3s» упала с
`0xC0000005` и полным управляемым стеком:

```
   JIT stress: 4 threads emit+run, 3s             Fatal error.
0xC0000005
   at System.ModuleHandle.<GetDynamicMethod>g____PInvoke|9_0(QCallModule, Byte*, Byte*, Int32, ObjectHandleOnStack, ...)
   at System.ModuleHandle.GetDynamicMethod(...)
   at System.Reflection.Emit.DynamicILGenerator.GetCallableMethod(RuntimeModule, DynamicMethod)
   at System.Reflection.Emit.DynamicMethod.GetMethodDescriptor()
   at Program+<>c__DisplayClass0_15.<<Main>$>b__231()
   at System.Threading.Thread.StartCallback()
```

Падение забрало весь прогон: лог обрывается здесь, до лаунчера дело не дошло.

**Не детерминировано.** Та же проба прошла в трёх прежних прогонах на том же
ноутбуке — 81009, 72295 и 80344 метода
(`work/bench-2026-09-14/sharpos-laptop-bootlog.txt`,
`…-poolwarm-bootlog.txt`, `work/rig-bootlog.txt`). Значит гонка, а не
сломанный путь.

**Разделяющая деталь.** Соседняя проба «4 threads, retained» в том же прогоне
прошла (79812 методов). Падает именно та, где созданные методы **не
удерживаются** и сразу становятся мусором. То есть подозрение на время жизни:
что-то освобождается, пока QCall ещё держит на это указатель.

**Гипотезы, ни одна не проверена:**
- Гонка времени жизни `DynamicMethod`/`RuntimeModule` при сборке параллельно
  с созданием — сборщик забирает то, на что смотрит нативная сторона.
- Замок в форке CoreCLR вокруг этого пути опирается на примитив PAL, который у
  нас слабее, чем предполагалось.
- Сдвиг таймингов: в этом прогоне впервые работал приёмник лога в COM-порт
  (`Probes.UsbSerialLog`), добавляющий передачу по USB на каждую строку с
  запрещённым вытеснением. Гонка, трижды проскочившая, могла вылезти от этого.

**Что закроет.** Серия повторов на стенде — он для этого и строился. Если
частота около одного из четырёх, ловить под `-TraceFaults` и смотреть CR2 и
адрес: указывает ли он в освобождённую память. Если при
`UsbSerialLog=false` частота падает до нуля на десятке прогонов — причина в
таймингах, и тогда гонка всё равно наша, просто раньше её прятал более
спокойный ритм.

**Почему не взялись сразу.** Ярус hosted, и на критическом пути (загрузка,
лаунчер, батарея) этот код не лежит — он живёт только в стресс-пробе переписи.
Но падение фатальное и уносит весь прогон, поэтому для стенда, который должен
гоняться ночами, это блокер: одна такая проба обнуляет серию.

## SYM-005 — вечный цикл в управляемом коде после долгого сеанса

**Дата:** 2026-09-16 (step175-followup)
**Ярус:** CoreCLR-hosted
**Статус:** открыт, воспроизводится

**Наблюдение.** Машина с работающим PowerShell простояла 23 минуты
**без единого выделения** (образ на диске не менялся). После нажатий клавиш —
лаунчер на них отвечал — сеанс перестал отзываться. Машина при этом **жива**:
сэмплер продолжает печатать отчёты каждые 10 000 проб.

```
[prof] samples=1075228 ... halt=955976 busy=23565 threads[1:120392 ... 31:954363]
       | 943281x ext@0x7e7eb2b6 | 759x krnl+0x6077ce | 197x krnl+0x606dc3
       <= 943281x krnl+0x602b95 , 117256x ext@0x10003b1a8
[prof] samples=1085228 ... halt=955976 busy=23565 threads[1:130392 ... 31:954363]
       ... , 127256x ext@0x10003b1a8
```

**Что видно из счётчиков:**
- `halt` и `busy` **не растут** — процессор больше не останавливается ни разу.
- Поток 1 забирает ровно 10 000 проб на каждый отчёт, то есть **все**.
- `ext@0x10003b1a8` растёт на 10 000 за отчёт — это и есть петля, и она
  **вне образа ядра**: код, порождённый JIT.
- В ядро цикл почти не заходит: `Hpet.ReadCounter` 759 проб,
  `XhciController.Write64` 197 на сотни тысяч.
- `krnl+0x602b95` = `X64Asm.StiHlt`, 943 281 — это накопленный простой ДО
  события, счётчик замер; поток 31 это холостой поток, а не заблокированный.
- `critDepth=0`, `yieldsInCrit=0` — в критической секции цикл не сидит,
  вытеснение ему не мешает.

**Итого:** один поток крутится в управляемом коде, не отдавая процессор и не
обращаясь к ядру. Не отказ страницы, не тройная ошибка, не исчерпание памяти
(за весь прогон 39 ростов кучи, около 10 МБ при семи гигабайтах свободных).

**Чем это НЕ является** (проверено):
- Не рост кучи: за 23 минуты простоя куча не выросла ни разу.
- Не переполнение счётчика HPET: `64bit=yes`, оборота нет.
- Не цикл ожидания ввода в `ConsoleRead`: он зовёт `Scheduler.Idle()`, а
  счётчик остановов замер.

**Гипотезы, не проверены:**
- Приостановка мира сборщиком CoreCLR: поток крутится, ожидая, что другой
  дойдёт до безопасной точки, а тот заблокирован внутри нашего PAL и не дойдёт
  никогда.
- Спин-замок в рантайме поверх примитива PAL, который у нас слабее ожидаемого.
- Обычный бесконечный цикл в самом PowerShell, вызванный потерянным событием
  ввода.

**Что закроет.** Опознать `ext@0x10003b1a8` — это адрес в коде JIT, а таблицы
его символов у нас нет. Ближайший путь: реестр кадров JIT, который уже
используется для размотки (`seh.lookup.jit`), научить отвечать «какому методу
принадлежит адрес». Без этого дальше только гадание.

**Почему важно.** Это, судя по всему, и есть то самое «лаунчер зависает через
полчаса», с которого началось расследование. Утечка в `XtermSharp`
(1.45 млн `byte[]`, 49 МБ, исправлена в этом же шаге) оказалась **другой**
проблемой, найденной по дороге: она делала машину медленной, но не вешала.

## SYM-006 — лаунчер исчерпывает свою кучу: замедление, потом падение

**Дата:** 2026-09-16 (step175-followup)
**Ярус:** PE-приложение (лаунчер, Terminal.Gui)
**Статус:** ЗАКРЫТ 2026-09-16 — декодер `GcInfo` не читал таблицу точек
безопасности; см. раздел «РЕШЕНО» в конце

**Наблюдение (воспроизведено дважды).** Лаунчер, по которому долго ходят
стрелками и заходят в папки, **постепенно замедляется**, а затем падает. Оба
падения — в одной точке, `List<Rune>.ToArray`, на пути перерисовки:

```
InvokeKeybindings            ← стрелка
 → TreeView.AdjustSelection  :1037
 → AppEntry.ShowSelection    :266
 → View.ProcessResizeView    :825
 → View.GetBoundsTextFormatterSize :2821
 → View.GetHotKeySpecifierLength   :2792
 → TextExtensions.Contains   :263
 → TextExtensions.ToRunes    :181
 → List<Rune>.ToArray        :110
```

**Решающее наблюдение — от автора:** открытый из оболочки **новый** лаунчер
снова быстрый. Будь причина в ядре или в общей куче, второй экземпляр тормозил
бы так же. Значит копится состояние самого приложения.

**Корень.** Куча приложения — фиксированные 64 МБ в `.bss` образа
(`std/no-runtime/shared/GC/GcMemorySource.AppStatic.cs`), выдаются сдвигом
курсора и **никогда не возвращаются**. Сборщик приложения исправен
(`AppGC.Collect`: статические корни, обход стеков через службу ядра,
подметание), но освобождать может только **внутри уже взятых сегментов**;
новый сегмент берётся из пула, а пул не пополняется. Поэтому растущий живой
набор даёт сначала всё более частые и всё менее полезные сборки (замедление),
а потом отказ выделения.

Место падения значения не имеет — `ToArray` просто первым попросил память.
Отсюда же разные лица одного отказа: в одном прогоне `#PF` с `CR2=0x0D`, в
другом `#GP` с неканоническим `0x040725C000000014` в регистрах.

**Что НЕ подтвердилось** (записано здесь же вчера и опровергнуто):
- Не порча памяти консервативным сборщиком. Куча приложения своя, её собирает
  `AppGC`, и он отрабатывает штатно.
- Не утечка `byte[]` из `XtermSharp` — та исправлена в этом же шаге и жила в
  куче ядра, а не приложения.

**Открытый вопрос, уже узкий:** что удерживает лаунчер при переходе между
папками. Кандидаты не проверены: узлы дерева `FileTree`, подписки на события
Terminal.Gui, история `TreeView`.

**Что закроет.** Перепись кучи по типам — та же, что сделана для ядра
(`GcHeapCensus`), но для приложения: назвать тип, которого становится больше от
навигации. У приложения для этого всё есть, кроме самой печати.

### Поправка 2026-09-16 (вечер): падает НЕ тот лаунчер, который тормозил

Диагноз выше объясняет **замедление**, но не падение. Из лога:

```
5891  child start   ← оболочка (глубина 1)
5899  child start   ← лаунчер  (глубина 2)
5931  child end     ← вышел чисто
6081  child end     ← оболочка вышла
6232  child start   ← оболочка снова
6239  child start   ← лаунчер снова (глубина 2)
6293  HW fault
```

Связка «лаунчер → оболочка → лаунчер» проделана дважды. Первый вложенный
лаунчер отработал и вышел с нулём. **Второй упал через 54 строки лога** — без
долгой навигации и без исчерпания пула: у него свой свежий пул, а `RhpNewArray`
при нехватке бросает нехватку памяти, а не возвращает `null`. Значит отказ
страницы по `CR2=0x0D` — разыменование почти нулевого указателя, и версия
«пул кончился» к нему не относится.

Отличается здесь одно: это **повторный запуск на той же глубине вложенности**.
Области стека назначены по глубине в этом же шаге (`StackMappedTopForDepth`) и
переиспользуются; до этого глубина 2 была невозможна, так что земля нехоженая.
Простое объяснение «остались старые отображения» не проходит —
`CleanupProcessMappings` снимает и образ, и стек.

**Разделяющий опыт (не проведён):** проделать «лаунчер → оболочка → лаунчер»
дважды, **почти не ходя по папкам**. Если второй вложенный лаунчер падает и
так — дело во вложенности, и подозрение на правку этого шага. Если нет —
падение всё-таки связано с объёмом работы, и тогда его ищет перепись кучи
приложения.

### Корень найден 2026-09-16 (ночь): сборщик приложения не находит корни

Отчёт из самой сборки (`AppGC.Collect`, печатается без выделений, в момент
события):

```
[appgc] collect #1 swept=985848 kept=508
[appgc] collect #2 swept=12 kept=509
```

**508 живых объектов** в приложении с работающим интерфейсом Terminal.Gui —
столько не бывает: одно дерево каталогов держит больше. Разметка не нашла
почти ни одного корня, и сборка **уничтожила живое**. Вторая сборка следом
подмела 12 объектов: подметать больше нечего.

Это объясняет всё, что наблюдалось:
- первая сборка случается только при исчерпании пула (она привязана к отказу
  выделения), то есть один раз за сеанс и сразу разрушительно;
- следующее обращение к уцелевшей ссылке даёт `_items == null` при `_size` в
  сотню с лишним — состояние, которого интерфейс `List<T>` создать не может;
- падения приходят в разных местах одного района (`ToArray`, `GetRange`,
  перерисовка) — это просто те, кто первым коснулся подметённого;
- «замедление» перед падением — заполнение пула, отдельная и меньшая беда.

**Не выяснено:** почему разметка не видит корней. Обход (`AppGcService.WalkRoots`)
формально делает и текущий стек (`RunFromCurrentFrame`), и остальные потоки, а
точный обходчик умеет чужие образы — он берёт базу по каждой записи
(`ImageBaseForRecord`). Значит теряется что-то между: `GcInfo` кадров
приложения, граница службы, или разметка статики приложения.

**Почему это важнее замедления.** Пока сборка не находит корни, **запускать её
чаще нельзя** — это способ портить память чаще, а не реже. Поэтому порог
сборки по бюджету, который напрашивался по симптомам, сейчас был бы прямо
вреден.

### РЕШЕНО 2026-09-16 (ночь): декодер `GcInfo` читал только половину формата

**Статус SYM-006: закрыт.**

Измерение, разделившее поиск корней на половины, назвало виновного за один
прогон:

```
[appwalk] frames=79 roots=25 unresolved=11 outofrange=30 slotoverflow=0 capped=0
[appgc]   collect #1 swept=960652 kept=558 slots=28 bystatics=556 stackroots=25 dropped=0
```

`outofrange=30` — **30 кадров из 79 выбрасывались целиком**.
`CoffGcInfoDecoder.EnumerateLiveSlotsAtPc` знал только прерываемые диапазоны, а
таблицу точек безопасности **пропускал не читая** (`SkipSafePointOffsets` —
имя честное, читателя у неё не было нигде). Но обход стека спрашивает про
адреса возврата, то есть почти исключительно про места вызова, а частично
прерываемый код — а ILC генерит в основном такой — держит свои наборы живых
слотов именно там. Кадр, чей PC не попал ни в один диапазон, объявлялся
неразметимым, и все его локальные `View`, списки и массивы уходили под нож.

Вторая половина правки — сдвиг на −1. Кодировщик индексирует места вызова
смещением **внутри** инструкции `call`; обход стоит на адресе возврата. Без
сдвига поиск либо не находит ничего, либо находит набор *следующего* вызова.
`CoffNativeCodeManager::EnumGcRefs` делает ровно это и предупреждает, что
половины формата связаны.

Попутно развели три точки входа обходчика: верхний кадр по-настоящему активен
только у прерванного потока, а у снятого контекста и у припаркованного потока
`Rip` — тоже адрес возврата, и сдвиг им нужен наравне со всеми.

После правки:

```
[appwalk] frames=51 roots=21 unresolved=8 outofrange=3 slotoverflow=0 capped=0
[appgc]   collect #1 swept=983862 kept=551 ...
[appgc]   collect #2 swept=789132 kept=523 ...
```

Две сборки подряд пережиты там, где раньше первая же убивала приложение.
Батарея без изменений: перепись 157/2/18, AOTTESTS 61/61, паник нет.

**Что это чинит помимо лаунчера.** Обходчик общий, поэтому та же слепота была
и у сборщика ядра — просто ядро выделяет несравнимо меньше и до отказа не
доходило.

**Отброшенные по дороге версии** (каждая закрыта измерением, не рассуждением):
- предел таблицы корней в 256 слотов — переполнение зовёт
  `GcHeap.Fatal`, оно громкое, его не было;
- переполнение стека разметки (4096 записей, отбрасывались молча) — `dropped=0`;
- необойдённая секция замороженных объектов образа — там 17000 байт
  строковых литералов с одним `MethodTable`, а строки ссылок не держат;
- потеря блоков статики — в образе их ровно 27 (секция 201, 108 байт),
  `slots=28` совпадает с ними полностью.

**Осталось открытым, отдельно от этого симптома:**
- `unresolved=8` — обход всё ещё обрывается на кадрах без `GcInfo`. Часть из
  них законна (дно потока — входной переходник), но не проверено, что все.
- Куча приложения — 139 158 строк (`mt=0x100052320`) на 11.3 МБ за несколько
  минут навигации. Сборка теперь их возвращает, но сам темп выделения —
  отдельная задача.

**Наблюдение.** Лаунчер на ноутбуке встаёт примерно через полторы минуты работы.
Машина при этом **жива**: тики идут, дампы потоков печатаются раз в десять
секунд. За 14 часов — 5105 дампов, из них **5095 подряд побайтово одинаковых**:
все восемь потоков в `Waiting`, двое на `wait=Timer`, ни одно значение не
изменилось. На QEMU не воспроизводится ни разу.

**Корень.** Прошивка ноутбука сообщает:

```
hpet: freq=14318180 Hz period=69841278 fs comparators=3 64bit=no
```

Счётчик **32-битный**, период обхода `2^32 / 14318180 ≈ 300 секунд`.
`OS/src/Hal/Timer/Hpet.cs` `ReadCounter()` читает 64 бита:

```csharp
// 64-bit counter is atomic on x64; on 32-bit-only HPETs (rare on
// modern hardware), the upper 32 bits are zero so a simple
// 64-bit read still yields the correct value.
return *(ulong*)(s_base + OFFSET_COUNTER);
```

Комментарий верен ровно до первого переполнения. Дальше счётчик обнуляется, а
`Scheduler.Sleep` уже посчитал `deadline = now + ms * ticksPerMs` — и если `now`
был близок к верхушке диапазона, дедлайн лежит там, куда счётчик больше не
попадёт. Поток остаётся в очереди таймера навсегда, будить его нечему, все
прочие ждут своего, планировщик уходит в halt.

**Почему искали долго.** Отказ не в исполняемом коде, а **в числе, которое
сравнивают**. Профилировщик молчит (окно в простое — подавление по построению),
трасс нет (никто не падает), дампы показывают совершенно здоровое состояние.
Шесть версий подряд были сняты, прежде чем очередь дошла до строки загрузки.

**Что проверить помимо сна:** `PerfCounters` считает разницы по тому же
счётчику; `HpetCounterAddress` отдаётся **приложениям** через таблицу служб, и
они читают MMIO напрямую — у них та же беда, `Stopwatch` приложения тоже.
`fami` пасётся 60 Гц по HPET.

**Правка.** Программно расширить счётчик до 64 бит: хранить старшее слово,
увеличивать при обнаружении обёртки. Опрос обязан происходить чаще периода
обхода — 300 секунд запас огромный, тика 1000 Гц хватает с избытком. Для
приложений либо отдавать расширенное значение через службу, либо описать правило
в ABI.
