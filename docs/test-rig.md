# Стенд: прогон на железе без рук

Цикл: собрать на ПК → доставить по сети → включить ноутбук → прогнать батарею
→ забрать лог. Человек не нужен ни на одном шаге. Первый полностью автономный
прогон — 2026-09-15.

Зачем: каждый прогон на железе раньше стоил человека у ноутбука, а вытеснение
и USB требуют их десятками.

## Из чего собран

| Часть | Роль |
|---|---|
| ПК | собирает, доставляет, включает розетку, читает лог |
| Ноутбук (Ryzen 3 7320U, AMI) | машина под тестом; RJ45 нет, есть Type-C |
| Oukitel WP19 (Android 12, Magisk) | флешка + COM-порт + (в планах) клавиатура для ноутбука |
| Умная розетка TP-Link Tapo P110 | включает ноутбук; управляется по локальной сети |

Скрипты — `C:\android-home\rig\`, на телефоне их копии в
`/data/local/tmp/rig/`. В репозитории только батарея:
[`apps_native/Shell/autorun.sh`](../apps_native/Shell/autorun.sh).

## Как идёт прогон

```
.\build.ps1 shell                    # если менялась оболочка
.\run_build.ps1 -Autorun             # кладёт батарею как \apps\AUTORUN.SH
C:\android-home\rig\deploy.ps1       # шлёт изменившееся на телефон
C:\android-home\rig\plug.ps1 pulse   # питание на минуту — ноутбук стартует
```

`-Autorun` — единственный переключатель: ядро видит `\apps\AUTORUN.SH` и
запускает `SHELL.EXE` вместо лаунчера. Оболочка прогоняет строки, выходит,
ядро гасит машину. Без ключа файл удаляется и сборка снова грузится в лаунчер.

Строка, которую стоит искать в логе:

```
[sh] done ran=2 failed=0
```

## Телефон как флешка: четыре слоя

Каждый сам по себе давал «флешка не работает», и ни один не сообщал о себе.
Собирает гаджет `rig.sh`.

1. **`init` перепривязывал UDC каждую секунду** — при `sys.usb.config=adb` и
   гаджете без `ffs.adb` functionfs у adbd мигает, хост не проходит дальше
   `addressed`. Лечится `setprop sys.usb.config rig`: значение, под которое нет
   правил; adbd при этом жив, так что adb по Wi-Fi остаётся.
2. **VID/PID/серийный совпадали с fastboot-устройством телефона**, которому в
   Windows вручную привязан драйвер. Свои: `1d6b:0104`, serial `sharpos-rig`.
3. **MS OS descriptors.** Android включает их на `g1`; Windows просит Extended
   Compat ID, ответа нет, четыре сброса, Code 10. Выключить `os_desc/use` мало
   — надо убрать и ссылку `os_desc/b.1`. Ответ кешируется в
   `usbflags\VVVVPPPPRRRR osvc`, поэтому при смене менять и `bcdDevice`.
4. **SELinux.** Поток ядра `file-storage` (домен `kernel`) не может читать
   `shell_data_file` — хост видит нечитаемый диск и предлагает
   отформатировать. Лечит `policy.sh` (`magiskpolicy --live`).

Ничего из этого не переживает перезагрузку телефона: после неё нужны
`rig.sh`, `policy.sh`, `serial.sh start` и adb по Wi-Fi заново
(`service.adb.tcp.port` не персистентен, `persist.adb.tcp.port` телефон не
читает).

## Образ и доставка

Носитель — `sharpos-rig.img`, 512 МиБ, **MBR с разделом на LBA 2048**. Образ
сборки `esp.img` сюда не годится: это «суперфлоппи» mtools с фиктивной записью
MBR (start=0, длина больше диска). QEMU и наш FAT это прощают, Windows и
прошивка HP — нет.

`deploy.ps1` шлёт только файлы, изменившиеся с прошлой отправки (обычно один
`BOOTX64.EFI`, 8 МиБ из 350), телефон монтирует раздел через `losetup -o
1048576` и копирует их внутрь. Гонять 512 МиБ на каждую сборку не нужно.

Носитель заметно быстрее флешки SanDisk, с которой стенд начинался: сектор
лога 0.2 мс против 1.6–2.7, Enter в PowerShell 0.22 с против 1.7.

## Живой лог по COM-порту

`acm.0` даёт ноутбуку CDC-ACM, наш драйвер (`OS/src/Hal/Usb/UsbCdcAcm.cs`)
шлёт туда тот же текст, что и в файл, и при подключении переигрывает ранний
буфер — лог приходит с самого начала загрузки и **во время** прогона, а не
после вскрытия образа.

Две ловушки, обе стоили пустого лога:

- **Номер порта не нулевой.** У телефона свои `ttyGS0`–`ttyGS3` под модем,
  наш `acm.0` получил `ttyGS4`. `serial.sh` спрашивает номер у самой функции
  (`functions/acm.0/port_num`). Запись при этом проходит успешно: гаджет байты
  принимает и выбрасывает, потому что его порт никто не открыл.
- **`cat` умирает в конце каждого прогона** — хост отваливается, когда машина
  гасит себя. Одноразовый читатель жил ровно один прогон. Сейчас цикл с
  переоткрытием.

Забрать: `adb pull /data/local/tmp/rig/serial.log`.

## Питание

У ноутбука нет батарейки CMOS: часы и настройки держатся от основного
аккумулятора. Вынуть его нельзя — сбрасывается Setup, а вместе с ним и сам
пункт, ради которого вынимали. Поэтому **аккумулятор остаётся внутри**, и
розетка отвечает только за включение:

- в Setup: `Power on when AC detected` — Enabled, `USB Boot` — Enabled, USB
  выше внутреннего диска, Secure Boot и Fast Boot — выключены;
- в приложении Tapo состояние при подаче питания — **Выключено**, иначе
  моргание в сети само запустит прогон.

Выключается машина сама (ядро гасит её после батареи). Не закрыто: зависание
до инициализации сторожа — там нужна рука.

**Запускать прогон надо импульсом, а не включением.** `plug.ps1 pulse` даёт
питание на минуту и снимает его: прошивка ловит появление питания, грузится, а
дальше машина работает от аккумулятора. Снимать питание обратно — не
аккуратность, а необходимость. Если оставить включённым, контроллер заряда при
полной батарее ещё минут пять держится в состоянии «заряжается» — его питает
собственная ёмкость блока питания. Пока это состояние не сбросилось, с точки
зрения прошивки питание не пропадало, поэтому следующее включение не считается
новым событием и не запускает ничего. Импульс означает, что к моменту
следующего прогона отключение давно состоялось.

Розетка управляется с ПК локально, мимо облака: `plug.ps1
pulse|on|off|cycle|status|power|wait` поверх `python-kasa` (венв
`C:\android-home\rigvenv`). Учётные
данные аккаунта TP-Link — в `tapo.cred` рядом со скриптом, двумя строками; в
командную строку они не попадают, передаются через переменные окружения,
которые читает сам инструмент.

**Обязательная настройка:** в приложении Tapo у устройства включить
«Third-Party Compatibility». С прошивки 1.4.0 розетка иначе говорит
`Encrypt Type: TPAP` — схему, которой пока не знает ни `python-kasa`
([открытая задача](https://github.com/python-kasa/python-kasa/issues/1590)),
ни интеграция Home Assistant. С включённой совместимостью работает сразу.

`power` и `wait` — то, ради чего взята именно P110: машина под тестом ничего
не сообщает по сети, но потребляет ток. `wait` ждёт перехода «работала →
упала», то есть конца прогона.

**`wait` работает только пока питание подано**, то есть в паре с `on`, а не с
`pulse`: после импульса машина живёт от аккумулятора, розетка не видит ничего,
все показания нулевые — и `wait` отрапортует о конце прогона, который не
начинался. Платой за оставленное питание будет те самые пять минут ожидания
перед следующим стартом.

Замерено на этом ноутбуке (2026-09-16, полная батарея):

| Состояние | Показание розетки |
|---|---|
| выключен (питание подано) | 0.0 Вт, 0.0 А |
| загрузка и прогон батареи | 25–30 Вт |

**Ноль здесь — «ниже порога измерения», а не «нет потребления».** Розетка
отдаёт ток с разрешением в сотые доли ампера, то есть при 235 В не различает
нагрузку меньше ~2 Вт; выключенная машина с полной батареей потребляет
заметно меньше. Прибор грубый и в другую сторону: прогон на 25–30 Вт за 42 с
это 0.33 Вт·ч, а суточный счётчик показывает `0.0 kWh` — у него разрешение в
целые ватт-часы.

Для стенда этой грубости хватает с запасом: разрыв между «выключен» и
«работает» больше порядка. Промежуточного «вхолостую» в цикле не бывает —
машина гасит себя сразу после батареи. Пороги скрипта (`IdleWatts` 2,
`BusyWatts` 12) лежат в этом разрыве, но они от этого ноутбука; другой машине
нужны свои.

**Полный цикл — 42 секунды** от подачи питания до самовыключения: загрузка,
перепись, AOTTESTS, BenchAot, выключение.

## Что ещё не работает

**Клавиатуры нет.** Гаджет объявляет HID как `class=0x3 sub=0x0 proto=0x0` с
4-байтной точкой, хотя в configfs лежат `protocol=1 subclass=1
report_length=8`: `f_hid` забирает эти значения при создании функции и больше
не перечитывает. `rig.sh` теперь удаляет `hid.0` перед пересборкой — нужен
один прогон с выключенным ноутбуком, чтобы проверить. До этого в логе
`keyboard=NO`, и клавиши в Setup (F9, Ctrl+Alt+Del) недоступны.

`kb.sh` уже умеет: `kb.sh key f9`, `kb.sh key ctrl-alt-del`,
`kb.sh line "ls -la"` — коды проверены на сгенерированных отчётах.

## Ловушки окружения

- `fastboot` — только `C:\platform-tools-33`. Новый берёт путь профиля через
  `SHGetFolderPathW` и создаёт `.fastboot` ANSI-функцией; на профиле
  `C:\Users\админимтратор` он падает, и переменные `HOME`/`USERPROFILE` не
  помогают.
- mtools считает `C:\...` буквой диска — пути только относительные.
- `adb push /data/...` из Git Bash превращается в путь Windows — PowerShell
  или `MSYS_NO_PATHCONV=1`.
- Второй гаджет создать нельзя: `mkdir /config/usb_gadget/x` → ENOMEM, а
  попытка уронила ядро телефона. Всё мультиплексируется на `g1`.
