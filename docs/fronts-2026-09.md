# Фронт 1 — таймер (HPET)

Закрывает SYM-007. Первым по порядку: без него стенд не живёт дольше пяти
минут, и проверить два других фронта на железе невозможно.

## Масштаб шире, чем сон

Ломается весь класс «дедлайн = сейчас + дельта». Вешают машину навсегда:

| место | что встаёт |
|---|---|
| `Scheduler.cs:526-534` | `Sleep` — диагностированный случай |
| `HostLocks.cs:279-282` | `Monitor.Wait` с таймаутом |
| `AddressWait.cs:86-109` | `WaitOnAddress` с таймаутом |
| `Iocp.cs:46-56` | ожидание завершения |
| `Process.cs:93-107` | `WaitForExit` |
| `ThreadStubs.cs:403-414` | `ComputeDeadline`/`DeadlinePassed` — **все** конечные ожидания CoreCLR |
| `Ahci.cs:371-384` | бесконечный спин в драйвере **диска** |
| `Xhci.cs:285-295` | то же для USB |

Тихо врут: `PerfCounters.Wall()`; **калибровка APIC**
(`LocalApic.cs:142-144,271-273` — `while (ReadCounter() - start < window)`,
переполнение внутри окна закрывает его мгновенно, таймер калибруется неверно с
вероятностью ~100 мс на 300 с); `Stopwatch.cs:98`; `GcHeapCensus.cs:145`.
`Clock.cs:72-92` уже частично защищён переякорением по RTC.

**Ярус приложений — худшее.** `HpetCounterAddress` отдаёт приложению сырой
MMIO-адрес, приложение читает `*(ulong*)addr` напрямую:
`Stopwatch.AppStub.cs`, `UiLatency.cs`, `Fami`, `TriCNES` (спин упирается в
ограничитель — минуты на кадр), и **`DOOM` без ограничителя вовсе**
(`Program.cs:68-95`) — виснет намертво через ~300 с игры.

Вывод по ABI: раздача сырого адреса некорректна при 32-битном счётчике —
приложение не может узнать эпоху.

## Тесты

**T5/T6 — ярус приложений, краснеют СЕГОДНЯ без правок ядра.** Шов уже есть:
`Stopwatch.s_counterAddress` — `internal static`, тест направляет его на свой
`ulong` и крутит счётчик руками. Обход воспроизводится за микросекунды вместо
пяти минут и одинаково на QEMU, где 64-битный HPET сам баг показать не может.
*(Написано, лежит в `apps_native/AotTests/Program.cs`, `CheckClockWrap`.)*

**T1 — чистая функция.** `Hpet.Extend(latch, raw)` без состояния: без обхода,
ровно на границе, две эпохи подряд, откат на микросекунду не должен добавлять
эпоху. Регрессионная сетка, не ловля сегодняшнего бага.

**T2/T3 — ядро, синтетическая база.** Шов: `Hpet.UseSyntheticBase(byte*)` /
`RestoreRealBase()`, «база» — 4 КиБ из `KernelHeap`, probe сам пишет в неё
счётчик. T2: 5000 шагов через 4 обхода, монотонность и точная сумма. T3: сон на
50 мс через границу, **сторож — `LocalApic.TimerTicks`** (программный
64-битный, обходу неподвластен), 500 тиков без пробуждения → FAIL вместо
зависания. T3b: то же для `ThreadStubs.DeadlinePassed` и `Ahci.Expired`.

**T4 — настоящий обход на QEMU за ~20 мкс.** `ForceThirtyTwoBitForTest()` +
halt/write `0xFFFFFF00`/enable, читать 1 мс. Отдельный флаг, по умолчанию off:
трогает глобальное время. Предусловия: пустая `TimerQueue`, нет I/O в полёте,
APIC-тик армирован, запуск до лаунчера.

Место: `OS/src/Kernel/Diagnostics/HpetWrapProbe.cs` (новый), `Probes.HpetWrap`
и `HpetWrapHardware` рядом с `TimerHz`.

## Правка

Расширение — **только в `Hpet.ReadCounter`**, все потребители зовут его:

```csharp
private static ulong s_latch;   // одно выровненное слово: атомарность на x64

internal static ulong Extend(ulong latch, uint raw)   // чистая, тестируемая
{
    ulong v = (latch & 0xFFFFFFFF00000000UL) | raw;
    if (raw < (uint)latch) v += 0x1_0000_0000UL;
    return v;
}
```

64-битный путь (QEMU) не меняется. Защёлка — носитель эпохи, не источник
времени: каждое чтение берёт сырое значение само, поэтому «устаревший
читатель» невозможен.

**Кто двигает защёлку.** Любой читатель — побочно. Плюс тик APIC, потому что
`DrainExpiredTimers` специально не читает HPET при пустой очереди, а `Idle()`
уходит в `HLT`: простаивающая машина часы не читает вообще. Дросселировать
`if ((TimerTicks & 63) == 0) Hpet.Refresh();` → 15.6 Гц.

Безопасный интервал — половина диапазона:

| частота | обход | предел |
|---|---|---|
| 14.318 МГц (ноутбук) | 300 с | 150 с |
| 100 МГц (QEMU) | 43 с | 21.5 с |
| 10 МГц (минимум спеки) | 429 с | 214 с |

Пропуск обновления = потеря ровно одной эпохи: время прыгает назад на 300 с,
но зависаний уже нет.

**Любая запись в счётчик обязана сбросить защёлку** (`TryForceRestart`), иначе
первое чтение добавит несуществующую эпоху — прыжок вперёд на 300 с. Сегодня
все записи идут до армирования тика; зафиксировать как требование порядка.

**Ярус приложений** — публиковать эпоху, не звать службу: в хвост
`AppServiceTable` (версию **не** бампаем — правило «табличка растёт хвостом»)
добавить `HpetCounterBits` и `HpetLatchAddress`; SDK `Stopwatch` повторяет ту же
формулу. Служба-переходник не годится: дорого на кадр, и у переходников нет
данных размотки. Плюс **второй рубеж**: пейсинг считать разницами
(`ReadCounter() - frameStart < ticksPerFrame`) — беззнаковая разница корректна
через обход сама по себе, и у DOOM исчезает единственный неограниченный спин.

## Риски

`Preemption.Suppress` **не делает** обновление защёлки атомарным: он мешает
переключить поток, но прерывание доставляется и `Idt.Dispatch` всё равно
выполнится. Корректность держится на однословной атомарности — никаких пар
`(high, low)`. **Для SMP это неверно**, там нужен seqlock или CAS-max; пометить
в файле.

Probe с синтетической базой подменяет время всему ядру — пустая очередь до и
после, восстановление в `finally`, ранняя фаза.

## APIC и TSC как замена

**APIC — нет.** Регистр счёта 32-битный и считает вниз; полезен только
`TimerTicks` как сторож для тестов. Разрешение 1 мс, тики теряются, сам
калиброван по HPET — круг.

**TSC — да, но отдельным фронтом.** 64 бита, переполнение через 243 года,
~25 циклов против ~0.5-1 мкс на MMIO. Но: инвариантность не проверяется
(`CPUID 0x80000007.EDX[8]`), под TCG это не счётчик циклов, номинал и реальная
частота расходятся втрое (`tsc 2404 MHz ... actual 4156 MHz`), для SMP нужна
синхронизация. Правильный порядок — сперва монотонный 64-битный HPET как
эталон калибровки, потом TSC. Записать в `donext.md`.

# Фронт 2 — аллокаторы

## Тесты (все счётчиковые, ни один не смотрит на часы)

Место: новый `CheckAllocator()` в `apps_native/AotTests/Program.cs`,
вызывается **последним** — churn оставляет тысячи свободных блоков.
Зеркало в ядре: `GcAllocatorProbe.cs`, печатает `[gcalloc] ok|FAIL`, **без**
`KernelAssert` — красный пробник не должен кирпичить загрузку.

| тест | утверждает | почему красный сегодня |
|---|---|---|
| **A1** фрагментация | крупный запрос обслужен из освобождённого, без нового сегмента | в списке 4096 блоков по 256 Б, `blockAligned >= 65552` не выполнится ни разу → новый сегмент |
| **A1b** тот самый OOM | `!oom` при потолке сегментов | воспроизводит наблюдавшийся отказ за миллисекунды вместо 64 МБ |
| **A2** цена поиска | ≤64 шага на выделение | ни один блок не ≥4108 Б, проход всего списка: ≈8192 шага |
| **A3** склейка | крупнейший свободный ≥64 КБ | слияния нет нигде: `largestFree == 256` |
| **A4** цена разметки | ≤8 шагов на объект | `GcMark.Drain` зовёт `FindSegmentContaining` **дважды на кандидат**, до 512 шагов при 256 сегментах |

A4 в задании не значился — найден агентом и подтверждён по коду
(`GcMark.cs:86` и `:111`). Комментарий `GcHeap.cs:506` «Linear search — OK for
small segment count» неверен ровно в нашем масштабе.

## Хуки, без которых тесты не пишутся

| | нужно | зачем |
|---|---|---|
| D1 | `FreelistProbeCount` | длину обхода видно только по часам |
| D2 | `AllocSlowPathCount` | доля медленного пути |
| D3 | `GetFreeStats(out …)` | вынести счёт из `ReportOutOfMemory`, чтобы тест и лог считали одно |
| D4 | `SegmentLimit` (0=∞) | OOM за миллисекунды вместо 64 МБ |
| D5 | `CurrentSegment` | сейчас выводится из недокументированного инварианта |
| D6 | `SegmentScanSteps` | цена разметки ненаблюдаема |
| D7 | счётчик шагов `KernelHeap` + `LargestFreeBytes` | то же для ядерной кучи |

## Стадии

**0. Приборы и красные тесты.** Поведение не меняется. Отчёт: A1 FAIL,
A1b FAIL, A2 FAIL (`per≈8192`), A3 FAIL (`largest=256`), A4 FAIL.

**1. Склейка в подметании.** `GcSweep.Run` уже идёт по адресам вверх — копить
`runStart`/`runBytes`, при встрече живого или конце сегмента писать **один**
маркер. Не выходить за сегмент, не трогать `seg->Current`. Заодно линковать
прямо здесь и убрать `RebuildFreelist` — это второй полный обход кучи на каждую
сборку. → A1, A1b, A3 зелёные; A2 красный **по построению** (блоки не соседние).

**2. Классы размеров.** Головы вёдер — `StructLayout(Size=14*8)` в `.bss` +
`fixed`, **не** `static readonly nint[]`. Индекс = log2, от 32 Б до ≥256 КБ.
Ведро `bucket(size)+1` и выше — голова подходит по построению, O(1).
Сохранить правило: остаток ≥16 всегда walkable-маркер, в список только ≥32
(фикс step131, трогать нельзя). → A2 зелёный.

**3. Контекст аллокации.** `s_allocPtr`/`s_allocLimit`, refill 8-32 КБ.
**Обязательная часть, не опция:** неиспользованный хвост обязан стать
walkable-маркером **до любого обхода кучи** — иначе `GcSweep.Run` встретит нули,
сделает `break` и молча бросит остаток сегмента. Тихая утечка, невидимая.
Нужен `RetireContext()` в начале `GcSweep.Run`, `RebuildFreelist`,
`AppHeapCensus.Walk`, `GcHeapCensus.Dump` и точного ходока.
Контекст на поток пока невозможен — `ThreadStatic` не работает.

**4. `FindSegmentContaining` за O(1).** `s_heapLow`/`s_heapHigh`, отсечка
диапазоном. → A4 зелёный.

## Риски

Ловушка `ClassConstructorRunner`; ходибельность кучи (слитый маркер обязан
давать `ComputeSize() == сумме`); не сливать через границу сегмента; остаток
<32 Б оставить как есть (иначе возвращается корраптор step131); `[oom]`-строка
не должна начать аллоцировать при выносе в `GetFreeStats`.

# Фронт 3 — исключения и трассы

## Поправки к вчерашнему аудиту

**Причина схода обхода названа точно, и фикс — одна строка.**
`Scheduler.cs:150-171` пишет `slot[0..7]=0` и `slot[8]=ThreadStartThunk`, а
**`slot[9]` не пишет никто**. После `ret` размотчик читает оттуда мусор.
Проверка `nextIP == 0` (`StackFrameIterator.cs:237-241`) существует и **не
может сработать**, потому что слот не обнулён. Это причина четырёх
неканонических адресов в каждой сборке на обеих машинах.

**Новое: кадр фанклета разматывается кодами родителя.**
`StackFrameIteratorOps.Next` берёт `info.RootRuntimeFunction->UnwindInfoAddress`;
сток берёт **текущую** запись (`CoffNativeCodeManager.cpp:535,630`). Бросок из
`catch` — обычное дело, и он даёт молча неверный SP.

**Буфер трассы недостижим для обоих сборщиков.** Массив кадров выделяет
**ядерный** код из **ядерной** кучи, объект исключения PE-приложения лежит в
**куче приложения**. Метка приложения чужой адрес пропускает, у ядра на него нет
корней. Ядерное подметание освободит, приложение продолжит ссылаться. Это не
«неудобная аллокация», а латентный use-after-free, и он проверяем.

## Имена: оценка упала дважды

Агент разобрал блобы офлайн, не по документации. В `BOOTX64.EFI`:
`313 EmbeddedMetadata` — **63 378 Б**, `327 RvaToToken` — **27 384 Б**.
Блоб 327 разобран целиком: **2761 запись**, декодер дошёл ровно до границы —
формат подтверждён. Достаны реальные имена (`RethrowSource` → rva `0xCA72E0`),
пройдена цепочка типов до `OS.Kernel.Diagnostics.NativeAotProbe`.

`DecodeUnsigned` у нас **уже есть** — `NativeFormatDecoder.cs`, 73 строки,
бит-в-бит как у апстрима.

**Ловушка порта:** *типизированные* хэндлы (`ConstantStringValueHandle`) хранят
голое смещение, *нетипизированные* `Handle` — `тип | смещение<<8`. Перепутать =
читать мусор и решить, что формат другой.

Итог: **~150 строк своего кода**, а не 854 апстримных и не
`Internal.Metadata.NativeFormat` (11 880 строк, не нужен вовсе).

## Тесты

Ядро — `EhProbe.cs`, нужен репорт с вердиктом по форме
`NativeAotProbe.ReportProbe`, иначе `probe_report.ps1` не отличит OK от FAIL.

| тест | утверждает | почему красный |
|---|---|---|
| **T-K1** текст есть | `StackTrace.Length > 32`, есть `"\n   at "` | литерал `"[trace]"`, 7 символов |
| **T-K2** имя метода | `Contains("HelperLevel3_17")` | то же; имя физически лежит в блобе 313 |
| **T-K3** глубже 16 | `GetStackIPs().Length >= 40` | `StackTraceCapacity = 16` |
| **T-K3b** маркер обрыва | текст кончается `"... N more frames"` | маркера нет; `MaxFrames=100` — второй потолок, его обрыв тоже надо назвать |
| **T-K4** rethrow дописывает | `n2 > n1` по числу кадров | при `isRethrow` `traceTarget` null; проверять **прирост**, а не сохранение — исходные кадры и так сохраняются |
| **T-K5** трасса аппаратного отказа | ≥3 кадра, первый — виновник | текста нет; «первый кадр — виновник, а не мост» никем не утверждается |
| **T-K6** обход встаёт на дне | `LastSkippedCount == 0` | `slot[9]` не обнулён; телеметрия **уже есть** |
| **T-K7** фанклет по своим кодам | все кадры разрешаются в `.pdata` | тест-детектор: если зелёный — тоже результат |
| **T-K8** шаг через переходник | `Next` вернул true | `TryUnwindServiceThunk` подключён только к GC |

Приложения: **T-A1** текст, **T-A2** имя метода приложения, **T-A3** глубже 16,
**T-A4** буфер в куче приложения (`FindSegmentContaining(addr) != null`),
**T-A5** непойманное из приложения доходит до ядра (лог-тест, фатальный,
отдельным тумблером, по умолчанию off).

Существующая проба `rethrow preserves stack trace` **не может пройти никогда**:
ищет имя в строке `"[trace]"`. Имя оставить, тело заменить и разделить на две —
счётную (зеленеет на стадии 3) и именную (на стадии N1).

Каждая новая проба — строка в `tools/probe_report.ps1`, иначе приедет как
`UNKNOWN` и батарея её не заметит.

## Стадии

1. **Форматтер** — текст из записанных адресов, `   at 0x<hex>` с местом под
   имя. Логику «адрес → свой образ» вынести из `UnhandledExceptionReport`, чтобы
   отчёт и геттер не разъехались. → T-K1, T-A1.
2. **Потолок 64 + маркер**, и здесь же **владение буфером**: наполнять
   `ReserveStackTrace()` из конструкторов `Exception`, тогда массив выделяет тот
   образ, что создаёт исключение. Снимает use-after-free и аллокацию на пути
   аппаратного отказа. → T-K3, T-K3b, T-A3, T-A4.
3. **Append при rethrow** — дать `traceTarget` и для rethrow, `NotifyFirstChance`
   не трогать. → T-K4 (счётная половина).
4. **Переходники служб в EH-обходе** — как в `KernelGcPreciseWalk`, но итератор
   держит SP в `RegDisplay`, нужна обёртка, не копия. → T-K8.
5. **Дно потока**: `slot[9] = 0` (взять `stackTop - 80`, выровнять вниз), плюс
   страховка «новый SP в пределах стека потока», плюс дно `JumpStub` как
   терминатор. → T-K6, T-A5.
6. **Громкие провалы регистрации** — пять `return` в
   `PeLoader.TryRegisterExceptionTable` и `RegisterImage == -1`.
7. **`Next()` по текущей записи, а не корневой.** → T-K7. Дёшево, и без него
   недостоверна любая трасса, прошедшая через `catch`.
- **N1** имя метода (~80 строк), **N2** тип и namespace (~70), **N3** ярус
  приложений (своя таблица у образа + служба `SymbolizeAddress` в хвосте ABI).

Стадии 1-3 независимы от 4-6.

## Hosted: сперва замер

`coreclr-hosted-limits.md` §12 сам говорит, что после починки FH3 (step172)
LIMIT-12.1 **не перепроверялся**, а пробы в `normal-hello` содержимое
`StackTrace` сознательно не трогают. Значит «пусто» может быть неправдой
годичной давности.

Замер: печатать `e.StackTrace` **дословно** для трёх случаев — управляемый
бросок, `throw;`, EE-internal (`new int[int.MaxValue]`). Проба ничего не
утверждает, она печатает. Одна строка лога решает, есть ли там фронт вообще.
Попутно выключить безусловные `[seh-step]`/`[seh-pers]` — в замере это шум, и
заодно закрывается враньё комментария `SehDispatch.cs:33-40`.

**Оставшиеся два обрыва обхода названы.** `WaitHandle_WaitOneCore + 0x64` —
потоки яруса CoreCLR, припаркованные в ожидании; размотка их нативного кадра
отдаёт неканонический адрес. Это то же самое, что `slot[9]`, но для стартового
пути hosted-потоков, и оно сцеплено с проверкой диапазона в `CoffMethodGcInfo`:
у нативного кадра указатель на `GcInfo` мусорный, а ходок разбирает мусор как
таблицу живых слотов. Сначала третий ответ ходока («корней нет, разматывай
дальше»), потом проверка диапазона, потом дно hosted-потока.

**Замер hosted дал не то, что ожидалось.** `StackTrace` там `null` — не пустая
строка, и не только для EE-internal, а для обычного управляемого `throw` тоже.
В CoreCLR геттер отдаёт null ровно когда не записано ни одного кадра, то есть
наш первый проход не приводит в движение `StackTraceInfo` рантайма вообще.
Задача на этом ярусе не «дополнить трассу», а «включить запись кадров», и она
не имеет ничего общего с форматтером. Подробности — `coreclr-hosted-limits.md`
LIMIT-12.1, переписанный по замеру.

**Калибровка APIC: диагноз исправлен.** Первая версия этого пункта предлагала
брать минимум из N окон, как делает Linux. Для нашего случая это **неверно и
опасно**. Три прогона одного образа дали калибровку 7877 / 7849 / 7843 кГц —
одно и то же с точностью 0.4 % — при доставке 9, 67 и 8 тиков за 100 мс. Счёт
взводится одинаково, значит часы взведены верно, а теряется **доставка**: под
TCG QEMU роняет периодические прерывания, когда vCPU не поспевает. Минимум из
окон — самое потерянное окно, то есть худший возможный множитель; коррекция по
нему укорачивает счёт, тиков просят больше, доставляется меньшая доля. Эта
спираль уже случалась — 47 тысяч прерываний в секунду в step173, — и
`RetuneToDeliveredRate` отказывается от поправки именно поэтому. Отказ был
правильным.

Починена **проба**, а не арифметика: `ApicTick` меряет три окна и называет
причину. `PASS` — частота примерно та. `FAIL` — не та, и все окна согласны
насколько: устойчивый множитель означает неверно взведённый счёт, это наше.
`HOST-LOSS` — не та, и окна расходятся: хост не доставил, и это не дефект
здесь. Признак тот же, что у подстройки (четверть разброса), намеренно: проба
должна краснеть ровно тогда, когда подстройка попыталась бы починить и не
вышло.

`CPUID 0x40000010` остаётся в бэклоге, но ценность его ниже, чем казалось:
чинил бы он калибровку, а она воспроизводима до половины процента.
