# Прерывания и вытеснение — оценка готовности (Phase F)

Разбор состояния перед началом работ: что есть, что сломается, в каком порядке
двигаться.

**Статус (step155):** F1, F2 и F3 сделаны и проверены; оба вскрытых дефекта
закрыты. Вытеснение работает, но включается только вокруг проб — глобально оно
всё ещё обесценило бы предположения из §3. F4 (SMP) — следующий. Разделы ниже
оставлены как есть, включая описание того, чего не было: они объясняют, почему
порядок работ именно такой.

**Про остановку мира.** §6 ставил её главным открытым вопросом и перечислял
безопасные точки, IPI и гибрид. На одном ядре ничего этого не понадобилось:
исполняется ровно один поток, все прочие уже припаркованы со стабильным
контекстом, и «остановить мир» означает лишь не дать вытеснить сборщика. Выбор
из §6 остаётся актуальным для SMP.

Продолжает `docs/threading-architecture.md` (Phase E), где вытеснение, SMP и
приостановка для сборки мусора вынесены в §14 «out of scope → Phase F».

## 1. Что уже есть

**Ловушки процессора.** `OS/src/Hal/Idt/` — своя таблица, 32 вектора
исключений через шеллкод-трамплины в управляемый диспетчер. Полный слепок
регистров в `InterruptFrame` (включая CR2), выровненный вызов по Win64.

**Возврат из прерывания — есть и работает.** `X64Asm.TryResumeFrame`
восстанавливает регистры из кадра и делает `iretq`. Сегодня им пользуется
отложенное отображение страниц: `#PF` внутри окна → страница подкладывается →
возврат на ту же инструкцию. **Это ключевой актив:** переключение контекста при
вытеснении — это правка `Rip`/`Rsp` в кадре перед возвратом, а не новый
механизм.

**Компиляция шеллкода на этапе сборки.** `BootAsm.Generator` + Iced. Трамплины
для векторов ≥32 пишутся тем же способом, что и существующие.

**Планировщик.** `OS/src/Kernel/Threading/` — кооперативный round-robin,
`ContextBlock` (RSP + 512 байт FXSAVE), переключение шеллкодом, per-thread
стеки, границы стека, очередь дедлайнов, события, семафоры, мьютексы,
`SpinYieldLock`. Всё написано, всё работает — не хватает только того, кто
отберёт процессор без спроса.

**Точный разбор gcInfo** (step110) — предусловие безопасных точек. Умеем по
адресу возврата找 живые слоты. Без этого разговор о вытеснении не начинался бы.

**MADT разобран** — адрес локального APIC, число APIC'ов, число IO-APIC.

## 2. Чего нет

**Своих аппаратных прерываний нет вообще.** `Idt.cs` владеет векторами 0..31;
векторы 32..255 **копируются из таблицы UEFI дословно**, IRQ обслуживает
прошивка. Ни локального APIC, ни IO-APIC, ни отправки EOI, ни таймерного
вектора. Все драйверы опрашивают устройства в цикле.

**Общий стаб не умеет возвращаться.** После вызова диспетчера стоит `hlt` —
возврат идёт только через отдельный `TryResumeFrame`. Для IRQ нужен путь
«сохранил → обработал → восстановил → `iretq`» как штатный, а не как аварийный.

**Сборщик мусора видит один стек.** `GcRoots` хранит **один** `s_stackTop`;
корни ищутся только на текущем стеке. Стеки других потоков не сканируются
никогда.

**Остановки мира нет.** Ни протокола приостановки, ни безопасных точек.
`threading-architecture.md` §8 фиксирует это прямо: Phase E живёт на Zero-GC
именно потому, что приостановки нет.

**Куча не заблокирована.** `KernelHeap.Alloc/Free` без замка сознательно
(`KernelHeap.cs:42`): кооперативность гарантирует отсутствие окна. Наивная
обёртка `SpinYieldLock` уже пробовалась (step95) и сломалась — путь
журналирования сам аллоцирует, получается рекурсивный захват.

## 3. Зона поражения — что именно сломается

Кооперативность сегодня не «режим планировщика», а **несущее предположение**,
на которое явно опираются как минимум:

| Место | На что опирается |
|---|---|
| `KernelHeap` | нет окна между проверкой и захватом блока |
| `ProcessTable`, `Event`, `AddressWait` | «замки не нужны, исполнитель один» |
| `TimerQueue` | очередь трогается только внутри `Yield`/`Sleep` |
| Драйверы (USB, AHCI, PS/2) | циклы опроса никто не прерывает |
| Патчеры шеллкода | никто не исполняет патчируемый код в момент правки |
| Сборщик мусора | пометка идёт на единственном живом стеке |
| CoreCLR | ведёт **собственную** приостановку потоков для своего GC |

Каждая строка — это не «надо добавить замок», а «надо решить, что делать»:
замок в пути журналирования даёт рекурсию, замок в драйвере — задержку в
обработчике.

**Регрессионная поверхность — всё зелёное сразу.** PowerShell, DOOM, оба
эмулятора, батарея 29/29, перепись. Это единственная из обсуждавшихся работ,
которая способна сломать уже сделанное. Гейт и прогон батареи на каждом шаге
обязательны (`tools/probe_report.ps1`).

## 4. Два дефекта, вскрытых этим разбором

Оба существуют **уже сейчас**, независимо от вытеснения.

**(а) `STI` после снятия UEFI, при чужой таблице прерываний.**
`ExitBootServicesProbe` делает `CLI` сразу после выхода — правильно, потому что
хвост таблицы принадлежит прошивке. Но `HwFaultBridge.DispatchTrap` делает
`X64Asm.Sti()` перед передачей в управляемый диспетчер (нужно, чтобы `catch`
исполнялся с разрешёнными прерываниями). То есть **любое аппаратное исключение
после EBS снова разрешает прерывания**, а обработчики остались прошивочные, и
контроллер прерываний мы не маскировали — маскирования PIC в дереве нет вовсе.
Дальше достаточно нажатия клавиши (IRQ1), чтобы уйти в код прошивки в мире, где
прошивки уже нет.

Почему не выстрелило: post-EBS исключения редки, а `TryResumeFrame`
(отложенные страницы) восстанавливает `RFLAGS` из кадра и `STI` не делает.

**(б) Корни на стеках спящих потоков не сканируются.** Кооперативные потоки
существуют с step94, объекты на их стеках сборщику не видны. Сегодня спасает то,
что многопоточные сценарии и сборка почти не пересекаются — но это везение, а не
свойство.

Оба закрыты в step154, каждый со своей пробой: `[fpfault]` и `[gcroots]`.
Первый — сохранением состояния FPU в кадре прерывания плюс маскированием
контроллера, второй — реестром потоков и обходом с сохранённого контекста.

## 5. Порядок работ

Три куска, разные по риску. Сливать нельзя.

**F1. Забрать себе путь прерываний. — СДЕЛАНО (step154).**
Локальный APIC, маскирование PIC, свой таймерный вектор, EOI, трамплин с
честным возвратом. Никакого вытеснения. Критерий: наш тик считается вверх,
батарея зелёная, дефект (а) закрыт.

**F2. Корни всех потоков. — СДЕЛАНО (step154).**
Обход стеков спящих потоков по их `ContextBlock`. Критерий: объект, живущий
только на стеке спящего потока, переживает сборку. Закрывает дефект (б) и
является предусловием F3.

**F3. Вытеснение на одном ядре. — СДЕЛАНО (step155).**
Обработчик тика зовёт `Scheduler.Yield()` — переиспользует кооперативную
машинерию целиком, второго представления приостановленного потока не появляется.
Остановка мира = подавление вытеснения на время сборки; критические участки
(куча ядра, управляемая куча) закрыты тем же счётчиком, а не замком — замок
здесь входит в себя через путь журналирования (step95).
Пробы: `[preempt]`, `[preempt-alloc]`.

**F4. SMP — отдельно и позже.** Умножает каждый инвариант на число ядер.

## 6. Решения, которые придётся принять

- **Приостановка для сборки:** опрос безопасных точек (нужна вставка опроса на
  обратных дугах — у нас нет своего кодогенератора для AOT-кода) против
  перехвата адреса возврата против IPI. Точный gcInfo есть, значит перехват
  реалистичен.
- **CoreCLR на hosted-ярусе** ведёт свою приостановку. Либо вытеснение не
  трогает его потоки, либо два механизма надо мирить.
- **Драйверы:** оставлять опрос или переводить на прерывания. Опрос под
  вытеснением становится дороже, но безопаснее.
- **Замок кучи** с учётом рекурсии через журналирование (счётчик глубины).
