# Фронты — есть следующее действие

## Обход стека сборщиком ядра не проходит сквозь BigStack

Hosted-прогон (`CoreClrHost.TryExecute`) уходит на BigStack через шеллкод `BigStack.RunOn`, у которого нет данных размотки. Точный обход сборщика ядра останавливается на нём: управляемые объекты ядра, которые держат только кадры ниже (на собственном стеке потока), для него мусор.

step207: так `RunManagedApp` потерял строку пути, и после выхода NormalHello `[perf] run.<имя>` печатал чужую память. Строки держатся в статиках — заплатка на одно место.

Настоящее решение — размотка для шеллкода: запись в `.pdata` динамического диапазона или явный переход обходчика на сохранённый RSP вызывающего, как `ContinueBelowApps` для переходников служб. Проверка — сборка под `--gc-stress` во время hosted-прогона из приложения.

## Разборщики BCL

Что есть и чего нет — README, таблица «Стандартная библиотека». По пользе:

1. **Целые типы.** `int` и `long` — ручные `Parse(string)`/`TryParse`, дважды (`OS/src/Boot/MinimalRuntime.cs` и `apps_native/sdk/MinimalRuntime.cs`); у `uint`, `ulong`, `short`, `ushort`, `byte`, `sbyte`, `char` нет `Parse`. Порт `Number.Parsing` из dotnet/runtime со всеми перегрузками, как уже лежит для `double`/`float`/`decimal` в `Number/`; ручные копии снести.
2. **`Version.Parse`.**
3. **`Regex`** (`System.Text.RegularExpressions`). Самый большой и самый нужный: из-за него вырезаны `matches regex` и `extract()` в BabyKusto, а разбор `.env` (`Formats/Dotenv`) заменяет регулярки compose-go ручным сканированием. Сначала интерпретатор (`RegexInterpreter`), без компилятора и генератора исходников.
   Порт из `dotnet-runtime-sharpos`: 35 тыс. строк, без компиляторов
   (`RegexCompiler`, `LWCG`, `AssemblyCompiler` — Reflection.Emit; BCL и сам
   уходит в интерпретатор без динамического кода) и без `Symbolic`
   (NonBacktracking) — ≈19 тыс. С step212 в std есть `Hashtable`,
   `CharUnicodeInfo` с таблицами, `SearchValues<char>`, `IndexOfAnyInRange`,
   `string.Create`, `Lock`; не хватает `SearchValues<string>`, слабого
   `WeakReference<T>` (сейчас сильный), `Environment.TickCount64`.
   Второй потребитель — Okojo: восемь его внутренних образцов `[GeneratedRegex]`
   сейчас идут через его собственный движок ECMAScript (`vendor/Okojo/SharpOS/OkojoShims.cs`).
   Ещё потребитель — подсветка синтаксиса для редактора: все готовые движки на
   регулярках. Кандидат — подсветка AvaloniaEdit (`.xshd`, построчно с
   состоянием, MIT), уже вынесенная под терминал в `tui-cs/Editor`; включается
   в `TextView` v1 через `SetNormalColor(line, idx)`, как в
   `UICatalog/Scenarios/SyntaxHighlighting.cs`. Загрузчик `.xshd` хочет
   `XmlReader` — у нас TurboXml.
4. Позже: `Enum.Parse` по имени (нужны метаданные перечислений; числом есть), `IPAddress`, `System.Collections.Frozen` (у Okojo заглушки), `Encoder`/`Decoder` в `Encoding` (у Lua вырезы); XML в std (сейчас TurboXml только в ядре, для манифестов).

## Expando ↔ тип по описанию

Тип теряется (становится Expando) на `extend` нового столбца, `project`
подмножества или в другом порядке, `summarize`; из JSON и CBOR получаются
только Expando. Тождественный `project` тип сохраняет (step208). Нужны
обратные шаги — программами, не операторами KQL: грамматика — у
Kusto.Language (правка чужого парсера), `evaluate` в BabyKusto нет.

- `CONVERT --to expando` — любые сообщения в Expando, вложенные — во вложенные.
- `CONVERT --to type 'Ghost(Level:int, Weight:real, Name:string)'` — Expando
  в тип по описанию. Синтаксис — **схема таблицы KQL** (как в `datatable`):
  парсер уже есть (`new TableSymbol(name, "(…)")` в Kusto.Language), но
  CONVERT его не линкует. Типы только KQL: нет `float`/`short`/`byte`/`char`,
  перечислений, вложенных типов (`dynamic` → вложенный Expando).
- `--like file.pipe` — описание из готового externalpipe-файла, без синтаксиса.
- Блоки по описанию пишет SYNTH (тип, которого нет ни в одной программе);
  значения — по правилам `Into<T>` (сужение с проверкой, разбор строк), не
  подходит — отказ, код 1.
- Потом: `KQL --as 'Тип(…)' 'запрос'` — результат сразу в этот тип.
- Если понадобятся вложенность, перечисления, точные ширины — **Protocol
  Buffers** (`.proto`), парсер protobuf-net.Reflection (Apache-2.0). Другие
  системы описания (JSON Schema, Avro, CDDL, Thrift/Cap'n Proto/FlatBuffers)
  — тяжелее или без зрелого парсера на C#. Своего синтаксиса не изобретать.

Хвосты GVM (`GenericVirtualMethods.cs`, step198), каждый — исключением при
встрече: вариантная интерфейсная диспетчеризация; unboxing-заглушки для
структур-получателей; конструктор по умолчанию в словаре (нужна карта
конструкторов); типы, которых нет в образе (типы во время выполнения не
строятся). Кэш — словарь под замком на каждый вызов: если GVM окажется
горячим, — кэш без замка, как `TypeLoaderExports` в CoreLib.

## Труба к экрану: обобщение

С step218 между писателями и движком терминала — очередь байт
(`TerminalConsole`): запись кладёт, движок получает её целиком в конце записи,
рисует насос ввода раз в 10 мс или читатель, ждущий клавишу. Четыре правила
«когда рисовать» сняты. Осталось:

- **Тип в std и подписчики.** `OutputRouting` — жёсткие наборы стоков по
  каналу; станет списком подписчиков трубы: экран, COM1, журнал, панели.
- **Кадр из нескольких записей.** SDK режет запись на куски по 4 КиБ; если
  насос придёт между кусками, кадр нарисуется наполовину и через интервал
  дорисуется. Лекарство — режим синхронного вывода (`CSI ? 2026 h/l`) в
  движке или конец кадра в SDK; браться, если мелькание заметят.
- **Противодавление.** Полная очередь (64 КиБ) — писатель сам кормит движок;
  блокировать писателя некому, пока нет потока экрана.
- **Строки ядра** пишутся по символу и в журнале на диске перемешиваются
  посреди строки (`[proc] generation [proc] generation 527 …`): очередь ядра
  не касается журнала.

## Каналы вывода программы: stdout объектами, stdtext, подсказки

Половина находок трёх тестеров (`work/ostest/`) — одна неясность: куда программа
пишет и кто это рисует. `Console.WriteLine` пишет на экран мимо stdout,
`Pipe.Write<T>` сам решает «экран или труба», диагностика и строки ядра
печатаются на тот же экран одновременно с результатом. Модель (обсуждено
2026-10-25):

- **Ядро знает только таблицу концов процесса:** номер → труба, файл,
  терминал; наследуется при запуске. Смысла номеров не знает.
- **stdout (1) — объектная труба по умолчанию у всех.** `Console.WriteLine`,
  `Console.Out`, `OpenStandardOutput` — она же: строки идут сообщениями
  `string`, байты — `byte[]`. Чужая программа пишет туда без правок.
- **stdin (0)** — та же труба; `Console.ReadLine` получает объект его строкой.
- **stderr (2)** — диагностика, напрямую на терминал.
- **stdtext** — дополнительный канал наших программ для явного текста
  человеку (`Std.Text.WriteLine`): панель FETCH, отчёт тестов, сводка PIPESPY.
  Чужие программы его не трогают. Перенаправляется как любой; по умолчанию его
  забирает оболочка и печатает.
- **Подсказки — в описании трубы**, рядом со схемой: писатель объявляет их при
  открытии, до первого сообщения. У stdout — «не для терминала» (FETCH), у
  stdtext — свои. Едут с данными: externalpipe хранит их в заголовке.
- **Оболочка по умолчанию выводит и stdout последней стадии, и stdtext;**
  подсказки убирают лишнее, явное «выводи всё» их перекрывает.
- **Полноэкранные программы** (LESS, лаунчер, USBTEST, приглашение KQL) рисуют
  на терминал напрямую.
- **Ядро в консоль пользователя не пишет** — только в свой журнал.

Закрывает: пустые `proctest > f`, `pipecnt > f`, `proctest | less`; вывод
встроенных команд мимо трубы в `shell | pipecnt`; обрезанные и пропавшие строки
нескольких стадий; `[proc] …`, `---- X.EXE end ----` посреди вывода;
невидимое приглашение интерактивного KQL.

Сделано: `Console` → stdout, stdtext, концы с номерами (step212); подсказки
у писателя, строки ядра вне сессии пользователя, FETCH с SYSINFO, вход
оболочки каждой команде (step216). Осталось:

1. **Подсказки — в транспорт.** Сейчас их соблюдает сам писатель
   (`Pipe.Write<T>(PipeHints)`, `Pipe.TextHints`): экран рисует программа.
   Когда читателем экрана станет оболочка (панели, п. 3), подсказки едут в
   описании трубы, externalpipe хранит их в заголовке.
2. **`1>&2`** — у 2 без перенаправления нет конца, это консоль ядра. Конец
   «экран ошибок» даёт труба к экрану (раздел выше).
3. **Терминал на две панели и прокрутка.** Панели делятся по роли, не по
   каналу — каналы в ленте не разводятся, иначе пропадает порядок вывода:
   - слева — хронология всего, как сейчас: stdout, stdtext, stderr,
     приглашение, ввод; объект — одной строкой (`ToScreenString`) или сводкой
     `▸ 1000 × Ghost.Rusupv`; «не для терминала» — объекты в ленту не печатаются;
   - справа — инспектор объектов последней команды: дерево для разнотипных,
     таблица по схеме для однотипных, раскрытие полей; строка-сводка слева
     выбирает, что показать справа;
   - сама панель не разворачивается, пока приходят только строки и байты;
     разворачивается, когда приходит объект другого типа или stdtext;
   - своя прокрутка у каждой (Shift+PgUp/PgDn, Tab — переключение);
   - полноэкранная программа — весь экран, без панели; последовательный
     терминал стенда — плоский вид;
   - программе — размер её панели; смена размера — событие (раздел «Ввод
     программы»).

Проверка: обычное консольное .NET-приложение собрано под std без правок —
`pipegen 5 | hello | kql "take 1"`, `hello > f`, `hello 2> err`.

Тесты пишут отчёт в stdout (`Console`), не в stdtext: перевод ломает проверки
DATATEST, читающие stdout детей, а пользы пока нет — `proctest | less` и так
работает. Вернуться, когда оболочка станет читателем экрана.

## Ввод программы — байты терминала: что осталось

С step217 `Console.ReadKey`/`KeyAvailable`/`CursorLeft` читают байты терминала
(служба `TerminalRead`, разбор в SDK `TerminalKeys`), ответы XtermSharp идут
туда же. Осталось:

- **Владелец терминала.** Байты берёт тот, кто читает; программа переднего
  плана — нет такого понятия. С панелями (у каждой свой ввод) понадобится:
  ядро отдаёт ввод программе, которой терминал передан, остальным — ничего.
- **Ctrl+C останавливает программу** — сигнал от ядра владельцу терминала;
  сейчас 0x03 — просто байт (см. «Долги шага 197»).
- **Лаунчер на байтах.** Terminal.Gui читает сырые события (`TryReadKey`, с
  отпусканием). Перевод — карта `ConsoleKeyInfo → KeyEvent`, как у стокового
  `NetDriver`; отпускания модификаторов ему тогда не нужны.
- **Смена размера — событие** (`SIGWINCH`); размер остаётся службой
  `ConsoleSize`.
- **Раскладки.** Декодер скан-кодов — только US; кириллица с клавиатуры не
  набирается (UTF-8 во вводе уже проходит).
- **hosted-ярус** (`ConsolePal.Unix`) по-прежнему читает клавиши своим путём.

## Вытеснение управляемого кода (CoreCLR)

Механизм есть: активация потока (`ThreadActivation.cs` плюс переходники в форке),
доставка с таймерного тика, обработчик исполняется на стеке прерванного потока с
полным кадром регистров. Замер `act=2/1/15` (запрошено/доставлено/точка
небезопасна).

**Гейт `Probes.PreemptHostedSession` сейчас включён**, то есть вытеснение живо
внутри сеанса CoreCLR и выключается за ним (`Preemption.Disable()`,
`ExitBootServicesProbe.cs:321`). Это и есть источник неочевидного класса отказов:
критическая секция, прерванная внутри окна, остаётся прерванной **после** него —
возобновить поток нечем до первой добровольной уступки. Так пропал первый кадр
лаунчера (step184). Каждый такой случай надо искать не как гонку, а как
подвешенное состояние с длинным сроком жизни.

**Включить вытеснение везде всё равно нельзя.** Это фронт, а не переключатель:
каждое исправление вскрывает следующее предположение о порядке, видимое только
после починки предыдущего. Уже выпали:

1. консоль не переносит повторного входа (падение внутри `WriteConsole`);
2. у `Semaphore.WaitUntil` щель между проверкой счётчика и постановкой в
   очередь — потерянное пробуждение, все потоки блокируются навсегда;
3. права на страницы JIT выставляются пачкой, которая раньше гарантированно
   успевала завершиться до прыжка в этот код (отказ выборки инструкции на
   NX-странице);
4. к критической секции ведут два пути, и защищён только один — достаточно
   одного незащищённого входа, чтобы флаг остался висеть (step184).

**Что вытеснение даёт и чего не даёт.** Оно не ускорит старт — работы меньше не
станет. Оно уберёт залипание ввода во время компиляции. Без него ту же роль
частично играет настоящий простой: ждущие потоки не забирают процессор у
работающего.

## FAT32: что осталось

Пишем FAT32 целиком (step197, step208): создание, удаление, каталоги,
переименование и перенос, рост каталога, запись в любое место, `SetLength`,
имена в UTF-8 и регистр 8.3, FSInfo, сброс кэша устройства, кэш одиночных
секторов. Каждый прогон `run_build.ps1` проверяет том снаружи (`fsck.fat`,
`last_fsck.log`), DATATEST 22 — мясорубка из 600 смешанных операций.

- **Журнал загрузки фиксированного размера.** Файл выделяется заранее и пишется
  секторами, размер в записи каталога не меняется: `cat bootlog.txt` печатает
  ~16 M пробелов и выглядит зависанием. Обновлять размер по мере записи.
- **Цена сброса на флешке.** Сброс идёт после каждого закрытого файла и каждой
  правки каталога (за прогон батареи — 2 200). Под QEMU с `cache=unsafe` бесплатно;
  на стенде замерить, при нужде — сбрасывать реже (по времени, при выключении).
- **Кэш данных и отложенная запись.** Кэш — только одиночные секторы
  (каталоги, FAT), запись сквозная. Данные идут мимо. Отложенная запись требует
  порядка записи и точек сброса, иначе после сбоя том в состоянии, которого не
  должно существовать.
- **Чего нет:** атрибутов (только чтение, скрытый), времени создания и доступа
  при записи, записи на FAT12/16, нескольких томов. `FileStream` только на
  чтение грузит файл целиком; `EnumerateFiles` не ленивый. Каталог после
  удалений не сжимается.
- **Том FAT16 — запись отказывает «отказом диска».** Отчёт тестера (2026-10-26):
  образ `mkfs.vfat -F 16` (и `fat:rw:` QEMU — тоже FAT16). Все пути записи
  (`Fat32Create`, `Fat32Files`, `Fat32Remove`) молча отказывают при
  `!s_isFat32`, и наверх приходит `DeviceError` (статус 7): `echo > f`,
  `mkdir`, `bootlog` «create failed». `df` молчит — FSInfo есть только у FAT32.
  После неудачной перезаписи файл перестаёт читаться — вероятно `Locate`
  (`Fat32.Lock.cs`), который на FAT16 отвечает «нет файла». Сделать: монтировать
  FAT16 только для чтения с честным отказом, `df` по таблице FAT, разобрать
  чтение после отказа; позже — запись на FAT16 (16-битные элементы, корень
  фиксированного размера).- **PowerShell (PAL)** — см. «Долги шага 197».

## xHCI: устройство на контроллере 4:0.0 ноутбука не адресуется

На ноутбуке каждая загрузка: контроллер `1022:1505` (один порт), на порту 0
High-Speed USB2-устройство, сброс порта и Enable Slot проходят, `Address Device`
— код 4 (USB Transaction Error): устройство на `SET_ADDRESS` не ответило вовсе.
Что за устройство — неизвестно, до дескриптора не доходит. Скорее всего
встроенная камера.

Команда собрана по спецификации (`XhciDevice.TryAddressDevice`). Отличия от
Linux и Windows — в том, что перед ней:

- **нет паузы восстановления после сброса.** `UsbProbe` после `PRC` сразу
  включает слот и адресует. USB 2.0 §7.1.7.5 (TRSTRCY) даёт устройству 10 мс;
  Linux ждёт 10 + 40. Встроенные камеры и сканеры отпечатков без паузы
  молчат — ровно этот симптом;
- **нет повтора**: Linux при неудаче сбрасывает порт и адресует ещё раз;
- **нет «нового порядка»**: Windows и Linux сначала включают слот без
  `SET_ADDRESS` (BSR=1), читают 64 байта дескриптора и только потом адресуют.

**Следующее действие:** один прогон на ноутбуке с паузой ~50 мс после сброса
и одним повтором. `addr=OK` — корень пауза; нет — пробовать BSR=1. Параллельно:
в Windows, «Диспетчер устройств → Устройства по подключению», что висит под
`VEN_1022&DEV_1505`.

Рядом, без связи: Bluetooth Realtek (3:0.3, порт 1) — `functions=none
(stage=5 lastCode=0x6)`, Stall при настройке. Класс не поддерживается.

## Стенд: чего не хватает прогону без рук

Сам прогон без рук работает; эксплуатация, ловушки и скрипты —
[docs/test-rig.md](docs/test-rig.md). Не хватает четырёх вещей, и три из них —
работа в SharpOS.

- **Сторож на тике**: «N секунд без прогресса → сброс», и паника в этом режиме
  тоже сброс. В дереве сторожа нет вообще (в `OS/src` только чужой
  `SetWatchdogTimer` в таблице UEFI), поэтому зависание держит стенд до руки —
  единственное, что ещё требует человека.
- **Сторож чипсета AMD** — на случай зависания с выключенными прерываниями,
  куда тиковый не дотянется. Проверить, не заблокирован ли прошивкой.
- **Клавиатура для прошивки**: ввод в сам SharpOS решён по CDC
  (`SerialInput` → `UsbCdcAcm`), но до загрузки его нет — в Setup прошивки
  клавиши по-прежнему недоступны. Наш HID-драйвер готов, мешает гаджет: он
  объявляет функцию с подклассом 0 и 4-байтной точкой, а `f_hid` запоминает
  значения при создании. Нужно только для того, чтобы менять настройки прошивки
  без рук.
- **xHCI Debug Capability (DbC)**: порт USB 3 ноутбука как устройство, кабель
  USB 3.0 A–A без VBUS. Заменяет и COM-порт, и запись лога на флешку, и даёт
  приём сборки прямо в SharpOS. Первый шаг — напечатать расширенные
  возможности xHCI на ноутбуке и ПК: есть ли DbC вообще.

## Асинхронный ввод-вывод и сеть

Цель и критерии этапов — `plan.md`, «Текущее направление». Здесь — как.

**Где мы сейчас.** Этапы 1–2 под QEMU сделаны (step210, limits §16): AHCI и xHCI
на MSI/MSI-X, драйвер спит до прерывания (`IrqWait`), команды разделяет замок.
Остальное синхронно: служба `FileRead` → FAT32 под одной блокировкой на всю
систему (`Fat32.Lock.cs`) → `CachedDisk` → драйвер, одна команда в полёте.
`Iocp`/`IocpBridge` — LIFO-семафор для пула потоков CoreCLR, а не порт
завершения. PAL `ReadFile`/`WriteFile` синхронные. Сети нет. Проба
`Socket ctor (TCP)` выключена.

**Хвосты этапов 1–2.**
- Стенд: на железе MSI не проверены (AHCI ноутбука, xHCI двух контроллеров).
- Разбуженный драйвер ждёт ближайшего `Yield` или тика, если процессор занят:
  пробуждение из прерывания не вытесняет. Если окажется заметным — запрос
  вытеснения из `IrqWait.Post`.
- Блокировка FAT32 — `SpinYieldLock` с `Idle`: ждущий спит до прерывания, но
  просыпается на каждом, а не только на освобождении. Если станет узким
  местом — список ожидания.
- Замеры из плана, не сделанные: `PIPEPERF --ipc-threads` рядом с чтением;
  `[start]` для `KQL.EXE` с диска при выключенном `ProgramCache`.

**3. Очередь команд AHCI.** До 32 слотов, завершения по `PxCI`/`PxSACT`; NCQ
(`READ/WRITE FPDMA QUEUED`), где поддерживается. Запрос драйвера: сектор,
число, буфер, событие завершения.

**4. Порт завершения ядра.**
- `CompletionPort`: очередь пакетов (ключ, байты, статус, адрес overlapped),
  привязка дескриптора, `Post`, `Get(timeout)`, `GetMany(n)`; пробуждение LIFO.
- Порт — ресурс процесса: уходит с процессом вместе с невзятыми пакетами.
- Тесты в AOTTESTS: post/get, таймаут, LIFO, много ждущих, конец процесса с
  ждущими и с полной очередью. `IocpBridge` — поверх нового порта.

**5. Асинхронные операции ФС.**
- Рабочие потоки ввода-вывода в ядре (2–4): `ReadAsync(handle, offset, buffer,
  key)` → синхронная операция FAT в работнике → пакет в порт. Асинхронность
  внутри FAT — позже, если понадобится.
- Службы в хвосте ABI (версия не меняется): чтение и запись по смещению,
  асинхронные чтение и запись, порт (`Create`, `Bind`, `Get`, `Post`).
- SDK/std: `FileStream.ReadAsync`/`WriteAsync`, `RandomAccess` поверх порта и
  нашего `async`/`await`.
- DATATEST: параллельные `ReadAsync`, закрытие посреди, ошибки диска, конец
  процесса с запросами в работе.

**6. CoreCLR: overlapped и порт.** PAL: `CreateFileW` с
`FILE_FLAG_OVERLAPPED`, `ReadFile`/`WriteFile` с `OVERLAPPED`,
`CreateIoCompletionPort`, `GetQueuedCompletionStatus(Ex)`,
`PostQueuedCompletionStatus`, `CancelIoEx`, `GetOverlappedResult`. Выяснить,
какие пути нынешней Unix-IL CoreLib дойдут до overlapped.

**7. Сеть — Windows IL одним комплектом.** Ни fake-epoll, ни своего
`SocketAsyncEngine`: путь IOCP в .NET зрелый, берём его целиком. Разреза нет:
только Windows-IL `Sockets.dll` упадёт на первом `ThreadPool.BindHandle` (его
нет в Unix-IL CoreLib), а Sockets вместе с CoreLib не найдут
`CreateIoCompletionPort` в PAL. Комплект:
- Windows-IL CoreLib, Sockets, Primitives — ветка в сборке форка;
- сторона IOCP у пула потоков: `OverlappedData`/`NativeOverlapped`,
  `BindHandle`, `UnsafeQueueNativeOverlapped`, `g_IOCompletionPort` и потоки
  завершений в CoreCLR;
- PAL ws2_32 (~25 функций, только ABI) поверх сокетов ядра на порту этапа 4.

Чего в комплекте нет:
- драйвер сетевой карты: в QEMU virtio-net или e1000 (с MSI); у ноутбука стенда
  RJ45 нет — USB-сеть CDC-NCM/ECM через наш USB-стек (телефон стенда умеет быть
  такой картой);
- стек TCP/IP, DHCP, DNS — взять готовый (MIT/BSD/Apache; кандидатов сравнить
  отдельно), не писать свой.

Порядок: кадры туда и обратно (ARP, ICMP) → UDP/TCP → сокеты ядра на порту →
ws2_32 PAL → Windows-IL Sockets → `HttpClient`. Попутно появляется весь
Windows-side async I/O: трубы, файлы, консоль.

**Зависимости.** 1 → 2 — главный выигрыш: машина перестаёт стоять, ABI не
меняется. 3 — после 2, от остального не зависит. 4 — до 5, 6, 7.

# Долги — ждут повода

Каждый проверен по дереву и никому сейчас не мешает. У каждого назван триггер:
момент, когда чинить станет дешевле, чем обходить.

## `SharpAppBootstrap` приложений не исполняется

В `link.rsp` два `/ENTRY`: `SharpAppBootstrap` (`FreestandingPe.props`) и
`SharpAppEntry` (`EntryPointSymbol`); побеждает последний. 32 бутстрапа и
`RuntimeImports.ManagedStartup()` в них — мёртвый код (step214). Триггер:
первое, что понадобится от `ManagedStartup` (module initializers, порядок
инициализации), — тогда выбрать одну точку входа и убрать вторую.

## XMM через `catch` — дыра есть, следствия нет

Факт в дереве: RyuJIT эмитит `UWOP_SAVE_XMM128` для xmm6+ в прологах, а наш
`ApplyCode` опкоды 8 и 9 распознаёт и **глотает** без эффекта
(`SehUnwind.cs:939-943`, комментарий прямо говорит «We don't restore XMM regs»).
`EmitCapture` не снимает FP/XMM/MxCsr, `EmitRestore` не грузит.

По этому описанию `double` в callee-saved XMM, удержанный через `throw`, после
`catch` должен быть мусором. Канарейка (`Probe_XmmAcrossThrow`,
`NativeAotProbe.cs:1391`) **зелёная**:

```
XMM regs preserved across throw [P0-1 canary]: ok val=21
XMM6+ doubles preserved across throw/catch     [OK]
```

Значит на нашем наборе кода JIT не оставляет эти значения только в xmm6+ через
броски — дыра не наблюдаема. Канарейку не снимать: она сторожит ровно тот день,
когда начнёт.

**Когда чинить:** если канарейка покраснеет, либо перед включением чего-либо,
что активно держит `double` в регистрах через EH. Объём — место в `Context`
(16-выровненное) плюс захват/восстановление плюс эффект у опкодов 8/9.
Риск при правке: layout `Context` читают по имени поля, но проверить grep'ом
magic-offset'ы (`0xF8`) обязательно.

## Свёрнутая размотка — диспозиция объявлена, не обработана

`ExceptionCollidedUnwind` (3) есть в `SehStructs.cs:173` и в комментарии
`CxxFrameHandler.cs:569` — и **больше нигде**: ни один проход диспетчера её не
разбирает. Проба при этом проходит (`L15 collided unwind: val=1501`), то есть
сценарий, который у нас есть, до этой ветки не доходит.

**Когда чинить:** вместе с любой работой по диспетчеру. Семантика Windows:
`finally`, бросивший своё, заменяет оригинал — это by design, не баг, и правка
должна именно заменять, а не терять оба.

## Долг: два декодера UNWIND_INFO на одну спеку

Тот же пункт 6 в `docs/eh-audit-2026-09.md` («Свести два размотчика в один»), и
там же уточнение: `StackFrameIteratorOps.Next` беднее на два пункта разбора, и
оба дают молчаливо неверный SP. Здесь — то, чего в аудите нет.

`SehUnwind.ApplyUnwindInfo` (`OS/src/PAL/SharpOSHost/SehUnwind.cs:610`, полный
разбор опкодов) и обходчик Tier A разбирают одну и ту же структуру `winnt.h`
каждый по-своему. Цена — одна спека, два места правок и два места регрессий:
любой фикс декодера (ближайший — опкоды 8/9 выше) надо приземлять в оба.

**Целевая форма.** Tier A зовёт общий `ApplyUnwindInfo` вместо своего switch'а.
`SehUnwind` уже kernel-side и от CoreCLR не зависит, циклической зависимости
нет. Отличие, которое придётся закрыть адаптером: Tier A ходит по
`PAL_LIMITED_CONTEXT`/`RegDisplay`, а не по `CONTEXT`.

**Триггер:** первый декодер-баг, воспроизводящийся в Tier A, либо момент, когда
фикс придётся дублировать в `StackFrameIterator.cs` — тогда сведение дешевле
дубля.

**Пока их два:** правка опкодов или `EstablisherFrame` в одном декодере обязана
явно ответить «нужен ли тот же дифф во втором» — строкой в step-writeup.

## Слить дуал-копии MinimalRuntime в общую

Отдельным шагом: blast radius — пересборка обоих ярусов ради чистого
рефакторинга.

**Факт:** `OS/src/Boot/MinimalRuntime.cs` и `apps_native/sdk/
MinimalRuntime.cs` — дуал-копии. После step141 (апгрейд app-копии до
kernel-парности под делегаты/std) их System-секция **текстуально
идентична** (~500 строк зеркала): Object + примитивы (с ToString/
Parse/IsNaN), IntPtr/UIntPtr, Single/Double, Nullable, Array, атрибуты,
EETypePtr, RuntimeHelpers/RuntimeFeature, Runtime*Handle. Логика НЕ
дублируется (всё форвардит в shared NumberFormatting/NumberParsing) —
дублируются объявления типов и тонкие обёртки, потому что ILC требует
core-типы внутри каждого SystemModule.

**Целевая форма:** общая System-секция уезжает в
`std-no-runtime/MinimalRuntime.Core.cs`, включаемый обоими
csproj (ровно как любой std-файл — каждый компилит его в свой
SystemModule). В tier-файлах остаются только хвосты: у ядра
DllImport/CallingConvention, у аппы RuntimeImports
(ManagedStartup/RhNewString) + StartupCodeHelpers/ThrowHelpers +
NativeMemoryStubs (namespace SharpOS.AppSdk vs OS.Boot).

**Почему это долг:** step141 уже показал механику гниения — каждая
добавка к примитивам (ToString/Parse/IsNaN) вносилась парным
идентичным диффом в оба файла; пропуск одной стороны = тихий дрейф,
который всплывёт как «у аппы int.Parse есть, у ядра нет» через
несколько степов (родня `curated_csproj_drift`).

**Триггер:** следующая правка, которой понадобится трогать примитивы/
IntPtr/Nullable в MinimalRuntime — сначала слить, потом править один
файл. Либо любой замеченный дрейф между копиями.

**Интеримное правило (пока две копии):** любая правка одной копии
MinimalRuntime обязана явно ответить «нужен ли тот же дифф во второй»
(строчка в step-writeup).

## Выделение: ядро на медленном пути

Приложения выделяют быстрым путём (`GcHeap.TryAllocateFast`: `new` объекта из
двух полей — 8,3–8,8 нс против 5–7 у CoreCLR в той же QEMU). Ядро — прежним
`GcHeap.Allocate` (~17 нс): у него хук `s_allocationAllowed`, который считает
выделения внутри прерываний, и быстрый путь при хуке выключен. Перенести
проверку «внутри прерывания» в быстрый путь одним чтением (глубина прерываний
планировщика) — и ядро получит то же. Строки ядра в управляемой куче (step203)
выиграют первыми.

## Труба на больших графах

30 002 объекта, блок 1,87 МБ (`PIPEPERF`, граф `big`; step208). Раскладка
после теневой карты — первым `RegionWriter.Add` (первое касание объекта).
Перевод после слияния проверки и сдвига (step208) — первый проход (план по

поиском достижимого) — для корня всего блока линейный `Region.ToHeap` дешевле.
Инструмент: `PIPEPERF --profile lay|write|resolve|release|toheap|bw` в режиме
тестов, адреса — по `dumpbin /disasm` `PipePerf.exe` (слот 1: +0x4000_0000).

## Ожидания PAL с таймаутом — опросом

`ThreadStubs.WaitForSingleObject`: у семафора и мьютекса с конечным таймаутом,
у `WaitForMultipleObjects` всегда — цикл «проверить, прочитать HPET,
`Scheduler.Idle`». `Idle` спит, только когда работы нет ни у кого: рядом с
занятыми потоками такой ожидающий не спит, вклинивается между их переключениями
и читает HPET (7,7 мкс под WHPX). У `Event` и ожидания потока это снято
(step208, `Event.Wait(timeoutMs)`) — тот поток и съедал переключения труб. Нужно
то же для `Semaphore` и `Win32Mutex` (список ожидания + очередь таймеров), а для
многих объектов — поток в нескольких списках сразу (сейчас блок ожидания один).
Сон до тика вместо `Idle` пробовался: проще, но каждый проход — до 1 мс.

## Поколения в сборщике

Сборка — mark-sweep без поколений: каждый раз размечает живое и проходит всю
кучу, мёртвое тоже. Приложение собирает при исчерпании бюджета страниц
(64 МиБ), то есть проход по десяткам мегабайт на сборку; у CoreCLR молодое
поколение собирается, не трогая мёртвых. Нужно: молодое поколение поверх
контекста выделения, барьер записи с карточной таблицей (барьер для обменной
кучи уже есть), продвижение выживших. Отдельная большая работа — для ядра и
приложений сразу, общая std.

Пауза: на одном ядре сборка идёт под запретом вытеснения, и вся её
длительность — задержка отклика (проба step155: ~16 сборок за 100 мс, куча
растёт, сборка — единицы-десятки мс). Станет видно, когда вытеснение включится
везде. Дешевле поколений — собирать реже или инкрементально.

## Модель процессора QEMU по умолчанию

`run_build.ps1` даёт `-cpu qemu64,+nx`: CPUID без SSE4/AVX/BMI, и JIT CoreCLR
строит код под этот минимум. `Bench.dll` в QEMU — в 2–4 раза медленнее хоста;
с `qemu64,+nx,+ssse3,+sse4.1,+sse4.2,+popcnt,+avx,+avx2,+bmi1,+bmi2,+fma,+abm,
+movbe,+xsave,+f16c,+aes,+pclmulqdq` — как на хосте (step208), полная батарея
проходит. NativeAOT это не трогает: ILC фиксирует набор при сборке. Решить,
делать ли это умолчанием (PowerShell в QEMU ускорится так же). `-cpu max` под
WHPX роняет OVMF (#GP до загрузки). С step212 к умолчанию добавлен `+rdrand` —
источник `RandomNumberGenerator`.

## Гигабайтные страницы прошивки ломают кучу приложения

С `-cpu EPYC-Rome` любое NativeAOT-приложение падает на старте: `[fatal] app GC
heap init failed` (первый `HeapCommit`). С `EPYC-Rome,-pdpe1gb` — работает
(step208). Версия: OVMF при поддержке 1 ГиБ-страниц отображает всё физическое
пространство такими страницами, и `Pager.Map` отказывает внутри большой
страницы. Не сходится: образ приложения в тот же слот загрузился. На железе с
такой прошивкой не запустится ни одно приложение. Начать с того, чем
отображение образа отличается от `HeapCommit`.

## Атомарный `Interlocked.CompareExchange` по ссылке

Ссылочные перегрузки в `std-no-runtime/Threading.cs` — управляемые
чтение-сравнение-запись, не атомарные. Комментарий рядом объясняет это двумя
доводами, и **оба неверны для нашего сборщика**:

- «нужен барьер записи» — барьера нет. Наш же
  `OS/src/Boot/ByRefAssignRefStub.cs` говорит прямо: несдвигающий mark-sweep,
  без карт и поколений, минимальный корректный шеллкод это копия с инкрементом,
  барьерной работы не требуется.
- «адрес управляемой ссылки в сыром стабе не переживёт несдвигающий сборщик с
  консервативным обходом» — вывернуто наизнанку: несдвигающий и делает такой
  адрес безопасным, объект не уедет. Проблемой это было бы у сдвигающего. И
  целочисленная перегрузка **уже** так делает — `fixed (int* p = &location1)`
  и указатель в стаб, там же строкой выше.

Настоящее препятствие механическое: на ссылочный тип `fixed` не наводится,
нужен `Unsafe.AsPointer` и обратное превращение слова в ссылку (приём есть,
им пользуется `Array.Copy`).

Почему не сделали сразу: цена ошибки здесь — тихая порча кучи, а не падение,
и ни один нынешний вызывающий этого не требует. Повод, по которому всплыло
(гонка ленивой инициализации таблиц `Monitor`), закрыт иначе — таблицы строятся
до появления второго потока, а ленивый путь публикует флаг последним.

Браться, когда появится вызывающий, которому нужна настоящая атомарность на
ссылке; тогда же убрать неверный комментарий, а не только код.

---

**С step183 добавилось `Interlocked.Exchange<T>`** — циклом поверх этого же
`CompareExchange`, то есть с той же дырой. Понадобился порту CBOR
(`CborReader` меняет им кэш списка диапазонов). Под вытеснением он не
атомарен, и имя об этом не говорит; в комментарии у него теперь сказано прямо.
Чинить его отдельно смысла нет — он чинится вместе с `CompareExchange`.

## Запуск сборок подряд: нужна изоляция через контексты загрузки

Проверено 2026-08-20, обе пробы за гейтами (`Probes.SequentialAssemblyProbe`,
переменная `SHARPOS_ALC_PROBE=1` для бутстрапа).

**`coreclr_execute_assembly` можно звать не один раз.** Простая сборка отработала
дважды подряд с `hr=0` и кодом выхода 42, причём после того, как в той же сессии
уже отработал PowerShell.

**Но это тот же процесс и тот же контекст: статика переживает запуск.** Повторный
старт PowerShell упал не поэтому, что «нельзя дважды», а на собственной защите:
`CommandLineParameterParser` держит одноразовый флаг `_dirty` в долгоживущем поле
и отказывается разбирать аргументы второй раз. Любое приложение, которое
инициализируется один раз, наткнётся на то же самое.

**Выгружаемый `AssemblyLoadContext` изолирует статику — проверено.** Счётчик в
загруженной копии показал 1 в обоих заходах, наш собственный при этом дошёл до 2.
То есть каждая сборка получает чистый лист, а хозяйская статика не страдает.

**Что это значит для лаунчера:** он должен быть управляемым и грузить приложения
в свой контекст на каждый запуск, а не звать `coreclr_execute_assembly` повторно.
Тогда «выбрал — запустил — вернулся — выбрал другое» работает, и PowerShell
перестаёт быть одноразовым за загрузку.

**Не проверено:** завершается ли выгрузка на самом деле. Проба печатает «выгрузка
запрошена» — она асинхронна и заканчивается, когда на область не остаётся ссылок.
При десятках запусков подряд это станет вопросом памяти; проверяется слабой
ссылкой после сборки.

## Известные красные пробы ядра

Четыре строки `FAIL` на каждой загрузке, в QEMU и на железе. Причины разобраны;
ни одна не про трубы и не про сборщик.

**`[term] FAIL wide` → `self-test FAIL` (7/8).** Вторая ячейка широкого
символа получает `CharData.Null` шириной **1**
(`vendor/XtermSharp/.../InputHandler.cs`, `var empty = CharData.Null`), а
xterm.js кладёт туда ширину 0. Ошибка самого XtermSharp: наверху ширина всегда
была 1 («until we get a fixed NStack»), мы включили настоящую (`ConsoleWidth`) в
step144 и вскрыли её. Следствие не только в тесте: приклейка комбинирующего
знака к широкому символу проверяет `chMinusOne.Width == 0` и за CJK не
срабатывает; отрисовщик видит вторую половину как пробел. Чинить в форке:
заглушка шириной 0, пометить `SharpOS cut:`.

**`enum.toString: FAIL val=8`.** У ядерного `System.Enum` (`MinimalRuntime.cs`)
нет `ToString`, вызов уходит в `object.ToString()` → `"(object)"`, 8 символов.
Имён членов без рефлексии в образе нет. Путь — генератор, кладущий таблицу
имён для перечислений, или метаданные ILC.

**`[ModuleInitializer]: FAIL val=0`.** В ядре их не вызывает никто. Сток зовёт
`StartupCodeHelpers.RunModuleInitializers` (проход по секции
`ModuleInitializerList`) из заглушки `__managed__Main`; ядро входит через
`EfiMain` мимо неё, а в ядерном `StartupCodeHelpers` нет
`RunModuleInitializers` — ILC и не порождает вызов. Чинить: прочитать секцию
так же, как `NativeAotModuleInit` читает соседние, и вызвать указатели после
материализации статиков. Проба не заведена в `probe_report.ps1` — завести.
(В step119 записано ✅ — расходится с нынешним.)

**`rethrow preserves stack trace: FAIL val=174`.** Проба ищет имя
`RethrowSource` в тексте трассы, а там только адреса — имён кадров нет (блобы
327/313 не читаются). `val` — длина текста; повторный бросок дописывает кадры
верно. Закроется вместе с именами кадров.

**Кириллица в живом логе стенда.** `третий` печатается как `B@5B89`: путь вывода
в COM-порт стенда берёт от символа UTF-16 младший байт. До приложения аргумент
доходит целым (`expect 3` проходит), в логе QEMU — верно.

## Две мелочи в хозяйском слое

**Блокировки чтения-записи берутся исключительно** в обоих режимах
(`HostLocks`): разделяемый доступ безопасен только пока нет пишущего, а
различать здесь нечем. Пере-сериализация, а не ошибка, но на SMP это станет
узким местом.

**Таблица замков перестраивается при переполнении** — записи без владельца и без
ждущих выбрасываются. Работает, но при четырёх тысячах живых замков паникует;
на SMP понадобится нормальное освобождение по `DeleteCriticalSection`.

## net10 не встаёт с первого захода

Флип TFM net8→net10 (ILC 10.0.x) падает на сборке:

```
error: Expected method 'BulkMoveWithWriteBarrier' not found on type '[OS]System.Buffer'
```

ILC 10 требует этот помощник в системном модуле обязательным. Откачено; net9 не
пробован. Бамп ≥net9 = порт новых обязательных хелперов плюс вероятная
переверстка layout major-10/11. Пока не нужно — на net8 живут и делегаты, и
DOOM, и весь std.

## Вычистить docs/build-setup.md

Файл написан по чтению скриптов, а не по прогону на чистой машине, и это
видно: часть утверждений неточна, текста заметно больше необходимого.
Проверять надо построчно против реальной установки — какие пакеты
действительно нужны, какие версии SDK, что из перечисленного лишнее.

Ориентир по объёму: секция «Как запустить» в README — это готовый рабочий
рецепт в одном блоке команд. `docs/build-setup.md` должен либо стать её
детализацией без дублирования, либо исчезнуть, а полезное из него
переехать в README.
