# Трубы: план работ

Основа — сверка спецификации «Трубы SharpOS: архитектура» (Р1–Р45, С1–С16) с кодом.

## Починить

1. **`RhpStelemRef` без проверок** ([GcRuntimeExports.cs:173-181](std-no-runtime/GC/GcRuntimeExports.cs#L173-L181); в [limits.md:284](docs/nativeaot-nostd-kernel-limits.md#L284) записано как silent UB). Добавить проверку null и границ, затем проверку типа элемента.
   Критерий: запись за границу массива ссылок бросает исключение в ядре и в приложении.
   **Сделано (2026-10-02):** null, границы, тип элемента (строго — `ArrayTypeMismatchException`; сначала был прогон со счётчиком, несовпадений 0). Пробы `Probe_StelemChecks` (ядро) и `CheckStelem` (`AotTests`) зелёные, полный прогон всех приложений без `ArrayTypeMismatch`. Без проверки: массивы как элемент/значение (п. 6), вариантность; `RhpLdelemaRef` всё ещё без проверок.

2. **Точный обход корней в ядре вместо консервативного** (хук в [BootSequence.cs:243](OS/src/Boot/BootSequence.cs#L243), сборка в [KernelGC.cs:165](OS/src/Kernel/Memory/KernelGC.cs#L165)). Условия корректности:
   - сборка не начинается из обработчика прерывания;
   - поток, остановленный не в точке вызова, сканируется консервативно целиком, остальные точно;
   - кадры приложения на стеке, когда сборка идёт внутри вызова службы, либо обходятся точно, либо эта часть стека сканируется консервативно;
   - режим `ReclamationDisabled` под CoreCLR не трогать.

   **Сделано (2026-10-02):** хук `GC.s_collectHook` → `KernelGC.Collect` (точный; консервативный путь видел только стек загрузочного потока, внутри службы приложения — ни одного корня). (а) `Thread.InterruptDepth`, сборка из обработчика отказывает. (б) вытесненный поток — консервативно от точки остановки до `StackTop`; не прогонялось, вытеснение выключено. (в) обход ядра перепрыгивает кадры приложений и продолжается с каждого `JumpContext`. Прогоны: `write barrier` с точным обходом (11 кадров); `[kgc-probe] … ok` на каждом вложенном запуске (AotTests ×2, BenchAot, UsbTest, Fetch, старый Foreign), `runs crossed` 2–3.

3. **Прогон: аппаратный сбой в приложении.** Разыменовать плохой указатель внутри `try { } catch (Exception)` в приложении и то же без обработчика. Записать, что произошло.
   Прогон решает, совпадает ли обработчик приложения с исключением, которое создало ядро ([DispatchEx.cs:586-600](OS/src/Boot/EH/DispatchEx.cs#L586-L600) сравнивает таблицы по указателю).
   **Результат (2026-10-02, `AotTests`, `HwFaultProbe = 1`):** не совпадает. #GP на `ReadAt`, обход дошёл до `RunHwFaultProbe` (адрес возврата внутри `try`), но ни `catch (Exception)`, ни `catch { }` не сработали: исключение — `AccessViolationException` ядра (`mt=0x7DA8F2A0`), а `catch { }` в IL — это `catch (System.Object)` приложения. Дальше `[failfast]` → `Panic` → остановка машины. Режим 2 даст тот же путь, отдельно не гонялся.

4. **Общая ловушка вокруг запуска приложения.** Необработанное исключение завершает приложение с отчётом и возвращает управление в лаунчер, а не уходит в `Panic`.
   Место: стартовый код приложения; если прогон из пункта 3 покажет несовпадение, то ещё и в ядре вокруг вызова приложения. После ловушки выполняется та же уборка, что при обычном выходе.
   Прогон из пункта 3 показал несовпадение, поэтому двумя частями:
   - **4а. Исключение типа приложения.** Сбой, у которого RIP в образе приложения, превращается в исключение, созданное std самого приложения: приложение отдаёт ядру фабрику через хвост `AppServiceTable` (отложенный в [limits.md:628](docs/nativeaot-nostd-kernel-limits.md#L628) `RhpThrowHwEx` в приложении). Тогда `catch (Exception)` приложения ловит сбой.
     **Сделано (2026-10-02):** служба `SetHwExceptionFactoryAddress`, фабрика `AppRuntime.CreateHardwareException` (сборщик придержан на время выделения), выбор по RIP в `HwFaultBridge.ResolveException`. Прогон, режим 1: `caught by catch (Exception)`, `AotTests` вышел с 92; ядерная проба `eh L13 hw fault` по-прежнему 3.
   - **4б. Ловушка в ядре.** Необработанное исключение во время работы приложения (поколение приложения активно) не уходит в `FailFast`, а сворачивает приложение к возврату из `JumpStub` с кодом выхода и отчётом; дальше обычная уборка. Ловушка в стартовом коде приложения одна не поможет: её `catch` тоже не совпадёт с объектом ядра.
     **Сделано (2026-10-02):** `JumpStub` сохраняет rbx/rbp/rsi/rdi/r12–r15/xmm6–15, RFLAGS, CR3, RSP в `JumpContext`; `FailFast` зовёт `JumpStub.TryAbortCurrentApp()` → код выхода 134, восстановлены `ExInfoHead.s_head` и глубина `Preemption`. Прогоны: #GP без обработчика (режим 2) и необработанный `throw` (режим 3, три запуска подряд из лаунчера) — `app ended, exit code 134`, `app threads ended with the app: 2`, лаунчер дошёл до `pe launcher done`. Не покрыто: необработанное исключение в рабочем потоке приложения (по-прежнему `Panic`), блокировки служб в момент гибели.

5. **Прерывания после пойманного сбоя в ядре.** Сейчас они остаются выключенными до следующего `IRETQ` (комментарий в шапке [HwFaultBridge.cs](OS/src/Boot/EH/HwFaultBridge.cs)). Восстанавливать флаг при входе в обработчик.
   **Сделано (2026-10-02):** IF из RFLAGS прерванного кода перед `DispatchEx`. Прогон: `Thread.Sleep(50)` после пойманного сбоя в приложении вернулся.

6. **Приведение массивов** ([GcRuntimeExports.cs:200-222](std-no-runtime/GC/GcRuntimeExports.cs#L200-L222)). `GetBaseType()` у массива отдаёт тип элемента, возможны ложные «да». Базой массива должен быть `System.Array`, приведение массива к массиву сравнивает типы элементов.

7. **`FileStream` приложения молча выбрасывает запись** ([FileSystem.AppHost.cs](apps_native/sdk/FileSystem.AppHost.cs)). Пока службы записи нет, бросать исключение.

8. **Версии ABI.** SDK объявляет V2 ([AppStartupBlock.cs:7](apps_native/sdk/AppStartupBlock.cs#L7)), ядро V3. Выровнять и добавить проверку при старте.

9. **Вытеснение для приложений.** Сейчас под лаунчером выключено ([Preemption.cs:5-19](OS/src/Kernel/Threading/Preemption.cs#L5-L19), step184), должно заработать. Конфликт с точным обходом: поток, прерванный таймером не в точке вызова, не описан `GcInfo`.
   Зависит от пункта 2 (условие «поток, остановленный не в точке вызова, сканируется консервативно целиком»). Включать только после него.
   **Решено (2026-10-02):** полное вытеснение на одном процессоре, ядро тоже — модель `preempt_disable`: критические секции `Preemption.Suppress()` уже размечены в 23 файлах ядра и прогонялись под CoreCLR. Недостающее: гонки из step174 (`Scheduler.Spawn`, `NativeArena`, `Fat32`, `TerminalConsole.Flush`), критические секции аллокатора и сборщика приложения, `ExInfoHead.s_head` на поток, подавление на время `DispatchEx` (фильтры), консервативный скан стека приложения у главного потока, аудит `AppServiceBuilder`/`ProcessManager`/лаунчера. Переключатель «вытеснять только код приложений» — в `Probes.cs`, на случай если ядро не выдержит на железе.
   **Сделано (2026-10-03):** вытеснение включено под лаунчером (`Probes.PreemptLauncher`). Найдено по ходу: утечка `Suppress` в `DispatchEx` (finally, бросивший во втором проходе, бросал внешнюю диспетчеризацию — подавление из диспетчера убрано совсем); заголовок объекта писался после критической секции аллокатора (два объекта в одном блоке — `GcHeap.AllocateObject/AllocateArray`); статические конструкторы не были потокобезопасны; ожидание конструктора внутри прерывания (`ClassConstructorRunner.s_canWait`). Прогон QEMU `-UsbOnly -SkipCoreClr -Autorun`, GUI: `[preempt] PASS`, AotTests 95/95 дважды (три проверки вытеснения ok), BenchAot 0, `[sh] done ran=3 failed=0`, все `[kgc-probe] ok`, красные — прежний набор. На железе не гонялось.

10. **Блокировки вместо `Suppress` (SMP).** `Preemption.Suppress()` защищает только на одном процессоре. Для второго ядра — настоящие блокировки в `KernelHeap`, планировщике, `Event`, `ProcessTable`, драйверах. Отдельный проект, не раньше второго процессора.

## Подготовить под трубы

1. **Обменная куча.** Распределитель блоков на страницах вне куч всех сборщиков (`PhysicalMemory.AllocPages` или `NativeArena`), с пулом свободных блоков и меткой владельца на блоке. Не в диапазоне образа приложения и не в сегментах `KernelHeap`.

2. **Учёт ресурсов процесса.** Реестр ресурсов по ключу `AppGeneration`, освобождение у `EndAppRun` → `Scheduler.LeaveApp` ([LauncherBoot.cs:245-249](OS/src/Kernel/Process/LauncherBoot.cs#L245-L249)). `ProcessState` должен доходить до `Exited`.

3. **Данные при старте приложения.** Один механизм для аргументов, позже для концов труб: служба в хвосте `AppServiceTable` или расширение `ProcessStartupBlock` вместе с зеркалом в SDK. Оболочка ([Executor.cs:285-293](apps_native/Shell/Executor.cs#L285-L293)) начинает передавать аргументы.

4. **Генератор для всех образов.** Подключить генератор Roslyn через `Std.props` (сейчас только в ядре, [OS.csproj:93-95](OS/OS.csproj#L93-L95)). Выровнять версию C# у ядра и приложений.

5. **`BinaryWriter` и `BinaryReader` в std.** Перенести одну копию из Fami или TriCNES в `std-no-runtime`, копии в приложениях убрать.

6. **Запрет выделять память в куче сборщика из обработчиков прерываний.** Проверить существующие обработчики, добавить отладочную проверку в распределитель.

7. **Пробелы std для печати.** `DefaultInterpolatedStringHandler` и форматирование `float`.

## Проверить опытом

1. **Ядро как получатель региона.** Ядро принимает регион в памяти вне куч, переводит его на месте и читает, пока идут сборки. Объекты региона и куча ядра остаются целыми.

2. **Чтение по описанию на SharpOS.** Перенести печать графа по таблице описаний с хоста, без зависимости от `FileStream`.
